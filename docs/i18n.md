# Interface languages

MoPilot shows its interface in the twelve languages Claude Code documents itself in: English, Simplified and
Traditional Chinese, Japanese, Korean, Spanish, French, German, Italian, Brazilian Portuguese, Russian and Indonesian
(`LANGUAGES` in `shared/i18n/languages.mjs`). Settings → General → Language picks one; the default, Automatic, follows
the first OS language the app has, and English otherwise.

This covers the desktop interface. It changes nothing an agent reads or says: replies, tool output and chat content
stay in whatever language they were written in.

## Writing interface text

Write English in the source, as always. There are no keys and no English catalog, so nothing to register:
`scripts/i18n/transform.mjs` finds the text at build time and wraps each piece in a lookup whose key is the English
itself. A string with no translation yet shows in English.

The transform wraps literals only, never a value the app holds at runtime, so a chat titled "Settings" stays that. It
reads:

- JSX text. Text around values and elements is one message (`Found {0} files in {1}`), so a translation can reorder it,
  and spaces at its ends stay out of the message.
- The literal value of a text prop (`title`, `aria-label`, `placeholder`, `label`, `desc`…).
- The first argument of `toast`, `toastFailure` and the error setters, and the message of `copyText`.
- In the interface's files (`objectTextIn`): the text keys of object literals, plus anything shaped like a phrase in a
  branch, a return, a list or a variable. One word needs a position that says it is text: `'Read'` may be a tool's name.
  Names that say a value is for an agent or a program (`prompt`, `command`, `query`, `url`…) are never read, so name
  text the app sends an agent accordingly: `resumePrompt`, not `resumeMessage`. A name covers that value's own literals, not
  interface text deeper inside it; a function declaration counts when its name ends in `Prompt`. The same test refuses a
  function that feeds a send under any other name.

Holes in a message are `{0}`, `{1}`, by position. A template literal or a sentence gets them automatically.

For text the rules can't see, such as a label held in a variable, call `t` from `src/lib/i18n.ts` with the literal
(`t('Harnesses')`), which the catalog check collects too. A file whose literals aren't interface text opts out by
containing the marker `@no-i18n`. Diagnostics (`noteIgnored`, `ignoring`, thrown errors) stay English on purpose: they
land in bug reports we read.

**Never make logic depend on displayed text.** A field the transform translates holds the translation at runtime, so
`row.label === 'Save'` stops matching in every other language. Compare an id or a flag.
Don't edit it either: `text.replace('Auto-fix', …)` does nothing once `text` is translated. Give each case its own
string. A stylesheet can't select on `aria-label` or `title` either. `tests/i18nCatalogs.invariant.test.ts` refuses
comparisons on the display fields of an interface file, and those selectors.

## Catalogs

`shared/i18n/locales/<tag>.json` maps English to the translation. A language's catalog is read by main, which uses it
for the menus and hands it to each window (`electron/app/language.cjs`); `src/launch.ts` installs it before any app
module evaluates, so a module-level `label: 'Save'` reads it too. For the same reason a window changes language only when
it opens. Nothing reloads one on its own: a reload ends its terminals' commands and loses what it holds in memory, so
the menus change at once and Settings offers a Reload window button, held back while a draft is unsent.

`npm run i18n:check` reports each language's coverage against the sources, and `npm run i18n:check -- --missing <tag>`
lists what a language lacks. A pull request does not have to translate what it adds: new text shows in English until
the next translation pass, and only a catalog that would show a raw `{0}` or lose a value fails the tests. Changing an
English string orphans its translations, which the check reports as stale.

## Not translated

- The mobile app, the web portal and `mopilot.ai`.
- Main-process text other than the application menu and the tray's own items: OS notifications, native dialogs, error
  messages main sends a window.
- Text composed at runtime from pieces, and dates and numbers, which keep their current formats.
- Chromium's own strings (a form's validation message, a native picker) in a language the interface lacks: a package
  keeps only the Chromium locales an interface language serves (`scripts/chromium-locales.mjs`, from
  `languageOfLocale`), and Chromium falls back to English for the rest, so they match the English interface. So do a
  window's default date and number formats there (`toLocaleString([])`), which follow Chromium's locale. macOS drops
  the same languages from the app's own `.lproj` folders, so its system panels in the app follow them too. The
  in-app browser does not follow Chromium's locale: it asks sites for the OS's languages
  (`electron/capabilities/browser/honestIdentity.cjs`), as a person's Chrome does.
- The first frame (`index.html`), which shows before the language is known.

The shipped translations were written by a model and checked mechanically for holes; no native speaker has reviewed them.
