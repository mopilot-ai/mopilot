# Architecture map (as of main)

This describes the code as it is on `main`, not the target design (that is `DESIGN.md`). When the two differ, the differences are listed in [Temporary seams](#temporary-seams). Paths are relative to the repo root. Design issues are written D-N, never "#N".

## 1. Process model

| Process | Entry | What lives there |
|---|---|---|
| **main** (Electron, Node, CommonJS) | `electron/main.cjs` | Everything stateful: the chat controller and per-chat session state, the Codex app-server connection, the Claude Agent SDK sessions, the ACP client, the tool registry, accounts and identity, projects, chat files, flags, updater, telemetry, pty, git, search. Windows never talk to a harness directly. |
| **renderer** (one per window; React 19, zustand, Vite) | `index.html` → `src/main.tsx` → `src/App.tsx` | UI, plus the part of the Claude and ACP adapters that translates events into thread items (`src/session/harness/claude.ts`, `src/session/harness/acp.ts`); it sends intents to main through `src/harness/adapters/proxy.ts` and never runs a turn. A window follows main's state through `window.native` (`electron/preload.cjs`, typed in `src/lib/native.ts`). The mini window is a second renderer (`#mini`). |
| **native helper** (Swift, macOS) | `native/helper` → "MoPilot.app" (in `Contents/Helpers`; macOS names an app by its folder, so privacy prompts and System Settings list the helper as "MoPilot"; grants follow its bundle id `ai.mopilot.code.computer-use` and signing requirement, not the name) | Holds Screen Recording and Accessibility grants and the input guard (refuses input to MoPilot, System Settings, Keychain Access; Esc/take-over). Launched with `open` by `electron/capabilities/computer.cjs` and spoken to over a private unix socket (JSON-RPC lines). Input, accessibility and capture are native (CGEvent, Accessibility, ScreenCaptureKit); the helper does not embed a pinned cua-driver (decision WP8-3). The computer-use tools, approval cards and activity bar that use it are on main (see FOLLOWUPS.md, WP8, for what is left). Built by `scripts/build-helper.mjs` into `native/helper/build`. |
| **sage-mcp** (Swift, stdio) | `native/sage-mcp` → `native/sage-mcp/build/sage-mcp` | A tiny MCP server each harness launches as a child. It forwards `tools/list` and `tools/call` over the unix socket in `SAGE_MCP_SOCKET`, after a `hello {token, pid, ppid}` that main verifies (`electron/capabilities/mcp/socket.cjs`). Built by `scripts/build-sage-mcp.mjs`. Without it Codex gets no tools and no basic harness is admitted. |
| **harness processes** | spawned by main | `codex app-server` (one process, JSON-RPC over stdio), `claude` (spawned by the Agent SDK, one per active session), one process per basic ACP harness. All started with the login shell's environment snapshot (`electron/platform/env.cjs`). |
| **website / gateway** | `web/` (Next.js, separate `package.json`) | Not part of the app: the MoPilot admin portal, release feed, flags endpoint (`/api/flags`) and model gateway. Has its own tests (`web/tests`). |

`ELECTRON_RUN_AS_NODE` is fused off, so any helper process must be a native binary, never Electron-as-node.

## 3. Data flow of a chat turn

Common start: the Composer calls `sendMessage()` in `src/store/send.ts`, which calls `native.session.send(chatId, {text, attachments, opts, followUp})` → IPC `session:send` → `ChatController.send()`.

- If the chat is idle, `send()` calls `start()`: patches `turn: 'running'` with a provisional `activeTurn` (`pending-<id>`), settles a `pendingSwitch` first (`SwitchRunner.perform` in main: no window involved), then `dispatch()`. The send that carries a switch waits in `perform` (history, Git, the new session) before any adapter emits `turnStarting`, so the sending window shows the message itself first (`src/store/earlyTurn.ts`: `pending-<request id>`, the id main keeps as the queue item's) and the adapter's `turnStarting` carries that id as `itemId` and replaces the early copy (`addPendingTurn`), so the message shows once. A switch that cannot settle keeps the message first in the queue, puts the `pendingSwitch` back (the retry still goes to the harness the user chose) and ends the turn `crashed` with the reason and the next step; the early copy shows that as a failed turn, and the retry's own turn replaces it.
- If a turn is running, the message is queued in `SessionState.queue` (each item keeps its full SendOptions), or steered into the turn for Codex and Claude when the user chose that and there is no plan, goal or switch. ACP follow-ups always queue.
- `ref(chatId)` reads the chat's last segment from the v2 chat file (`{kind, id, instance, key}`); `kind` is `codex`, `claude` or `acp:<id>` and decides the path.
- Every state change goes out as `session:patch` to all windows; they apply it in `rev` order.

### Codex (runs entirely in main)
1. `dispatch()` → `CodexAdapter.startTurn(chatId, ref, item, origin)` (or `startGoal` for `/goal`, `steer`).
2. The adapter sends `turn/start` over the single `AppServer` pipe, adding model, effort, permission and the thread's tool config from `prefs` and the item options.
3. App-server messages arrive in `AppServer`, pass the intercept chain (accounts, `codexServerRequests`, `CodexToolInjection.observe`), then `CodexAdapter.onMessage` which maps them to their chat and calls `observe` → `ChatController.onCodexMessage` (turn started/completed, approvals added to `SessionState.approvals`).
4. The same messages go to windows as `codex:item` events (`codexEmit` in `electron/app/windows.cjs`; `mine` is true for the window that sent the message). In the window `onCodexItem` (`src/store/send.ts`) feeds `applyNotification`, which updates the thread view.
5. A user's answer to an approval goes `native.codex.respond` → `codex:respond`; `controller.onCodexOutgoing` drops a second window's answer before `codex.respond` forwards the first.
6. `turn/completed` → `controller.end()` → idle, then `drain()` starts the next queued message.

### Claude Code (turns in main, translation in the window)
1. `dispatch()` calls `ClaudeAdapter.startTurn(chatId, ref, item, origin)` (`electron/harness/claude/adapter.cjs`). No window is needed.
2. The adapter resolves what the turn runs with: model and effort (prefs, then what the chat picked and its windows pushed with `session:claudeOwn`, then the message's own), permission (plan, or the pref after the auto-mode check), the chat's login, whether the session starts or resumes (`session:claudeNew` names a session a window just created), its folder. It emits `turnStarting` to the window the message came from (`claude:event`), brings a live CLI in line (`setModel`, flag settings, permission mode; none when the login changed), and sends through `ChatController.claudeSend()` (turn bookkeeping), which builds the SDK user message (`electron/harness/claude/message.cjs`) and calls `electron/harness/claude/index.cjs` `send()` (`electron/harness/claude/sessions.cjs`). That starts a session with `startSession()` when needed (SDK `query`, `buildSessionOptions`, injected SDK MCP server). Then `turnStarted` (or `turnFailed`), and the first message of a chat gets its title written in main (`threadName`).
3. SDK messages are emitted by `harness/claude/index.cjs`; main's hook `onEvent` → `ChatController.onClaudeEvent()` updates turn state (a `result` message ends the turn; `outstanding` counts prompts in flight) and `ClaudeAdapter.observe()` keeps the goal, then `broadcast('claude:event')` sends them to windows, where `onEvent` in `claude.ts` translates them (`claudeTranslate.ts`) into Codex-shaped notifications for the store.
4. Steer: `ChatController.send` with `followUp: 'steer'` calls `ClaudeAdapter.steer` (priority `now`). Stop: `session:claudeStop` → `ClaudeAdapter.stop`, which pauses an active goal first and interrupts.
5. Goals: the goal bar's buttons call `session:claudeGoal` (`pause`, `resume`, `extend`, `clear`); the adapter runs the plans of `shared/claudeGoals.mjs`, sending `/goal ...` through the controller. A crash holds an active goal, and Resume then clears the CLI's goal before setting it again.
6. Permission requests: `canUseTool` in `harness/claude/sessions.cjs` → `requestPermission` → event `permission` → `addApproval` (`method: 'claude/permission'`); answered through `claude:permission`.

### ACP harness (client and turns in main, translation in the window)
**Decision: the ACP client is hand-rolled** (`electron/harness/acp.cjs`, JSON-RPC 2.0 over stdio, ACP v1 only) and does not use `@agentclientprotocol/sdk` (the plan, WP6-1, first named 1.7.0). Reasons: v1 is all the plan needs, and `initialize` refuses an agent that answers anything else; the SDK is ESM only and releases about weekly (the version named was under the two-week rule when written), so it would add a moving dependency and its `zod` peer to a small surface; and the adapter has to control the spawn itself, with the login shell's env snapshot and the disclaim launcher (`spawnArgs` in `electron/platform/winbin.cjs`) and process-tree kill, which the SDK's own stdio transport would not do. Revisit if the protocol grows past v1.

1. `dispatch()` calls `AcpTurns.startTurn` (`electron/harness/acpTurns.cjs`): it emits `turnStarting` to the window the message came from, builds the content blocks (text, images, file links), and calls `ChatController.acpSend()` → `AcpHost.send(key, payload, meta)` in `electron/harness/acp.cjs`, then `turnStarted` (or `turnFailed`) and the chat's title (its first words). No window is needed.
2. `AcpHost` starts the harness process if needed (only if admitted), runs `initialize`, `session/new` (with the session's sage-mcp in `mcpServers`) or load/resume, then `session/prompt`. Every user turn and `session/update` is appended to `threads/<key>.items.jsonl`, which is also the history source.
3. Host events (`turnStart`, `turnEnd`, `permission`, `session`, `state`, `update`, `closed`) go to `ChatController.onAcpEvent()` (turn state, approvals as `acp/permission`, modes/config options/commands/usage under `SessionState.acp`) and to windows as `acp:event`, where `src/session/harness/acp.ts` and `src/harness/acpTranslate.ts` produce thread items.
4. Stop: `native.session.acpCancel` → `ChatController.acpCancel` → `AcpHost.cancel` (`session/cancel`).

## 4. Where state lives

Everything is under `app.getPath('userData')` (`~/Library/Application Support/MoPilot Code`, or `$MOPILOT_USER_DATA`).

| What | Where | Owner |
|---|---|---|
| Chat segments and meta (archived, pinned, unread, worktree, account, …) | `threads/<encoded id>.v2` (`SCHEMA_VERSION` 2) | `ChatsStore` in `platform/chats.cjs`; atomic writes, one file per chat. Legacy `threads/<id>.json` and the old ui-state keys are frozen and mirrored for older builds (flag `data.legacyMirror`). |
| ACP chat history | `threads/<key>.items.jsonl` | `ItemsLog` (`chats.cjs`), written by `AcpHost` |
| Preferences (model, effort, permission, notifications, update channel, …) | `ui-state.json` → `prefs` (plus `codexBin`, `stateVersion`, legacy keys) | `ChatsStore` merges prefs per key so two windows don't overwrite each other; other keys via `state:read` / `state:write` in `electron/app/ipc/chats.cjs` |
| Projects | `projects.json` | `ProjectsStore` in `platform/projects.cjs` |

## 5. Tool injection and approvals

The registry (`electron/capabilities/contract/registry.cjs`) is the single place tools run. A tool is `{name, description, schema, policy: 'observe'|'act'|'irreversible', handler(args, ctx)}`; `ctx` has `chatId`, `segmentId`, `callId`, `signal`. `Registry.invoke()` runs only in main, dedupes by call id, validates args against the top level of the schema, asks the approval hook before any `act` or `irreversible` call (no hook means refused), logs the outcome, and aborts a chat's running calls when its harness quits, or when the user stops its turn on a harness whose channel cannot cancel each call (`abortChat`, wired through `ChatController.onCrash` and `onInterrupt` by the turn ledger in `capabilities/turnEnd.cjs`; Codex and ACP). A call's own `signal` (the Agent SDK's cancel on Claude's channel, which the CLI aborts on an interrupt) aborts that call alone. A tool that serves only some chats names them with `visibleTo(chatId)` (MoMo's memory tools: only MoMo chats, while MoMo is allowed); `Registry.list({ chatId })` leaves it out for any other chat or for a list with no chat, `invoke` refuses it as `unavailable`, and every channel passes its session's chat to `list`.

Per session, `ToolSessions.open(key, {harnessPid, chatId, segmentId})` returns a random server name `sage_<12 hex>` and token. Allow rules match only that random name, so a repo's own MCP server called "sage" is never trusted. Three channels deliver it, one per harness (kinds in `src/harness/adapter.ts` → `Negotiated.toolInjection`):

| Harness | Channel | File | How |
|---|---|---|---|
| Claude Code | `sdkMcp` | `capabilities/mcp/sdkMcp.cjs`, used from `harness/claude/sessions.cjs` `startSession` | A new in-process SDK MCP server per process; each handler closes over its `{chatId, segmentId}` and calls `registry.invoke`. `canUseTool` auto-allows its own tools (`autoAllow`). |
| Codex | `threadConfigMcp` | `channels/codexConfig.cjs` (`CodexToolInjection`) + `harness/codex.cjs` | A config fragment on `thread/start`, `thread/fork` and `thread/resume` adds `mcp_servers.sage_<nonce>` (command = sage-mcp, env `SAGE_MCP_SOCKET`, `SAGE_MCP_TOKEN`, tools pre-approved) and disables Codex's native computer use plugin. Token rotates on resume. |
| ACP | `sessionMcp` | `channels/sessionMcp.cjs` (`SessionMcp`) | sage-mcp goes into `mcpServers` of `session/new` / load; a harness whose quirks say `mcpStdio: false` and whose initialize advertises http (Copilot CLI) gets main's http endpoint instead (`capabilities/httpMcp.cjs`, `ToolHttp`). A harness is admitted only if its tools say hello within 10 s (sage-mcp's hello, or the harness's MCP `initialize` over http). |

For Codex and ACP the call path is harness → sage-mcp (stdio) → unix socket → `ToolSocket` (checks token and that the peer was started by the harness) → `registry.invoke`; over http it is harness → `POST http://127.0.0.1:<port>/mcp` with `Authorization: Bearer <token>` → `ToolHttp` (checks the token, Host and Origin, and with lsof that the connecting process is the harness or one it started) → `registry.invoke`. Both answer tools/list and tools/call through `answerToolRequest` in `capabilities/mcp/socket.cjs`. Main wires it at app ready in `openTools()` of `electron/app/agentTools.cjs` (search for `new ToolSocket`). A legacy path also exists: `codexServerRequests` answers Codex `item/tool/call` requests from the same registry.

Approvals today. Harness permission cards (commands, file changes, questions) go through `SessionState.approvals` and `src/components/thread/Approvals.tsx`. Sage's own tools ask for themselves: the computer-use and browser tools are registered with `authorizesItself`, so the registry's generic hook (`Registry.setApprover`, with no approver installed on main: an `act` or `irreversible` tool without `authorizesItself` is refused) is not asked, and they raise Sage-owned cards through `ApprovalBroker` (`electron/capabilities/contract/approvals.cjs`; `ApprovalKind` `computerAccess`, `computerConfirm`, `browserOrigin`, `visionConsent`), which join the chat's `SessionState.approvals` and show in every window. Authorization by mode uses `anchorOf()` from `harness/quirks/index.cjs` (mode id → readOnly | ask | auto | full).

## 6. Identity layer

`electron/identity/contract/registry.cjs` defines `PROVIDERS` (openai, anthropic, mopilot, plus gateway profiles by host) and the `Instance` shape (harness, provider, credential kind `cliLogin | harnessAuth | sageKey`, billing `subscription | apiKey | credits`, status, active). The account modules keep their own records (`accounts.cjs`, `harness/claude/accounts.cjs`, the Claude key in `harness/claude/auth.cjs`, the MoPilot device key in `mopilot.cjs`); each harness has a driver (`identity/drivers/codex.cjs`, `harness/claude/index.cjs`) mapping them to instances. `electron/app/identity.cjs` registers the drivers on an `IdentityRegistry`, and `electron/app/ipc/accounts.cjs` serves `identity:view`. Switching accounts is only allowed within the same billing lane (`identity/contract/switch.cjs` → `shared/switch.mjs`), which is also what carries Claude goals over. Renderer views: `src/harness/accounts.ts`, `billing.ts`. Basic harnesses have no identity driver yet (they sign in themselves).

## 7. Temporary seams

- **Codex's thread items are built in the window.** Codex's, Claude's and ACP's turns all start in main (their adapters), with or without a window. Claude's and ACP's are translated there, by the core (`core/crates/translate`), and reach the window as items; their stored history is read there too, and the window gets a page of turns, the latest 30 with a cursor for the ones before, which it reads as the chat's older history. So state that spans turns, such as a background agent settling turns later, reads as one replay has it, and raw SDK messages never cross to the window; they are many times the size of the turns built from them. Codex's items are still read in the window, from the app server's `thread/turns` pages, through `shared/codexTurns.mjs`, which main uses too for a switch's handoff record (`electron/session/switch.cjs`).
- **`HarnessAdapter` is a type, not an implementation.** `src/harness/adapter.ts` defines the contract but no class implements it; `CodexAdapter` and `ClaudeAdapter` (`electron/harness/codex.cjs`, `electron/harness/claude/adapter.cjs`, both run in main) are similar in shape but not typed against it, and ACP is `AcpHost` in `electron/harness/acp.cjs`.
- **Components still compare against harness names** (`tests/boundary.test.ts` ceilings: `harnessLiterals`, `codexRequests`); WP7 replaces them with capability keys and `runSemantic`. Done so far: HarnessPicker, HarnessSettings, the Fast toggle (caps `speed`) and the store's goal / rename / compact / shell / fork. Not through `runSemantic` yet: Stop (`interrupt()` pauses a Codex goal directly, because it must work with goals off), archive, delete, side chats, review, the other store branches.
- **Legacy ids.** Renderer ids are `claude:<id>` / `acp:<harness>:<id>` and bare Codex ids; `toRendererSegment` in `platform/chats.cjs` translates segment records. The legacy mirror into `ui-state.json` and `threads/<id>.json` stays until `data.legacyMirror` is retired.
- **TCC responsibility of child processes (disclaim).** macOS attributes microphone, Automation and file-folder grants to a process's "responsible process", by default the app that started it, so Codex, Claude Code, ACP agents, ptys and every command they run ride on MoPilot's grants. `native/disclaim` is a launcher that `posix_spawn`s its argument with `POSIX_SPAWN_SETEXEC` and `responsibility_spawnattrs_setdisclaim` (a private libSystem symbol, looked up at run time; if it is gone the command still runs, undisclaimed). It execs in place, so pid, stdio, controlling terminal and signals are unchanged, which is why it works for node-pty and for app-server's stdio. `electron/platform/disclaim.cjs` routes every spawn through it: `spawnArgs` in `winbin.cjs` (app-server, ACP agents, version probes), `platform/pty.cjs`, and `sdkBin` in `harness/claude/cli.cjs` (a small generated script, since the Agent SDK spawns the program path itself). Limit: a disclaimed command is its own responsible process, so it loses MoPilot's access to Desktop, Documents, Downloads and removable volumes and macOS asks (or refuses) for the command itself; on a checkout under ~/Documents the e2e fakes fail outright. Because of that it is **opt-in** (`MOPILOT_DISCLAIM=1`) until a person has checked the prompt flow on a packaged build (FOLLOWUPS WP8). The helper app is unaffected: LaunchServices already makes it its own responsible process.
- **CI is disabled** (billing); merges are gated locally (`scripts/handoff/localci.sh`).

## 8. How to add a harness

First tier is reserved for Codex and Claude Code. Basic-tier harnesses use their own native ACP entrypoint and the
shared main-process adapter. Their static source of truth is one descriptor in `shared/harnesses/`, discovered by
`scripts/harness-catalog.mjs`; build, test and typecheck preparation generate its ignored JSON artifact. The app,
server flags, installation UI and version checks consume the same catalog. Adding a harness never requires another
shared ID-list entry.

1. Add the descriptor under its stable id: label, vendor, executable aliases, official install guidance, native ACP
   argv/environment and privacy settings. Start it disabled and leave tested versions empty until native evidence
   exists. Runtime MCP admission remains mandatory; new integrations also require native session recovery.
2. Add a quirks module only for behavior that cannot be static data. Set `runtimeQuirks` so a missing module fails
   closed. Existing harnesses retain their ids and runtime quirks, including Antigravity. Protocol hooks stay at this
   adapter boundary; shared UI reads negotiated capabilities.
3. Add focused UT for actual detection/launch, admission failures, permission/cancel paths, restart identity and
   independent same-folder chats. Directory-discovered invariants check every consumer and every descriptor.
4. Native evidence goes in individual admission records. A source-backed entrypoint or fake test never counts as a
   native admission pass. Release verification runs in CI or an isolated VM under AGENTS.md; only then enable a
   compatible version. Defer a version that lacks tool injection, permissions or reliable continuation.

New additions and the intentionally excluded/deferred agents are described in `docs/native-acp-harnesses.md`.

## 9. How to add a tool

1. Write the handler module, for example `electron/capabilities/tools/<name>.cjs`, exporting `{name, description, schema, policy, handler}` (`debug.cjs` is the smallest example). Choose the policy honestly: `observe` runs without asking, `act` and `irreversible` go to the approval hook.
2. Register it in `openTools()` of `electron/app/agentTools.cjs` next to the `sage_debug_echo` line: `capabilities.register(require('../capabilities/tools/<name>.cjs').tool)`, behind a flag from `electron/platform/flags.cjs` if it is risky (add the key to `DEFAULTS` and `web/lib/flags.ts`). Tools must be registered before sessions start: each session reads `registry.list()` once when it opens.
3. Do not add anything per harness: all three channels expose whatever the registry lists. Handlers get `ctx.signal`; honour it for long work.
4. If it needs user approval, extend the approver (`Registry.setApprover`) and add the card in `src/components/thread/Approvals.tsx` through a new `SessionState.approvals` method; do not prompt from inside the handler.
5. Tests: `tests/capabilities.test.ts` (registry behaviour), `tests/toolChannels.test.ts` (per-channel), `tests/e2e/echo.spec.ts` (the real channels end to end with the fake harnesses: copy it and add your tool to the fakes' `MCPCALL`/`TOOLCALL` paths if needed).
