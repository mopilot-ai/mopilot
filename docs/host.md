# Host: run a chat on another machine

A Host is the MoPilot program that runs chats on a machine you pick. The Mac app is the window; the Host does the work, so the agent keeps going when the Mac is closed, and a chat can move from one machine to another. The package is `host/` (see [host/README.md](../host/README.md) for its commands and data folders); the design, with the decisions behind it, is `design/host/index.html`. The goal: from your own Mac, pick which machine runs any session, and never sign in again per machine.

Host is open to every signed-in MoPilot account (see [Who can see it](#who-can-see-it)). MoPilot does not provide machines: a Host runs on a machine of your own, which you reach over SSH or add by command.

## What a Host is

- A Node program (`host/bin/mopilot-host.mjs`), not Electron, carrying one native file, the Rust core built for its machine. It reuses the app's session and harness code with the Electron-only parts replaced by ports (`host/src/electronPorts.mjs`; the modules it loads declare `@host-portable`, checked by `tests/hostPortable.invariant.test.ts`).
- It runs ACP agents, **Codex** (a `codex app-server` per Host) and **Claude Code** (the app's Claude adapter over the `claude` CLI found on the Host), all through the same chat controller the app uses, so queueing, Stop and approvals behave as they do locally.
- It listens on a unix socket in its data folder, never on TCP. The Mac reaches the socket through an `ssh -L` tunnel (`electron/host/sshTunnel.cjs`). A socket path must fit 104 bytes on macOS and 108 on Linux: when the Host's data folder is too deep its socket moves to the system temp dir (`mopilot-host-<hash>.sock`), and the tunnel's local end does the same.
- It authenticates the app, not the network: the app signs each connection with its own key, registered once by a pairing code (`host.challenge`, `host.pair`, `host.auth`). A client that is not paired is refused every chat, file and git request with `unknown_client`.

## Requirements

On the machine:

- Linux or macOS (POSIX). Windows is not supported and untested. The installer refuses any other `uname -s`.
- Nothing to install for the Host itself: the installer brings MoPilot's own Node (see **Set up Node** below). A Host installed from an npm package instead needs Node 22 or newer on the ssh PATH, and carries no Rust core, so it does not serve until it has one. Nothing is compiled on the machine: the Host brings the core built for it (see **Prepare the Host** below).
- `tar` (to unpack the Host and updates) and `sha256sum` or `shasum`.
- The agents you want, installed where the process that starts the Host finds them: `claude`, `codex`, or an ACP agent. The installed unit carries the login shell's PATH.
- For the remote browser, a Chrome or Chromium; otherwise the Host downloads a pinned `chrome-headless-shell` (about 100 MB) on first use.
- Linux, for that downloaded browser: its system libraries (on Ubuntu 24.04 `libatk1.0-0t64 libatspi2.0-0t64 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libasound2t64`; a server image lacks them) and, as a non-root user on Ubuntu 23.10 and later, user namespaces for the browser's sandbox (`kernel.apparmor_restrict_unprivileged_userns=0`). The Host never turns the sandbox off for a user; a start that fails for either reason says which in the error.

From the Mac:

- ssh to the machine (on a Mac: Remote Login on). A key, an agent or a password works: ssh's questions are asked in the app, and a password-only machine gets MoPilot's own key (see **Key sign-in** below). `user@host` or a name from your ssh config works, including `-J` jumps set there.

## Who can see it

`hostAccess()` (`electron/host/access.cjs`; the renderer reads `useHostAccess()` in `src/lib/host.ts`) is true for any signed-in MoPilot account while the remote switch `host.enabled` is not turned off; there is no invite since Host left the closed alpha, and turning the switch off closes Host for everyone. `MOPILOT_HOST_DEV=1` opens it for an unpackaged build. Every Host surface checks that one function: the Run on chip and the composer's host chip, the project menu's machine rows, Settings → Connections → Machines, the registry heartbeat, ssh tunnels, port forwards and tool relays. When access goes away (`onHostAccess(false)`) they tear down. `userData/host-access.json` still records the signed-in account, but with no invite it decides nothing. A new Host entry point adds its own check of `hostAccess()`; it does not add another gate.

## Add a machine

Settings → Connections → **Machines** → **Add machine** opens the **Add a machine** sheet (`AddMachineSheet.tsx`) with three tabs; **Add machine…** in the Run on menu opens the same sheet in place over the chat, so adding a machine never leaves it, and a machine added from a new chat becomes that chat's machine (its folder picker opens when no folder was used there yet). Picking a machine or pressing **Add** starts the install at once, under the machine's own name.

- **Nearby** lists machines found on this network and on Tailscale, looked for only when the tab is open (`electron/host/discovery.cjs`, about 1.5 s): **On your network** (machines that advertise ssh over Bonjour, as a Mac does with Remote Login on, found with `dns-sd`; this Mac is left out) and **Tailscale** (online macOS and Linux peers by MagicDNS name, when Tailscale is installed). A machine found there that an ssh config alias also reaches is one row that connects through the alias, so its user, key and port apply; one already under Machines says **Added**. A Mac on the network that does not offer ssh (its AirPlay receiver names the model, but there is no `_ssh._tcp`) is listed with "Remote Login is off"; picking it shows how to turn it on (below). With nothing found the tab points to **Any network**.
- **Any network** is Add by command: the sheet shows one command to run on the other machine. Leaving the tab ends that command.
  - The only safe command is the one this app shows. It downloads the installer to a file, checks its SHA-256 and runs it only when it matches (`electron/host/bootScript.cjs`). The installer then checks every download against the hash written in it. A `curl … | sh` link someone sends you, even one on a MoPilot address, is not MoPilot's installer: what a boot link serves is chosen by whoever made it.
  - Where the relay has a boot host (`BOOT_ORIGIN`, relay/README.md), the command fetches from that host and the relay's own address serves no boot. An account may start 20 commands a day.
- **SSH** takes `user@host` or a name from the ssh config in one field (saved targets complete it) and **Add**. Typing filters the list under it of concrete `Host` entries of `~/.ssh/config` and its Includes (resolved with `ssh -G`).

The card lists each step as it runs, with its output:

| Step | What it does |
| --- | --- |
| Connect | `uname -sm`; refuses anything but Linux and macOS. |
| Look for an existing Host | Looks for the Host's files there. A Host that is there is never removed by a failed run, even one that cannot run yet (installed on a Node that is no longer on the ssh PATH). |
| Set up Node | The Host runs on MoPilot's own Node, one pinned official build per platform (`electron/host/nodeRuntime.cjs`, checksums from nodejs.org's signed `SHASUMS256.txt.asc`) in `~/.mopilot-host/runtime/<build>`, with `runtime/current` pointing at it. Kept from an earlier install, else uploaded from this Mac's cache (`userData/host-runtime/`), else (or when the upload arrives damaged) downloaded on the machine with curl or wget, within the 120 s an ssh command may take; the archive's SHA-256 is checked on the machine before it is unpacked. Where the official build cannot run (Linux older than glibc 2.28, musl), the machine's own Node 22+ from the login shell is used. Nothing has to be installed on the machine first, and Node need not be on the ssh PATH. |
| Prepare the Host | Asks the Node just set up which Rust core build it needs (`shared/host/coreBuild.mjs`: `darwin-arm64`, `darwin-x64`, `linux-{x64,arm64}-{gnu,musl}`), then builds the app's own Host for it as one deterministic tarball (`electron/host/bundle.cjs`) and checks it against its checksum. A machine with no build stops here, with nothing of its Host changed. |
| Upload the Host | Streams the tarball over ssh into `~/.mopilot-host/incoming/`. |
| Check the upload | SHA-256 on the machine must match; a damaged upload is removed. |
| Unpack the Host | Unpacks to `~/.mopilot-host/versions/<sha>` and points `~/.mopilot-host/current` at it. |
| Write the service unit | `mopilot-host install`: a launchd agent `ai.mopilot.host` on macOS, a systemd user unit `mopilot-host.service` on Linux, set to restart the Host. The unit's PATH is the login shell's (`$SHELL -lic`, so agents in Homebrew, nvm or `~/.local/bin` are found without editing `~/.zshenv`), plus the folder of the Host's Node. |
| Start the Host | macOS: `launchctl bootout`, then `launchctl bootstrap` into the logged-in user's GUI domain (the user domain when nobody is logged in) and `launchctl kickstart -k` (`shared/host/launchd.mjs`): an agent bootstrapped from an ssh session is registered but not started, so the explicit kickstart is what runs it. Linux: `systemctl --user enable mopilot-host && systemctl --user restart mopilot-host`. A Host that is already running restarts onto the version just unpacked. |
| Check the Host answers | Up to five tries of `status`. |
| Get a pairing code | The code is not shown; the app uses it at once to pair. |

**Questions from ssh are asked in the app.** The first command opens one shared connection (`ControlMaster`, `ControlPersist=60`) and every step reuses it. When ssh needs something, the card shows it in place: a machine seen for the first time asks **Connect**, with its key type and fingerprint on hover (`StrictHostKeyChecking=ask` is always passed, so a first-seen key is never accepted silently, whatever the ssh config says); a password, key passphrase or code goes in a secure field and only to ssh (never stored or logged); ssh's own yes/no questions get **Yes**. The answer travels through a small askpass script (`electron/host/sshAskpass.cjs`, plain `sh` and `/usr/bin/nc`, since the app cannot run as Node) over a private socket in the user's temp folder; the app answers only a process descended from the ssh it started (ps and lsof), so another process that reads the token from ssh's environment gets nothing. Only a machine being added may ask: an update or a heartbeat never prompts. A question nobody answers is cancelled after five minutes. A machine whose host key changed is refused with "This machine's host key changed since you last connected…", and nothing is sent.

**Key sign-in.** Right after **Connect**, **Set up key sign-in** makes sure the machine can be reached with nobody there to type a password, since the tunnel and heartbeat reconnect in the background. If this Mac's own ssh setup already signs in without a prompt (a fresh `BatchMode` connection), nothing changes. Otherwise MoPilot makes its own key once per Mac user (`~/.ssh/mopilot_ed25519`, ed25519, no passphrase, 0600), appends its public half once to the machine's `~/.ssh/authorized_keys` (0700/0600), and proves it on a fresh connection with only that key. The machine's record keeps the key (`identity`), and the tunnel, port forwards and every later command use exactly it (`-i … -o IdentitiesOnly=yes`), so a crowded ssh agent cannot exhaust the machine's `MaxAuthTries` first. A machine whose sshd refuses keys stops here with that reason. **Remove** takes it off again (best effort: a machine that cannot be reached keeps the line; delete the `mopilot@…` line from its `authorized_keys` by hand).

**When it ends.** Success reads "<machine> is ready" with **Start a chat on it**, which opens a new chat with that machine chosen. A failure reads as its cause with one action (`shared/host/installFailure.mjs`), the steps behind Details: "Turn on Remote Login on <machine>" with how to turn on Remote Login (System Settings → General → Sharing → Remote Login; sshd on Linux) and **Check again**: the card asks every 3 s for up to 10 minutes whether ssh answers (`host:reachable`, one TCP connect after `ssh -G`) and runs the add again as soon as it does, "Can’t find <machine>", "Can’t reach <machine>", "<machine> didn’t accept the sign-in", "<machine> is out of disk space", "Couldn’t set up sign-in / Node on <machine>", "MoPilot installed but didn’t start on <machine>", each with **Try again**; "<machine>’s identity changed" with **Copy command** (`ssh-keygen -R <host>`); "MoPilot can’t run on <machine>" with **Copy details**.

A failed step stops the run. If this run created the install, it is rolled back (**Undo the install**: unit removed, `current` and the unpacked version put back); an install that was already there is left alone. Running **Install** again on the same machine is safe, and a second request for a machine joins the run in flight.

When the install works but pairing does not, the card shows a **Pairing code** row: run `mopilot-host pair` on the machine (with the Host's own command, see [Update, uninstall, remove](#update-uninstall-remove)) and paste the code. A code is good for 24 hours and is retired after five wrong tries.

The new row shows a dot: **Online**, **Offline** or **Needs attention**. The registry asks each machine for `status` every 30 seconds and calls it offline 90 seconds after the last answer. An ACP agent counts as signed in once the Host saw a sign-in or a turn finish, or when its `initialize` lists no login methods and its quirks name no setup (`host/src/noSignIn.mjs`, asked once per binary and kept 10 minutes), so a machine with only such an agent is Online. **Needs attention** with a reason means the Host is up but cannot run a chat yet: no agent installed, an agent not installed on the machine, or an agent signed out.

**Remove** asks first (`host:removePlan`), and asks ssh itself (a bounded `true`, 10 s), not the Host's status. On a machine that answers over ssh, its Host running or stopped, it stops the Host and deletes its files (install tree, data and config), then forgets the machine: tunnels and forwards end, tabs drop, the relay credential is revoked and MoPilot's key line comes off `authorized_keys`. A turn running there is named in the sheet and stops; a Host that does not answer while ssh does may be wedged rather than stopped, so the sheet says a turn may be running. A Keep running daemon is root's, so the sheet takes the administrator password; without it the Host is left running and the toast says so. Nothing is touched on the machine unless every other listed row (ssh or relay) is proved a different Host by what this Mac knows: another address and both Host keys known and different (two rows of one machine whose keys differ because one is stale cannot be caught). A lone row is purged whatever its key. Otherwise the row is only removed here and the sheet and toast name the other row ("uses the same Host", or "can't be told apart" when a key was never pinned); a Mac whose Host never said whether it starts at boot is not touched either. A failed uninstall keeps the machine in the list with the cause; **Remove here only** forgets it anyway. If ssh drops or runs out of time mid-way, the cause says the Host may be stopped and some files may remain. A machine that does not answer, or was joined by command (no ssh), is forgotten here only and the sheet says its Host and files are still there; nothing is retried later. This Mac's Remove keeps the row, with the cause, while its Host is left.

## Reaching a machine: direct or through the relay

Each machine is reached directly over the ssh tunnel or through MoPilot's relay; the row reads **Direct**, **Via relay · N ms** or **SSH** (no relay path).

- **Path** per machine (`host:setPath`): **auto** prefers direct and falls back to the relay silently; **ssh** never uses the relay; **relay** always uses it. After install, the machine needs no inbound port and no Remote Login.
- **How it works.** The Host dials the relay over wss (Host feature `relay`) and pipes each stream into its own `host.sock`, the same seam `ssh -L` uses; everything above it is unchanged. Traffic is end-to-end encrypted with the phone's scheme (`shared/remote/crypto.mjs`); the relay sees only ciphertext and stores no Host frames.
- **Enrollment** happens at pairing, over ssh: the app mints a per-Host id and secret and registers only the secret's hash (at most 10 Hosts per account). The Host keeps its credential in `<config>/relay.json` (0600), the app in a sealed `host-relay.json`.
- **Remove** revokes the relay credential, even while the relay is down (pending revokes are kept in `host-relay-revokes.json` and retried).

## Start a chat on a machine

Pick the folder on the machine: the project menu lists **Folder on <machine>…** for each online machine, which opens a browser bounded to the folders the Host shares (the Host user's home by default, or `MOPILOT_HOST_ROOTS`), with clone and worktree actions. Then choose an agent the machine has and send the first message: that message starts the chat on the Host (`host:startChat`, then `chat.start`).

A new chat picks where it runs in one place, the **Run on** chip in the bar above the composer (`RunOnChip.tsx`): this Mac, one of your machines, or, when the chat's agent has Codex Cloud, one of its environments; picking one drops the other, and the project chip then names only the folder on the machine. Without Host the bar keeps **Work in** (this computer or Codex Cloud). Once the chat has started, the composer's host chip names the machine it runs on and continues it elsewhere (**Switch host…**).

**Cloning a private repository.** When a clone fails because the machine cannot sign in to the address, the picker offers **Use this Mac's sign-in** under the notice, with "Used once, not saved on the machine." The click is the consent, for that one clone. Only `https` addresses qualify (ssh keys are never lent). The app reads this Mac's sign-in for exactly the address's protocol and host (`git credential fill` with prompts off, else `gh auth token --hostname <host>`, each with a timeout; a keychain prompt or a failure counts as no sign-in) and sends it on `git.clone` as `credential`, which needs the `cloneCredential` feature: an older Host is told to update, never served without it. The window never sees the credential. The Host gives it to that one `git clone` child through its environment and a credential helper scoped to the address's host (`credential.helper=` cleared first), so nothing lands in the address, `.git/config`, a credential store, the argument list, the dedupe ledger (which keeps only the outcome) or an error (a failure line is scrubbed of it), and a redirect to another host gets nothing. A retry with the sign-in uses a new attempt key. If this Mac has none for that host the picker says so and offers nothing.

Limit: only the clone borrows it. A later `git pull` or `git push` on that machine, by you or by an agent there, still needs the machine's own sign-in.

**Git never waits on a person on the Host.** Every git the Host runs, and every agent's git, prompts for nothing: no terminal prompt, no credential helper window (`GCM_INTERACTIVE=never`), so a machine with Git Credential Manager fails a clone in seconds instead of hanging. The machine's own helpers still apply, so a sign-in the machine has keeps working. An agent's git with no sign-in fails with one line that names the cause (`MoPilot: git has no sign-in on this machine for https://github.com. Sign in here (for example gh auth login), or do this from the Mac.`), written by a small askpass in the Host's data folder; a `GIT_ASKPASS` you set is left alone. `host.status` takes an optional `signIn: ["github.com"]` (up to four hosts) and then also answers `gitSignIn: { "github.com": "yes" | "no" | "unknown" }`, read with `git credential fill` the way a pull would (4 s limit, kept for a minute, the secret never returned); the heartbeat never asks, so it costs nothing until asked.

A chat on a Host is an ordinary chat in the sidebar; list, open, search, rename and restart work as for a local one, because the app writes the Host's events into the chat's own transcript.

## How a chat runs

- **One owner, one epoch.** Every chat has an owner Host and an epoch (`electron/host/ownership.cjs`, the Host's `epochs.json`). Each write the app sends carries the epoch; a Host refuses an older one with `stale_epoch`. Moving a chat (see [Continue on another host](#continue-on-another-host)) is the only thing that raises it.
- **A retry is one input.** Every request carries a key the Host remembers on disk (`host/src/ledger.mjs`), so a lost reply followed by a resend runs once. A key reused for a different request is refused (`key_reused`).
- **The stream.** The Host turns what its agent does into durable records (`{ t: 'event', family, event }`, family `acp`, `codex` or `claude`) and live deltas. The app's mirror (`electron/host/remoteChats.cjs`) writes them into the transcript and replays them on the app's event bus, and resumes after a reconnect from `(generation, rev)`. A Host with a durable session journal keeps that chat's generation and revisions across a restart; reserved sequence numbers may leave gaps, but are never reused. Older Hosts start a new generation, so the app takes a fresh snapshot instead of mixing numberings.
- **Second vocabulary (`stream2`).** What an app built before it would misread is sent only to an end that declared the `stream2` feature (`shared/host/stream2.mjs`); to any other end the Host leaves it out, never degrading it into the chat's reply. It is: a Claude sub-agent's own text and thoughts (updates tagged `_meta.claudeCode.parentToolUseId`, drawn inside that call's card), the live output of a Codex command (`tool_output_delta`, ephemeral: it takes no revision, is replaced by the finished call's whole output, and is retracted when its turn ends), and the **state lane**: the chat's automatic title, `/goal` and background tasks. The Host keeps the newest of each per chat (`stream.mjs` `state`), puts it whole in every Hello and tells changes as `{ t: 'state', patch }` frames, so a reconnect never replays or duplicates it; the app writes the title into the transcript (never over a name the person gave) and shows the goal and tasks from its session store. A Codex sub-agent's approval is a card on the chat's running turn, like any other.
- **Ids.** An ACP chat is `acp:<agent>:<uuid>` on both ends. A Claude Code or Codex chat on a Host is drawn in the app as an ACP-kind chat, `acp:host-claude:<uuid>` or `acp:host-codex:<uuid>`, which the Host knows as `claude:<uuid>` and the bare `<uuid>` (`shared/host/chatIds.mjs`).
- **Approvals.** A permission request is a card the app answers (`chat.answer`); any answer other than allow, or a dismissed card, refuses the call. Claude Code and Codex machine chats have a permission picker (`default`, `read-only`, `auto-review`, `full-access`), saved per machine chat without changing this Mac's defaults. A new machine chat starts in the machine's own pick for that agent, else this Mac's default permission (`prefs.permission`: Ask for approval, Read-only, Approve for me, Full access), else Ask for approval; a chat with no pick that is continued, switched or forwarded starts in its own mode, else that default (`remotePicks`). A mode the machine's agent cannot take is refused with its words and the set-to-its-maximum action, never silently lowered. This is the owner's decision of 2026-11-21 ("completely follow the local one"): all four modes follow, Full access included (`START_POLICY` = `inherit` in `shared/host/permissions.mjs`; `capped` and `remember` are kept as the other rules the same function takes). The selected mode goes to the Host with the chat's first message (`chat.start` `permission`) and by `chat.permit` before the first message after it changes, for Claude Code and Codex; any refusal, including an older Host's `unsupported`, keeps the message waiting. Each queued message keeps the permission selected when it was sent, including across restart. For an ACP chat `chat.permit` is the agent's own `session/set_mode`; an agent that has no such mode or no session answers `mode_unavailable`. Codex's extra-permission requests (`item/permissions/requestApproval`) are cards like a command's.
- **Rename.** The person's name for a chat is one wire write, `chat.rename` (feature `chatName`, paired clients only, carrying the chat's epoch and a key like every chat write). The Host names the family's own session where that family keeps a name (Claude Code's session title, Codex's `thread/name/set`; an ACP agent has none over ACP) as best effort, reporting a failure without failing the rename; records on the chat that the person named it (`config.titleNamed`, in the chat's record, so it survives a restart); and tells every client on the chat's state lane as `title: { name, provisional: null, named: true }`, which is also what `host.chats` (the phone's list) then shows as the chat's title. An automatic title (Claude Code's helper title, a Codex thread name, an ACP chat's cut-short first words) for a chat so named is dropped on the Host and never told. The app keeps the name in its own transcript first, so the person's choice stands while the machine is away; a Host that is unreachable, or too old to have `chatName` ("too old for this. Update it."), says why in a toast and the chat keeps the name here. The sidebar, the title bar, `/rename` and the phone's `chats.rename` are all the one ACP rename in the app (`AcpHost.rename`), which sends this write for a machine chat; a name that arrives on the lane marked `named` (from the phone or another Mac) is written as the person's own title. A Host that does not speak `stream2` sends no title; its chat is named by its first message (the sidebar shows the first line of the mirrored first message).
- **Offline outbox.** A message to a chat on a machine is written to `userData/host-outbox/` first, shown in the chat's queue, and sent in order. While the machine is away the queue reads **Waiting for host**; when it returns, the messages go out under their original keys, so none runs twice. If the Host refuses one (`invalid`, `unsupported`, `unknown_client`, …) it stays marked **Host did not accept it** and holds back the ones after it until you delete it (Send now retries). If the chat moved, it reads **Chat moved to another machine** and waits for the dialog. Attachments to a chat on a machine are refused up front.
- **Unanswered approvals pause the run.** If a chat owned by a machine has cards waiting for three 10-minute periods in a row, the app stops the run on the machine (`host.stop`) and says so; an answer resets the count and a message you send resumes.

### When the Mac is closed

The Host is a launchd or systemd service, so the turn runs on. What it needs from the app waits or fails:

- A running turn finishes on the Host and its records are kept (in each chat's journal under `<data>/sessions`, see Durable history). Open the app again and the mirror resumes from where it left off.
- A permission card stays on the Host until the app answers it. The pause rule above is the app's, so it does not fire while the app is closed. An ACP turn whose agent sends no update for 120 seconds is ended as no progress, and an unanswered card is not progress.
- A tool call from the agent that needs the app (the browser tools, see below) fails at once with "The MoPilot app that started this chat is not connected", and the agent carries on without it.
- A Host that is killed hard (kill -9, power loss) leaves nothing running: the next Host on the data folder ends the agents it recorded in `children.json` and ends their turns as cancelled ("The host stopped while this turn was running.").
- On Linux, a systemd *user* service stops when you log out unless lingering is on for that user. Adding a machine turns lingering on (`loginctl enable-linger`, which systemd lets a user do for themselves), so the Host keeps running after sign-out and starts at boot; a machine that refuses keeps the install, and its **Keep running after sign-out** step shows `sudo loginctl enable-linger $USER`. A rollback turns lingering off only when the install turned it on (`~/.mopilot-host/linger-on`).

## Sign in on a Host

Three tiers; details in [host-signin.md](host-signin.md). Nothing is ever read or copied from the Mac's `~/.codex` or `~/.claude` (`tests/hostVendorFiles.invariant.test.ts`).

- **The machine's own login (Tier 1).** A machine with a signed-out agent shows **Sign in <agent>** on its row under Machines, and a chat on it shows the sign-in card above the composer ("Sign in to <agent> on <machine>", with the agent new chats start on meanwhile). The Host runs the vendor's sign-in with no browser on its own screen; the app opens the link in the Mac's browser and shows the code in the row and the card, with **Copy** and **Open page**. On the machine itself: `mopilot-host login claude` (runs `claude auth login`) or `mopilot-host login codex` (runs `codex login --device-auth`).
- **An API key held by the app (Tier 1).** Settings → Connections → Machines → **How machines sign in** → **My API keys**: kept encrypted on this Mac and lent to the machine with each message, held only in the Host's memory and the agent's process. No sign-in on the machine is needed then.
- **Sign out everywhere** removes the keys here and signs Claude Code and Codex out on every machine, with each machine's result.
- **Organization sign-in (Tier 2).** An admin points MoPilot at the organization's IdP and LLM gateway; each user signs in once on the Mac, and every machine gets a short-lived credential (default 8 h) with each dispatch.
- There is no per-message account pick and no automatic move to another login at a usage limit. A limit or lapsed login ends the turn with the CLI's own message.

## The browser on a machine

When a chat runs on a Host, the in-app browser's tabs run on the Host, owned by `(hostId, chatId)` (`electron/capabilities/browser/tabsByHost.cjs`), and the `browser_*` tools drive them over the Chrome DevTools protocol.

What works:

- **Agent tools and pages.** Tabs open on the Host's Chrome or Chromium (`MOPILOT_HOST_CHROME` names one), else on a pinned `chrome-headless-shell` the Host downloads on the first open into `<data folder>/browser-bin` (the first open answers that it is downloading; ask again in a minute; `MOPILOT_HOST_BROWSER_DOWNLOAD=0` turns the download off). The browser starts when a chat first needs it, never at startup, and exits 60 seconds after the last chat lets go.
- **Frames and takeover.** The pane shows the page by polling screenshots: once a second while you have taken over, every 3 seconds while you watch, none while the pane is hidden. **Take over** forwards your mouse, keys and typed text, so you can sign in on a page; Done hands it back. It is a polled image, not a video.
- **Dev-server preview.** A page on the machine's own loopback (`localhost:3000` there) shows an **Open on this Mac** bar: the app starts `ssh -N -L 127.0.0.1:<free port>:127.0.0.1:<port>` and opens the forwarded address as a browser tab on the Mac. Forwards end when you remove the machine, lose Host access, or quit the app. A port nothing listens on fails with a reason.
- **Tool relay.** The Host relays the tool calls of its agents to the app, which runs them in its own registry (`electron/host/toolRelay.cjs`): the app announces its tools right after connecting and on every reconnect, and answers each call. A call times out after 30 minutes; Stop and a closed connection cancel it.

What does not:

- **Computer use and the user's Chrome are not remote.** They stay on the Mac. A Host chat has no desktop control, Claude in Chrome or Remote Control.
- Passwords are not masked in pane frames, and the agent cursor is not drawn on a remote tab.

## Continue on another host

The chip's **Switch host…** (off with a reason while a turn runs, before the first message, while the owner is being checked, or with no other machine) opens a dialog: pick a machine, pick or **Browse…** a folder on it, and continue. A chat moves as a handoff, not a migration: the target starts a new session in the folder, with the conversation so far written in front of the first message.

- **The move is a commit by the owner.** The app asks the target to prepare, then asks the source to commit at its current epoch, then releases the source. The source's `released` record is the commit point. An unanswered commit is `commit_unsettled`: the chat stays where it was and the next try settles it first; it is never taken back by guessing.
- **The handoff text** comes from this Mac's history when the chat ran here, else from the Mac's mirror, else from the source Host's stream. Stream items carry text only (no tool steps, images or compaction); a record that could not be read in full says so in its own text.
- **Code.** For a chat in a git repository the dialog shows the repository state. The target folder is checked or cloned (a credential-free address of the same remote). If the source has uncommitted changes, the dialog asks: **Carry changes** or **Continue without changes**. A carry makes one commit through a temporary index (the source's branch, index and files stay as they were), pushes it to `origin` as `mopilot/carry/<key>`, and the target applies it with `cherry-pick --no-commit` on a clean checkout of the same branch, then deletes the ref. New (untracked) files go only if you confirm them in the dialog.
- **Secrets are never carried.** Files whose names look like secrets (`.env*`, keys and certificates, `id_*`, `credentials*`, `.npmrc`/`.netrc`, token and auth config files, `.ssh/`, `.aws/` folders) are skipped and listed. Detection is by name, not content.
- **The source is lost.** If the owner Host is unreachable, the dialog says so and asks you to confirm continuing without it; only then does the epoch advance (`lostHost` is recorded). With the source gone the record has the folder and an incompleteness note, plus whatever the Mac's mirror holds.
- **Back to this Mac** works the same way; the handoff is settled at the chat's next message.
- Tabs the chat left on the old Host stay for 10 minutes and are then closed; the agent opens fresh ones on the new Host.

## Scheduled tasks on a machine

A task can run on a machine: its dialog's **Runs on** lists your machines and asks for a folder there. A Host that keeps schedules holds the task and fires it while the Mac is asleep or closed (`host/src/schedules.mjs`), each due time once, also across a Host restart; the app adopts those chats when it is back. A run uses only the agent's own sign-in on the machine, because nothing can be lent with the Mac away. What can't start is recorded in the task's history as `failed` with the reason, and a time too old or a previous run still working as `skipped`. Times are read in the zone the task was made in. A task whose agent isn't signed in on the machine (it uses this Mac's key), or a task on an older Host, is fired from this Mac instead, and its run waits in the outbox while the machine is away.

A task carries `onApproval`. With `skip`, a Host-fired run that raises a card closes it at once as `expired`, stops, and the run ends as `needs-approval` in the task's history; with `wait` (also what an older app implies) the normal approval clock applies. A run that waits on a card counts as still working, so the next due time is skipped as "previous run still working" instead of starting a second one beside it.

## Approvals when nobody is there

A Host that declares `approvals2` owns every card that waits for a person (`host/src/approvals.mjs`). It reminds once at 10 minutes and, at 30, closes each waiting card as `expired`, stops the turn and sets the chat's `attention` to `paused`. That pause is not a denial, so the agent never sees a refusal it could work around; the next message clears it and starts with one line saying the action was not run. The first answer to a card wins: a later one, from any client, is refused with `card_answered` and says who answered and when. Every close is a `permissionCancelled` record with a `reason` (`answered`, `expired`, `stopped`, `turn_ended`, `host_restarted`), and an answered one names the client. The chat's state lane carries `attention` (`approval`, `paused`, `credential`) and `host.pending` lists every card and chat that needs a person. While a card waits, an ACP turn's no-progress timer is off. The clock is 10 and 30 minutes until the owner's policy sets another. The app reads this instead of timing cards itself when the flag `host.unattended` is on. A turn that ends on the harness's typed `auth` error (a missing or expired model credential, found by code and never by words) sets `attention: credential` and tells the push port; a turn that later runs to its end clears it.

## Capabilities: tools follow the Host

A Host says what it can do in `host.hello` and `status` (`capabilities`: `iab` browser, `cu` computer use on the user's own Mac, `desktop` the Host's own desktop, `bu` the user's Chrome, `shell`). The app filters per chat: a tool whose surface the owner Host lacks is not listed to the agent and a call that gets through is refused with `capability_missing` (`electron/capabilities/contract/hostScope.cjs`). The composer note under the chip says it in a line, for example "Browser runs on build-box · No Computer use". `iab` is true when the machine has a browser or can download one. This is why a remote chat has no `desktop_*` or Chrome tools instead of tools that fail.
Browser history and bookmark searches, saved-login credential sheets, local-path file uploads, and the `browser_preview_*` process tools use this Mac's stores or filesystem, so they are not offered to chats on a Host. Calls from stale tool lists are refused, including nested batches and cached results. A remote screenshot cannot fall back to an old tab in this Mac's Chrome. Remote page tools continue to use the Host's own tabs; no local browser data is copied to provide these withheld tools.


Version gates work the same way: a request needs features both ends declared (`epoch`, `dedupe`, `isolation`, `lanes`, `browser`, `family`, `tools`), and a peer without one is refused with `feature_missing` rather than served half. A peer whose protocol minor is below the floor gets `version_refused`.

### Keep running after restart

A Mac's Host is the user's launchd agent, so after a restart (an OS update, a power loss) it starts only once that user signs in at the machine; the row says **Restarted · waiting for sign-in**. On a Mac added over SSH, the row's ⋯ menu has **Keep running after restart** (checked when on):

- Turning it on asks once for the machine's administrator password. The app sends it only to `sudo -S` on standard input over an ssh that never prompts and checks the host key; nothing keeps, logs or puts it on a command line (`electron/host/startAtBoot.cjs`). **Copy command** gives the same root step to run at the machine instead.
- Root runs only two scripts made of system tools (`shared/host/launchDaemon.mjs`): write `/Library/LaunchDaemons/ai.mopilot.host.plist` (root:wheel 0644) with `UserName` set to the user by the script itself, unload the user's agent, and `launchctl bootstrap system`; or unload and remove it. The Host runs as the user, never as root, from the `~/.mopilot-host/current` links, so later installs and updates need no new plist. Its status says `startup: { atBoot, fileVault }` (`host/src/startup.mjs`).
- Before anyone signs in the login keychain is locked: an agent login kept there (Claude Code's default on macOS) cannot be read. An API key or organization lease lent with each message needs nothing on the machine; a sign-in through the Host while the keychain is locked lands in `~/.claude/.credentials.json` (Claude Code's own fallback) and survives restarts.
- FileVault: after a cold restart (a power loss) nothing starts until someone unlocks the disk; the row says **Restarted · disk locked**. macOS 26 on Apple silicon also takes the unlock over ssh with a password. A restart that macOS authenticates (`fdesetup authrestart`, as updates use) does not stop there.
- Turning it off (password again) removes the daemon and loads the user's agent; with nobody signed in it starts at the next sign-in. `uninstall` refuses while the daemon is there.

## The Rust core on a Host

Each machine gets one archive, with the core built for it in `host-core/`. Node-API keeps one addon good for Electron and any Node 22+, so nothing is compiled on the machine. Linux builds are made in containers (`scripts/build-core.mjs`): glibc ones for glibc 2.17, the oldest a Node 22 is built for, since a machine too old for MoPilot's Node runs the Host on its own; musl ones with `crt-static` off, or rustc makes no shared library at all. macOS ones are for 13.5, the oldest MoPilot's Node runs on.

The core also frames the tool bridge's streams: each harness on a Host starts the portable sage-mcp (`host/bin/sage-mcp.mjs`) under the Host's Node, and it cuts the harness's and the tool socket's lines with the core beside it in `host-core/`, as main does (`electron/platform/coreFraming.cjs`). Without a core it says so and exits before it connects; a Host without one offers no tools anyway, since the peer check is the core's.

A Host does not serve without its core. `serve` exits with the reason, `status` gives it as `core.problem`, and the app's install fails at **Check the Host answers** with those words. An update is kept only if its core is for this machine, matches its record and loads here in a child process, so a bad one leaves the running Host alone.

The app carries all six in `resources/host-core` with their hashes in `app.asar`, and refuses to send one that changed. The signed update manifest covers the archive's SHA-256, and so the addon; the Host checks the addon against the archive's record when it stages an update and before each load. A package with none of them (a developer's) sends the checkout's own core for this machine's build and refuses any other. A Host whose addon fails to load (a home mounted `noexec`, for one) won't serve, and `status` says why; an install that ends this way puts back the Host it replaced.

## Update, uninstall, remove

The Host's own command on a machine installed by the app is `~/.mopilot-host/runtime/current/bin/node ~/.mopilot-host/current/host/bin/mopilot-host.mjs <command>` (a Host installed before the app brought its own Node runs on the machine's `node`). Add `--data-dir <dir>` for a non-default folder.

- `status`: JSON with version, harnesses (`detected`, `signedIn`), capabilities, the Rust core (`core`: `loaded`, `build`, `routes`, `problem`) and which isolation guarantees the machine gives or lacks.
- `update --manifest <https url|file>`: takes a version only from a manifest signed for this Host by a key it trusts (the paired app's, or `update-key.pub`), not expired and newer than the last build taken; checks the archive's SHA-256, keeps it under `updates/<sha>`, and restarts into it when the Host is idle (no turn, no sign-in; a running turn, including a Claude Code or Codex one, defers it). A version that does not serve after three starts is dropped. With no trusted key every update is refused. `trust-update-key` keeps the public key on standard input as the update key (the install does this with the app's). **Key rotation (Host side).** The keys a Host takes updates from are the update key file, every paired app and the keys signed updates added, less the revoked ones (`<config>/update-keys.json`, `host/src/updateKeys.mjs`). A v3 manifest (it carries `keyId`, the hash of the signing key, which is also a paired client's fingerprint) is checked against that key alone and may carry `nextKey` (a PEM Ed25519 key to trust from now on) and `revoke` (key ids to drop), all signed; they take effect only once the update is taken, and a key cannot revoke itself. A v2 manifest is still accepted and its key fields are ignored. A key the Host has not heard from for 180 days (an app authenticating or a manifest it signed) is refused for updates ("pair the app with it again"); a key first seen counts from then; the update key file (the administrator's own) is never stale. A key a signed update adds also connects (it is registered as a paired client, so a rotated app is not locked out), and a revoked key stops connecting too. **Rotating the app's key (`host:rotateKey`, `electron/host/keyRotation.cjs`):** the app makes a new key, sends every machine a v3 update signed by the current key that adds it, switches to it only when all of them took it, then sends each a v3 update signed by the new key that revokes the old one. Every machine must be online, reached over ssh and on this app's Host build first (an older Host does not know key changes); otherwise nothing changes and the refusal names the machines. A machine that does not take the revocation is remembered and told on the next call. Each key change rides the ordinary update (the same archive is sent again and the Host restarts once idle). Settings › Connections › Machines has **Rotate this Mac's key** (a text button under the sign-in row; it asks first, then says "New key on N machines", or reports failure before this Mac switches identity (some machines may already trust the new key; retry finishes with the same key), or those that still have the old key and will be told on the next press); it is hidden with no machines. The floor is `updates/floor.json` (`seq`, `sha256`): a manifest older than it, or equal with another archive, is refused as a rollback. The app builds the Host tarball it uploads at install (`electron/host/bundle.cjs`) and updates a paired machine with `host:update` (`electron/host/hostUpdate.cjs`). The row of a machine whose Host reports another build than the app carries (`status.build`, a hash of the Host's files that the archive records in `host/BUILD_ID`; a Host that names none counts as older) says **Host is out of date** with **Update**; it then reads **Updating Host…**, **Updates when idle** (the Host waits for every turn to end; after 10 minutes it reads as failed) and **Update failed** with the cause and **Try again**. A machine joined by command has no ssh and is refused in words. **Automatic update (`host.autoUpdate`, off by default).** With the flag on and Settings › About › Update automatically on, a heartbeat that finds a Host strictly older than the app (not one of the same version and another build, and never a newer one) over ssh sends the same update the button does (`electron/host/autoUpdate.cjs`): at most three tries per app build, after 5 minutes, 30 minutes and 6 hours (counted in `host-auto-update.json` in the user data, so a restart of the app does not start again; a timer brings the next try, and two machines at a time are sent a build); a refusal before anything was sent (another update running, the gate, a newer Host) uses no try; this Mac's own Host (`localHost.sync`), machines joined by command and any machine while keys rotate are left alone; after the third failure the row says MoPilot stopped trying, with **Try again**; a failure stays on the row as **Update failed** with **Try again**; a running turn still defers the restart on the Host. A Host that has an update staged says so in its status (`pendingUpdate: { version, build }`, the build it will become) until it has restarted into it; the row says **Updates when idle** ("Waiting for <machine> to finish its work.") for up to 30 minutes after another app's build was first seen staged (for as long as it is this app's own build), and no app sends it another build meanwhile. `idle` (a request on the Host's socket) tells the app whether a turn runs.
- `uninstall`: stops the service and removes the unit (`ai.mopilot.host.plist` or `mopilot-host.service`); it refuses while the Keep running daemon is there. It leaves the Host's files; the app's **Remove** deletes `~/.mopilot-host`, the data folder and the config folder after it.
- **Remove** in the app does both for a machine that answers (see above); the key line comes off best effort.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| "Enter a machine as user@host." or "Enter a machine like user@example.com" | The name has spaces or a leading dash, or characters ssh would read as options. | Use `user@host`, or an alias from your ssh config. |
| "MoPilot has no Host build for this machine (…)" | The machine's Node is not one of the builds: 32-bit, or a CPU other than Intel or ARM. | Nothing changed on the machine, and a Host already there keeps running. Run a 64-bit Node 22+ there. |
| "Could not ask this machine which Host build it needs: …" | The connection dropped, or no Node ran; what the machine said follows. | Nothing changed on the machine. Fix what it says and try again. |
| Install stops at **Connect** with an ssh error or "Timed out." | The password or key was refused, the question was cancelled, the machine is unreachable, or the login takes over 15 s. | Run `ssh <machine> uname -sm` in a terminal; fix the key, agent or password. |
| "This machine's host key changed since you last connected…" | The machine was reinstalled, or something is intercepting the connection. | If you reinstalled it, remove its old key (`ssh-keygen -R <host>`) and add it again; otherwise do not connect. |
| "…: only Linux and macOS machines are supported." | `uname -s` is neither. | Use a Linux or macOS machine. |
| "Neither this Mac nor the machine could get Node …" | This Mac could not download the pinned Node build, and the machine has no curl or wget or no internet. | Connect either one to the internet (or allow nodejs.org through the proxy) and try again. |
| "Node … does not run on this machine (Linux needs glibc 2.28 or newer)…" | An old or musl Linux with no Node 22+ of its own. | Install Node 22+ there (the login shell must find it) and try again. |
| "The upload does not match its checksum." | The tarball was damaged on the way; the upload is removed. | Try again. |
| "The Host is installed but not running yet." / status step fails | The service did not start; launchd logs to `<data folder>/host.log`. | Read `host.log` or `journalctl --user -u mopilot-host`; on Linux check the user manager runs. |
| Install worked but there is a **Pairing code** row | Pairing failed or the code expired. | Run `mopilot-host pair` on the machine and paste the new code. |
| `wrong_code` ("That is not the pairing code." / "Too many wrong codes.") | A mistyped code; the fifth wrong one retires the code. Case, spaces and dashes do not matter. | Retype it, or run `mopilot-host pair` for a new one. |
| `no_code` / "No pairing code is waiting." | No code was printed, it was already used (a code pairs one client once), or it was retired. | Run `mopilot-host pair`. |
| `code_expired` / "The pairing code expired." | The code is older than 24 hours. | Run `mopilot-host pair`. |
| `unknown_client` / "This client is not paired with the Host." | The app's key is not registered, for example after the Host's config folder was cleared. | Remove the machine and add it again, or pair with a new code. |
| `stale_challenge` / `bad_proof` | A challenge older than 60 s, or a key the Host cannot verify. | Retry; if it repeats, remove and add the machine. |
| Row **Offline** ("No answer for 90 seconds.") | The machine, the service or the ssh path is down. | Check `ssh <machine>`; on Linux check that the user lingers (`loginctl show-user $USER -p Linger`). Messages sent meanwhile read **Waiting for host** and go out when it returns. |
| Add machine: **Nobody is signed in on <machine>** | A Mac's Host starts as the user's login agent, and launchd refuses it with nobody signed in there ("Bootstrap failed: 5"). | Sign in at the machine once and try again; then turn on **Keep running after restart** in its ⋯ menu. |
| Row **Restarted · disk locked** | A Mac with FileVault restarted cold; its disk waits to be unlocked, and the key login is refused there. | Unlock it at the machine (or, on macOS 26 on Apple silicon, `ssh` in with the password once). |
| **Keep running after restart**: "That password didn’t work." / "Needs an administrator of this machine." | sudo refused the password, or the user is not an administrator. | Use the machine's own account password, or **Copy command** and have an administrator run it there. |
| Row **Stops when you sign out** (Linux) | The user's systemd manager does not linger. | `sudo loginctl enable-linger $USER` on the machine. |
| Row **Needs attention** | "No agent is installed on this machine", "<agent> is not installed…" or "<agent> is not signed in…". | Install the agent where the Host's PATH finds it (the unit has the PATH of the install shell), or use **Sign in**. |
| `harness_not_configured` ("Codex isn't installed on this Host…" / "isn't signed in…") | The agent is missing or signed out on the Host. Installing it later needs no Host restart. | `mopilot-host login codex` or `login claude`, or install the CLI. |
| `unsupported` ("<Harness> is not available on this Host", "Switching host isn't available yet.") | The Host cannot do this: changing the permission mode of a family it has no setter for, harness switching, per-message pick on Claude Code. | Expected today; see [Known limits](#known-limits). |
| `feature_missing` / `version_refused` | The app and the Host run builds that differ too much. | Update the older one (add the machine again to upload the app's Host). |
| `stale_epoch` | A write used an epoch the Host has moved past, for example from a window that was behind a continue. | Reopen the chat; the mirror refreshes. |
| `key_reused` | A request key was reused for a different request. | Retry from the app. |
| "Host did not accept it" on a queued message | The Host refused it and keeps the ones behind it waiting. | Delete the message, or **Send now** to retry. |
| "Pick a machine, a folder and an agent." / "<agent> isn't installed on <machine>." | The new-chat pick is incomplete. | Pick the folder again and an agent the machine has. |
| Folder picker: `outside_roots` ("That folder is outside what this host shares.") | The path is outside the Host's roots. | Pick inside the Host user's home, or set `MOPILOT_HOST_ROOTS` on the Host. |
| `directory_missing`, `clone_failed`, `worktree_failed` | The folder is gone, or git failed on the machine. | Pick another folder, or fix the remote or branch; for "This machine can’t sign in to that repository." on an https address, **Use this Mac's sign-in**. A request the Host died in answers `request_interrupted`; ask again. |
| Switch host: "<machine> isn't reachable." | The target is offline. | Wait for it to turn green. |
| Switch host: "The folder on <machine> has changes of its own." / "is on another branch." / "has other commits." / "The changes don't apply…" | The carry's checks on the target failed (`target_dirty`, `carry_other_branch`, `carry_diverged`, `carry_conflict`). | Fix the folder, or **Continue without changes**. |
| Switch host: "<machine> didn't confirm the switch." (`commit_unsettled`) | The commit's reply was lost. | Try again; the chat is still where it was. |
| "This chat moved to another host meanwhile." (`chat_released`, `owner_changed`) | Another window continued it. | Reopen the chat. |
| Browser tools missing on a machine's chat | The chip note says "No Browser": no Chrome and no download possible, or `MOPILOT_HOST_BROWSER_DOWNLOAD=0`. | Install Chrome or Chromium on the machine, or set `MOPILOT_HOST_CHROME`. |
| "This host is downloading a headless browser" | First browser use on a machine without Chrome. | Ask again in a minute. |
| "The browser can't start: … is missing on this machine" / "its sandbox is blocked" | The browser's libraries are not installed, or the distribution blocks user namespaces (Chromium's own message, passed on). | Install the libraries named in Requirements, or allow user namespaces; then ask again. |
| "The MoPilot app that started this chat is not connected" | A tool call arrived while the app was closed or reconnecting. | Open the app; the agent can retry the tool. |
| Forwarded preview "does not open" | Nothing listens on that port on the machine, or the Mac's ssh forward ended. | Start the dev server; open the preview again. |

## Known limits

- **Chats on a machine whose Host is lost.** The app's mirror of a chat (every harness: ACP, Claude Code and Codex events fold the same way) holds the user's messages, the replies and the tool steps between them (commands with their last output lines, edits, reads, searches, fetches, MCP tools, sub-agents), so a handoff from a lost Host lists them (#4003). A compaction is listed as a step (the summary text itself is the harness's own and is not carried), pictures sent with a message are counted ("N attached files, not carried over") and never carried, and pictures in tool results are not mentioned. The mirror holds only what the app saw: a chat the app never followed from its first record still hands over with the incompleteness note.
- **Not carried on the stream yet:** a Codex command's live output stops at 64,000 characters per command (the finished call has all of it). Questions an agent asks are form cards (Claude `AskUserQuestion` and MCP elicitation, Codex `requestUserInput` and elicitation); a Codex question that also allows free text is offered its options only, and an approval for the computer or a browser this machine does not have is declined. A rule Claude Code suggests remembering is offered as **Allow for this session**, the words of a chat on this Mac (the CLI decides where the rule lands: the machine's own settings, as for a chat run there by hand; the Host keeps no rule store of its own), and a plan is approved (**Approve plan**) or kept planning.
- **Goals.** A goal is shown on a machine chat from the state lane (Claude Code's goal as its adapter holds it, Codex's from the app-server's `thread/goal/updated` and `thread/goal/cleared`), and driven from the same goal bar and `/goal` as a chat on this Mac. `chat.goal` (feature `goalControls`; params `{ chatId, epoch, key, action, human?, tokens?, objective? }`, reply `{ goal }`) takes `pause`, `resume`, `extend`, `clear` (`human`: the person typed it), `budget` (`tokens`, null removes it) and `edit` (`objective`); the Host runs it on the agent the chat runs on now, with the same plans the app sends its own app-server (`shared/codexGoals.mjs`), Claude Code's own adapter for its goal, and answers with the goal the chat has after it. **Pause is Stop**: the goal is paused first, then the running turn interrupted, and a Stop on a chat with a running goal pauses it. Setting a goal is a message: `chat.send` and `chat.start` take `goal: true` (the text is the objective); Codex sets it through the app-server, and Claude Code is sent `/goal <objective>` as text, as on this Mac. A basic agent answers "<agent> doesn't support goals"; Claude Code has no `edit` or `budget`, and Codex no `extend`, and say so with the words a chat here has. A Host without `goalControls` is refused before anything is sent ("<machine> is too old for this. Update it."), so a goal is never sent as plain text. The phone app has no goal controls yet.
- **Plan mode.** The app's Plan toggle is disabled with a reason for new and started machine chats, including while ownership is unresolved. A typed app `/plan` retains the text and explains the refusal; main also refuses remote messages carrying Plan instead of silently dropping the mode. Native agent commands remain the agent's own protocol.
- **Permission mode.** `chat.permit` works on Claude Code, Codex and ACP agents that list the mode; `unsupported` and `mode_unavailable` retain the message with the reason. Other ACP agents keep the disabled "Set on <machine>" chip because their native mode ids differ from first-tier anchors. **Plan.** A Host that takes `plan` for an agent says so with `planMode: true` on that agent's `host.status` row (Codex today; Claude Code refuses it with "That permission mode is not one this host knows", because its own exits from plan, `ExitPlanMode` and a model's `EnterPlanMode`, are not yet written back to the chat's mode on a Host). `chat.permit` with `plan` puts a Codex chat in Codex's plan collaboration mode on the mode it was in (kept as `planBasePermission`, as the app's own chats do); any other mode leaves it. A policy ceiling ranks Plan with `read-only` and no ceiling is named after it; the mode Plan's tools run under (the chat's own, or the one Plan was entered from) is clamped to the ceiling each time a turn takes its config, so a ceiling set or lowered later holds a running chat too. - **Chat list.** `host.chats` (feature `chatList`, offered only by a Host with a data directory, and only to a client that declares it) lists the chats this Host holds, so a phone that lost its own memory of them (reinstalled, or its Mac is off) can show them again. Each row is `{ chatId, title, harness, createdAt, updatedAt, epoch }`, newest activity first; `harness` is the wire name a start takes (`claude`, `codex` or `acp:<agent>`, the agent a switch moved the chat to when it did), `epoch` the owner epoch the chat's next write must carry, and the title is the chat's own name, else the cut-short one it replaces, else empty. The answer is bounded by `limit` (1 to 200, default 200) and carries no total, count or cursor, so nothing about chats a client may not see can be told from it. A chat deleted on the machine is never listed. The list is read from a small checksummed `summary` file kept beside each chat's journal (written when the chat is first saved and when its title or agent changes, best effort: a failed write is reported and never fails the chat); `updatedAt` is the journal's last write. A chat saved before summaries existed is listed from the first bytes of its checkpoint, and each call finds the title of the newest ten such chats it lists (and the caller may see) from their journals, read without caching and written as real summaries; the answer carries `titles: { pending, deferred }`: `pending` chats of the answer still wait for a later call (the phone asks again after a few seconds), `deferred` chats cannot be filled (a journal over 8 MiB, or one that cannot be read) and get their title when they are opened: a chat whose journal is over 8 MiB has no title (the phone shows its own placeholder) until it is opened once. One call also reads at most 16 MiB of journal files in all (the size of each chat's checkpoint and events is checked against what is left of the call before it is read, so the total never goes over), so a few big chats do not make a call long: what does not fit waits for a later call (`pending`, not `deferred`; the phone's asks again pick it up). The memory a step uses while it parses is a different figure (about four times the journal's size at the largest, held for that one step only). A chat whose journal could not be read is not tried again until the Host restarts; a write that fails (a full disk or budget) is not that, and ends the filling for that call so the next call tries again. A person with hundreds of old chats gets their titles over several probes: each probe (launch, foreground, a machine's first answer in a session) fills ten, newest first, and the phone asks again after 2 seconds up to five times, so about sixty per probe; a titled chat is no longer a stand-in, so the next probe continues with the next newest rather than starting again, and a chat that is opened gets its title at once. Limits: a chat that was never written to disk is not on the list; archived is a notion of the app, not of the Host, so there is no archived state here; a Host with more than 200 chats lists the newest 200.
- **Journal lifecycle.** Normal journal writes across all chats share a 512 MiB file-byte budget; budget pressure refuses writes rather than evicting history. Atomic replacement temporary files count toward that budget. Journal and stream projections keep up to 128 loaded chats; only healthy durable inactive projections may be evicted, so active subscriptions, in-flight output, unwritten generations and failed readable projections are retained and new opens can receive an explicit capacity refusal. Deleting a chat commits a private tombstone before retiring its journal directory; late native events, resumed sends and restart recovery cannot recreate it. Empty tombstone files are retained as deletion fences; filesystem directory/inode overhead is outside the file-byte budget. An interrupted directory cleanup is collected on a later write after restart.

- **Queued messages survive a restart.** A message the Host accepted behind a running turn is kept in `<data>/queues` (one private file per chat, replaced whole and synced) until its turn starts, it is removed, or its chat is deleted. The next Host on the data folder puts those messages back in the chat's queue in order. - **Durable history.** A serving Host keeps each chat's checksummed journal under `<data>/sessions`, with private file permissions. Durable items and the latest title/goal/tasks survive a restart; unfinished token deltas do not. The log rotates into an atomic checkpoint without dropping history. At the 64 MiB per-chat storage budget, writes fail explicitly rather than silently evicting old items. A storage failure closes that chat’s stream with a typed reason and stops its agent; committed history remains readable, and a repaired disk permits write retry. Normal appends account for only the new record; checkpoints serialize history only at rotation. Sequence reservations allow gaps across restarts. Embedders without a data directory retain the older in-memory behavior. A snapshot larger than one wire frame is marked for lossless `chat.history` paging when both ends negotiate `historyPages`. Pages pin the chat epoch, journal generation and committed revision; individual large items span bounded fragments rather than being clipped. The app commits its baseline only after every page is validated, holds later live frames within count/byte limits, and serializes same-chat reads. A connection change or overflow refuses the read for retry. An older Host or app retains the bounded partial-snapshot behavior; partial history is never advertised as complete. A journal keeps a serialization LRU for up to four items (128 MiB total, 64 MiB per item), so interleaved readers can reuse their fragment sources. Durable catch-up replay has its own 16 MiB budget; a larger replay falls back once to a full snapshot and lossless pages instead of retrying the same resume cursor. Native-session resume is not made durable by this journal.

- **Last Turn in a Host chat's folder (#5255).** `host.gitTurnDiff {path, turnId}` (feature `gitTurnDiff`, `host/src/hostTurnTree.mjs`, the one file that runs git for it; `shared/turnTree.mjs` is the snapshot and tree-diff code this Mac's turn changes (`electron/session/turnChanges.cjs`) runs too) answers what one turn changed: `{isRepo:false}`, `{isRepo:true, baseline:false}` when the Host has no usable start of that turn (never taken, too big for the snapshot step, the Host stopped under it, git has forgotten the objects), or the patch (cut at 4 MB, `truncated`). The Host takes the trees itself, around every turn of every agent: it listens to the stream's `turnStart` and `turnEnd` (Claude, Codex, ACP alike) and learns the folder from the `cwd` of the messages the runtime sends (a message that names none keeps the chat's last one); a snapshot is made without anything waiting for it, so a turn is never delayed, and it is not taken at tool calls, so a machine's Last Turn is read when the pane asks (open, turn change, focus, Refresh) where this Mac's is also pushed after each tool call; an edit made in the first moments of a turn, before its start snapshot finishes, is part of the baseline (about 0.4 s a snapshot on this repository's 13,000 files, 0.7 s on one of 47,000). A snapshot is a Git tree built in a private index file in a temporary folder: status, stash, log, refs and the work tree are untouched (no ref, stash, commit, work-tree file or entry of the repository's own index is made or changed), the repository's filters and hooks never run (the same neutralizing as `git.diff`), but the snapshots add unreachable loose objects to `.git/objects` (as this Mac's turn snapshots do; a real run counted 7 objects at init, 15 after the first turn), bounded by 5 MB per untracked file and 50 MB of untracked files per snapshot plus the files git already stores for the user's tracked edits, and pruned by `git gc` (which then reads as no baseline). Kept: the newest 50 turns in `turn-trees.json` of the data folder, at most 256 KB (tree ids and the chat's folder, never file contents, the oldest dropped first), so a turn's baseline survives a Host restart; a turn that was running when the Host stopped has none (it is lost: the Host answers `baseline: false` for it, never a diff against the folder as it is later, and Last Turn says "This turn's baseline is gone" without showing the turn before it as if it were that one). Only two snapshots are taken at once. The app greys Last Turn for a machine whose Host is older than the app with "Update the Host on that machine to see a turn's changes", and an older Host that is asked anyway answers `host_outdated` with the same sentence.
- **Worktree and branch for a new chat on a machine (#5099).** The composer's Worktree switch and branch chip are the ones a draft in a folder of this Mac has (`src/components/composer/BranchPicker.tsx`), drawn for the folder picked on a machine, by its folder key (`machineFolderKey`), with the machine's Host as the source: `host.gitBranches {path}` (feature `gitBranch`; `host:gitBranches` in the app) answers the list the picker shows (origin's default first, the checked-out branch, whether a worktree can start there) with the repository's top folder and the folder's place in it, read by `shared/gitBranchOps.mjs`, the code this Mac's own list and switch run. With the switch on, the app makes the worktree through `git.worktree {key, repo, branch, from}`: `repo` is the repository's top folder, `branch` a new `<prefix><8 hex>` (Settings' branch prefix, `mopilot/` by default), `from` the branch the chip shows (this machine's copy, else origin's; the Host's HEAD when none), and the chat runs in the worktree, a folder inside the repository keeping its place in it (`<repo>.worktrees/<branch>`, as the folder picker's "Worktree…" makes it). Without the switch, a picked branch is checked out where the chat runs by `host.gitSwitch {path, branch}` (`host:gitSwitch`; the same steps and refusal sentences as this Mac, audited as `git.write` with `what.kind` `switch`, one write at a time per repository together with commit and discard). A folder that is no repository, or a repository with no commit, runs the chat as it is, as on this Mac. A Host from before the feature is not sent `from` or either call (`host_outdated`): the chip is not drawn, and a saved Worktree default starts the chat in the folder with a notice to update the Host. What it does not do on the machine, which this Mac does: no fetch before the worktree, no copy of ignored files, no environment setup script, no pull request or issue as a start, and nothing retires the worktree when the chat is archived or deleted (a chat on a machine never retires one on this Mac; the machine's worktree stays until it is removed there).
- **Code carry.** Secret detection is by file name (a key inside an ordinary file is carried), `.env.example` templates are skipped too, a modified tracked secret keeps its HEAD content on the target, and a clone of a tag cannot be repeated.
- **Heartbeat.** It opens one short ssh lease per machine every 30 seconds (a lease a chat already holds is shared). It is not slowed when the app is idle: the online window, the chip and the phone read the same answer, so a slower beat would show a live machine as offline.
- **Key rotation** needs every machine online, reached over ssh and on this app's Host build; otherwise nothing changes (see Update). A lost app key is replaced by pairing again.
- **Hosted sandboxes** are deferred.
- **Local Network privacy (macOS).** A launchd Host cannot reach LAN addresses until the user allows Local Network access on that Mac, so a self-hosted relay on the same LAN needs that dialog; `relay.mopilot.ai` is unaffected.

## How to verify

- Unit tests: `tests/host*.test.ts` (protocol, epochs, ledger, continue, outbox, tunnels, bundle, each agent family against stand-in CLIs), `tests/hostPortable.invariant.test.ts`, `tests/hostVendorFiles.invariant.test.ts` and `tests/hostAgentBundle.invariant.test.ts` (every offered agent's modules are in the bundle and detected from the unpacked tree; the bundle scanner also follows computed `require` names and `path.join(__dirname, 'file')` reads). A bug in this area gets its test next to the package's.
- The real-machine path: `node scripts/host-accept.mjs --vm <vm>` (or `--ssh user@host`) installs the Host with the app's own installer, pairs, runs a chat on the repo's fake ACP agent, kills the Host mid-turn, updates, uninstalls and refuses a damaged upload. It is release evidence, not a per-PR check. `--milestone M1|M2|M4|M5|M6` runs the Remote Run scenarios of that milestone (`scripts/host-accept/milestones/`, `design/remote-run/plan.md`) after the install and pairing; a check the run cannot make (the card clock, the push to a phone) is a SKIP row that names the gap, not a pass. `--milestone M1 --harness claude|codex` runs M1/S1 on that real harness (its cheapest model at low effort, ask-for-approval, a scratch git repo in the Host user's home); a harness that is signed out or absent is a SKIP, and the run never signs in. `--matrix` runs the Host side of the acceptance bar (`design/remote-run/plan.md`, Acceptance bar): per harness that can run on the machine (fake always; Claude and Codex when signed in, cheapest model, low effort) a journey of stream, tool call, approval, stop, resume after a client leaves and the same chat from a second client; then six chats at once across the harnesses with two clients each and one dropped and returned; then a p50/p95 table (`--runs <n>`, default 5) of start to first frame, the card round trip and resume. A question card and a harness switch are listed as `NOT COVERED` rows, never dropped. `--cell <harness>/<J>` runs only those cells (e.g. `codex/J5`); `--trace <dir>` writes, for each failing step, one JSON-lines file with every wire frame and its time, each touched chat's journal read afresh from revision 0 and the Host's log lines for those chats; `--stop-delay <ms>` makes J5 stop later than the turn's first frame. M6 writes the Host's managed-policy file as root (`sudo -n` only; without it S5 is a SKIP) and removes it in cleanup whatever failed; M4/S10 sets a tiny day limit through `host.policy`, runs a `SPEND <model> <in> <out>` turn of the fake agent and restores the policy. Run it on a Mac with nobody signed in too (auto-login off, after a restart): the Host's start differs there (no GUI domain; see **Keep running after restart**), and a check on a signed-in Mac misses it (#3593).
- **Attachment journeys (#5145).** A journey that attaches a file or folder to a machine chat stages the source where the Host's user cannot read it (another user's folder, or deleted right after the send), because a Host on the same machine as the Mac lets the agent find the source by searching the disk and pass for the wrong reason. It asserts on the agent's turn input in the session log (the Codex rollout's user items, Claude Code's transcript, the ACP prompt blocks) naming the Host-side path, never on the agent's answer. The fake Host logs the same as `turn.input` (`tests/e2e/fixtures/fake-ssh/host-chats.cjs`, `tests/fakeHostChatFiles.test.ts`). `host-accept` has no attachment journey yet; one added there follows this rule.

## The Host's own desktop (G8, #3903)

A Host in a logged-in session can serve its own desktop to a chat, for example a disposable macOS guest. It is a separate capability, `desktop`, never `cu`: `cu` means the user's own Mac, which no Host has, so an app that does not know `desktop` still refuses a Host chat's `desktop_*` tools instead of running them on its own screen.

- **When it reads true.** `status` reports `capabilities.desktop` from the last reading of the helper's own macOS grants (Accessibility and Screen Recording), taken by starting the helper the way a lease starts it. It is read in the background every 30 seconds and counts for 90, so `status` never starts or waits for anything, and a reading older than that is false. It asks for permission state only, so it cannot show a macOS prompt. A Host started by launchd's system domain (Keep running after restart) is expected to read false, because the helper must start in the user's session; that has not been run on a daemon Host yet, so do not turn Keep running on for a sandbox guest. A Host before login or after logout reads false the same way once its reading goes stale. The helper app is provisioned on the machine (`MOPILOT_HOST_HELPER`, else `<data dir>/helper/MoPilot.app`), not carried in the Host tarball; no helper reads false with the reason.
- **Lease.** One chat holds the Host's one desktop (`desktop.lease` with the apps it may control, or any app); the requests are for a paired client only, like `browser.*`. The lease belongs to the connection that took it and to the chat's epoch; every call checks both. A second chat is refused as `busy`, never queued or taken. The connection closing, `desktop.release`, `desktop.abort`, a new owner of the chat (its epoch moved on) and ten minutes without a call (a client that vanished without closing) end the lease, cancel held keys and buttons and give the helper's control back; nothing resumes by itself, and a reconnect takes a fresh lease with fresh grants. If the helper restarts mid-lease the Host takes control again and refuses the next write once (`helper_restarted`) so the chat looks first; reads go on. A launch that never ends (nobody logged in) is given up on after 15 seconds. Unattended means no client: nothing runs for a chat nobody is connected to. `desktop: true` reads the helper's permissions only, so provision a sandbox guest with auto-login, no screen lock and no display or system sleep.
- **Calls.** `desktop.call` passes one allowlisted helper request (`shared/host/desktop.mjs`; no permission prompts, deny list, scripts, pasteboard or recording). The Host enforces the lease's apps on every call: a named app outside them is refused (`outside_grant`) and the grant is injected into the helper's own restriction. A call id makes a resend safe: a repeated id gets the first answer and acts once, also after a reconnect (the Host remembers a chat's last 64 calls for ten minutes, for the chat's current epoch); looks (screenshots, reads) are taken again. Calls of a lease run one at a time; Stop fails the waiting ones at once.
- **Failures the person can see.** `unavailable` (with the reason), `busy`, `call_id_reused`, `no_lease`, `stale_lease`, `outside_grant`, `too_large` (ask for a smaller screenshot), `aborted`, and the helper's own refusals, such as a macOS permission prompt on screen. The helper's hard floor (System Settings, Keychain, password apps, MoPilot) stays on whatever the Host is. Nothing falls back to another desktop.
- **Verify on a guest.** `node bench/g8-host-desktop.mjs --vm <mopilot-*> --helper <path>` installs the Host with the app's installer, gives it the helper and drives lease, screenshot, move, a repeated call id, a second chat and a closed connection (hold the VM's lock first).

## Continue to a Host: every agent

A Host takes a continued chat for Claude Code and Codex as well as ACP agents (feature `continueFamilies`, offered only by a Host whose continue side does; `host/src/continueWiring.mjs`). An older Host answers `harness_not_configured` for those two, which an app that sees the feature missing reads as "too old".

- **Refusals by the fact that holds.** `prepareContinue` answers `agent_missing` (not installed on the machine: `details.agent` names the agent) or `agent_signed_out` (installed, nothing signs it in: `details.agent`, and `details.hint` lists the login the agent offers). A key or lease the app lends counts as signed in, as for a switch. `harness_not_configured` is kept for an agent this Host has not set up (an unknown ACP agent). The copy for all three is `CONTINUE_REFUSAL_COPY` in `shared/host/continue.mjs`.
- **Which agent.** A chat that lives on a Host names its agent as the app draws it (`acp:host-claude`, `acp:host-codex`, `shared/host/chatIds.mjs`); the Host starts that as Claude Code or Codex. The chat keeps its id, whatever family that id spells (a chat that switched agents keeps the id it began with).
- **Binding.** The first message after the continue binds the chat to the agent it was continued on before anything is checked or sent (`bindContinued`, `host/src/continueRuntime.mjs`): a native session of that family in the folder, recorded as the chat's only segment with the handoff, the same start a switch makes. A handoff already bound (a retried send, a restart) is kept; a chat that comes back with a new handoff gets a new session. A chat with no record here whose own id already names the ACP agent keeps the session that id names, as before.
- **Letting go.** A chat is held (`turn_running`) while a turn runs, waits on a card, is starting, or has a message waiting, whichever family runs it. When it has moved, the Host stops its turn, drops its waiting messages and closes its ACP session if it has one (a Claude Code or Codex session is left idle).
