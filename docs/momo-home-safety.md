# MoMo's home: at most one live home

MoMo lives on one Host at a time, named by a home id and fenced by a lease epoch. The Host's rules are pure functions in `shared/host/momoHomeSafety.mjs` (run by `host/src/momoHomeSafety.mjs` and `host/src/momoHome.mjs` inside their own writes); the client's rules are in `shared/host/momoHomeClient.mjs`, and the Mac and the phone call the SAME functions (`decide`, `createSteps`, `reviveSteps`, `execute`). `tests/momoHomeSafetyModel.test.ts` walks both over every order of events with three Hosts and two clients.

## What a Host holds: `host.momoHomeLook {}`

Owner devices only (a paired desktop or phone, never the CLI), read-only, **answered with no grant**. This is the one deliberate exception to "MoMo is veiled": it answers a paired owner device even for an account that was never invited, and says presence only (never any MoMo data). It is advertised by the hello feature `momoLook`, which does NOT depend on a grant (the feature `momo` means a LIVE grant: a Host whose grant lapsed lacks it, so `momo` says nothing about whether a home is held).

Answer: `holds`: `home` (running or moving; `homeId`, `leaseEpoch`, `name`, `state`), `none`, `moved` (MoMo moved away: its data is gone; `movedTo` names the new home), `retired` (a newer home superseded it: its data and key are KEPT; `movedTo`, `lastActive`) or `unreadable`; and `grantLive`; every answer but `unreadable` carries the Host's `leaseEpoch`.

How a client reads a machine (`answerOf`; an unknown `holds` value, a missing or non-numeric epoch or a malformed answer is "not heard"):
- **holds a home** — `holds: 'home'`, whatever `grantLive` says (a lapsed grant means send the grant again, never "no home").
- **holds none** — `none`; `moved` (it keeps where MoMo went); a machine with no Host installed; a Host with no `momoLook` whose reported version is a FRESH release older than `0.4.60` (the first build with a home record).
- **retired** — holds none, but an older MoMo is kept there.
- **not heard** — unreachable, a refusal or timeout, `unreadable`, malformed, and any Host with MoMo that lacks `momoLook` unless its version is a fresh release older than `0.4.60`. A look not made yet is pending: nothing is offered.

**Where the client gets the version**: the machines registry's `hostAppVersion` (a release version such as `0.4.61`); `hostBuild` is a build id and has no order, so it is never used. It must be a release (`d.d.d`): `dev`, `local`, an empty value, a build id or any other text is "not heard", and a version reported more than 10 minutes ago (`VERSION_FRESH_MS`) is "not heard" too.

## The grant

The Mac sends `host.momoGrant { account, features: ['momo'] }` to every paired, reachable machine at home start, every 30 minutes and when a machine returns; it is good for 7 days (`expiresAt`).

## Starting and winning

- `host.momoHomeStart { name, floor?, revive? }` starts at `max(own epoch, newest stamp seen, floor) + 1`. `floor` is the highest epoch the caller has seen on any Host. A floor more than 64 above what this Host knows is refused (`floor_too_high`), an invalid one is `floor_invalid`, and a start past 1,000,000,000 is `epoch_limit`. Nothing is clamped. **The ladder**: a client whose floor is far above the Host climbs in repeated starts, each with `climbFloor(own, target)` (at most 64 above the home's epoch), until the home's lease is above the target (`execute`, at most 200 starts, then `climb_failed`). The same running home asking again with a floor at or above its epoch takes a new lease above it; with none, or while moving, it is answered as it is. (Signed lease stamps as evidence would let one start jump further; they need a per-Host identity key the Host does not have yet.)
- **Which home wins**: the higher epoch; at the same epoch the greater home id (every Host and client agrees). The loser stands down. A winner that is MOVING is never given a new lease under its move: `decide().blocked` says `move-in-progress` and nothing runs until the move ends or is cancelled (the owner is told). A start that only bumps the lease of the running home, or answers as it is, changes the record alone: services are restarted only when a home is taken (made or revived).
- `host.momoStandDown { homeId, leaseEpoch, name? }` retires a running or moving home of another id whose lease the given one beats: its record is written first (a lease that landed meanwhile refuses it, and its services keep running), then services pause and stores close. It is fenced at once (not running, never acting) and RETIRED: its data and key are kept, the record is none with `retired` and a tombstone naming the winner at the WINNER'S lease epoch, with home id, name and account cleared. An equal or higher lease, the same home or a Host with none answers `{ stoodDown: false, leaseEpoch }`. A lease more than 64 above anything this Host has seen is refused (`epoch_unproven`). The client's stand-down uses the lease the winner's start ACTUALLY returned, and runs only when that start succeeded. **A stand-down is climbed too**: a Host takes a lease only 64 above what it knows, so a far winner retires the loser in steps (`execute`), the later ones raising the retired record's lease (`{ stoodDown: true }`, only for the same winner and within the bound), the last at the winner's real lease.
- **A retired home is never deleted by anything but the owner**: not by a move's finish (a finish at a retired home answers as it is), not by a start, and a move is never offered to or adopted by a machine that keeps one (`retired_copy_here`: "<machine> still has an older MoMo. Use it or delete it first."; the client hides such a machine as a move target). **"Delete the old MoMo"** is `host.momoReset { ifRetired: true, expectEpoch }`: only a copy still retired at the epoch the owner saw is deleted (`retired_changed` otherwise), so a revive that landed first is never wiped, and it deletes only that machine's copy, never the current home elsewhere. **Reset**, the owner's plain one, (or an explicit "Delete the old MoMo") deletes its data and clears the retirement, and the machine never starts below the lease it was retired by.
- **The way back**: the client tells the owner once that an older MoMo exists (where, when it last ran): "There is an older MoMo on <machine> (last active <time>). You're using the one on <machine>." with "Keep this one", "Use the one on <machine>" and "Delete the old MoMo". Taking it back (`reviveSteps`) starts the retired home again with `revive: true` above the current lease, with its data, after which the current home stands down the same way (retired, data kept), so the choice can be undone again.
- **The owner is told** which MoMo was kept and that the other is retired with its data kept (`decide().replaced`); a home that was mid-move says its move was replaced ("The move was replaced: MoMo was started again on <machine>").
- **A client creates a home only** when every reachable Host has answered and none holds a home, and either every machine answered "holds none" (choose) or the owner confirmed Start fresh knowing an unheard machine, a tombstone naming a home nobody holds now, or a kept older MoMo may still matter. Start fresh starts above every epoch seen.
- **accept-lease** (the owner keeps the older copy): the older home takes a new lease above the newer one, which then stands down (retired, data kept). A move's target is adopted only above the newest stamp the target has seen, not only above its own record.
- **The machine picker** (`decide().picker`): `choose` for a plain choose; for Start fresh `confirm` (ask first) and, once the owner confirmed (`memory.freshConfirmed`), `fresh`, so a confirmed Start fresh never loops back to the question; null while a look is pending or a home exists.
