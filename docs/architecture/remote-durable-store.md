# Remote durable relay store

The optional v2 store is an isolated persistence primitive. It has no network entrypoint and is not enabled by the existing relay. Schema migration is explicit. Integration requires a dedicated PostgreSQL transaction runner: each callback runs on one connection, commits only on success, and rolls back on error. Every durable operation locks the pair row before examining or changing its state. Counters advance per pair and direction; the epoch changes when a deleted pair is recreated. A frame is acknowledged by its exact id, direction and counter. Expiry retains the high-water mark and coalesces a bounded notice per pair and direction. Only ciphertext and nonce are stored.

The caller must authenticate identities and supply trusted server-side capacity limits and clock values. The store checks pair ownership, direction, epoch and committed revocations of both devices. Legacy revocation does not acquire the pair lock when inserting its revocation record; therefore concurrent revocation and durable operations are not yet serialized. Integration must establish that ordering before exposing this store to clients. A database transaction failure propagates to the caller and must not be presented as success. Database queries are parameterized and the caller must not reuse a transaction connection concurrently.

PGlite tests exercise the transactional storage logic in one local database. They do not establish multi-process PostgreSQL behavior, a production pool adapter, network acknowledgement, or exactly-once delivery across restart. Those require separate integration and end-to-end validation before a durable relay is enabled.
