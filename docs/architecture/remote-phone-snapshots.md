# Phone history and live snapshots

`chat.follow` returns the saved history as bounded display rows alongside the current live item ring. When live items exist, the response has `itemsShape: 'items'`, `history`, and `items`; otherwise `itemsShape: 'rows'` puts the saved rows in `items`. The saved conversation is never replaced by the shorter live ring. `liveTurn` identifies the current provisional run, or is null when none can be established.

`feedSeq` is the watermark already included in the copied live snapshot. Buffer item events while the response is pending, then discard events at or below that watermark. Session patches have a separate `rev` and must be reconciled independently. A history read is asynchronous: `historyStale` indicates an older turn changed during that read, even when its event is covered by the returned watermark.

The feed scopes native turn identities by harness family and native session. Old-turn updates never mutate the current live ring; their events carry `live: false` and prompt a saved-history refresh. Missing ownership, an ambiguous reused completed turn id, or exhaustion of the bounded 1,000-identity tracker cannot establish a new live owner. Ambiguous ownership remains visible as `liveUnavailable` across subsequent snapshots until a distinct fresh turn begins. Saved-history reads remain available. The lifetime ends when the feed forgets the chat or main restarts.

These fields establish ordering and ownership, not a complete mirror. A client without a shared saved/live item identity can show a provisional reply separately, using the existing Chrome panel's text reconciliation, and label unmatched activity explicitly. It must not remove older rows or claim exact deduplication of every tool, reasoning item, or repeated text.

## MoMo's answer chips (`options`)

In a MoMo chat only, an assistant row (a saved row of `history` or `items`, and a live `agentMessage` item in `items`, in a snapshot and in `items.append` / `items.replace`) may carry `options: string[]` (2 to 4 labels): the reply's last line `Options: A | B | C` was read by `shared/momoOptions.mjs`, the same parser the Mac's thread uses, and `text` is sent without that line. A reply with no valid line has no `options` key (never an empty list) and keeps its text as written. A tap on a chip is an ordinary send of the label. The field is additive: an older phone ignores it. Another chat's rows, and every chat while MoMo is off on the Mac, are never read for it. Text streamed as `items.delta` still holds the line until the item completes and replaces it. Saved rows are built in `electron/capabilities/browser/chromePanelLive.cjs` (`recentRowsOf`, `olderRowsOf` with `momo`), live items in `electron/app/phoneMessageItems.cjs`; `electron/app/phoneMomoChat.cjs` says which chats are MoMo's.

## Reading only the end of a chat

The saved rows of a snapshot, the cards a phone is shown, and the page before a row (`chat.read` with `before`) are read from the end of the chat's saved history, as far back as they need, so opening a chat costs the same however long it is (`readPeerRecentTurns`, `electron/session/peerTranscript.cjs`). The Chrome panel's own `read` is unchanged and still reads the whole history.

- Claude Code: the last 1 MB of the transcript is parsed by the SDK through a session store that holds only those lines (`readRecentMessages`, `electron/platform/claudeTranscriptRead.cjs`), with the same hook notices, end-turn marks and edit cutoff put back as in a whole read. If the turns that window yields are too few for what was asked (50 rows, unless a panel read's own limits of 200 blocks or 400,000 characters stop the scan sooner: `recentRowsOf`), the window grows to 4, 16 and 64 MB, and then the whole history is read as before. A chat whose last few turns are huge (tool output, images) can still end in the whole read. A file that fits the window is read whole. The SDK's store option is alpha: if it fails, the whole read answers.
- A window starts inside a turn, so its first turn is left out. The whole read answers instead when an edited message not yet sent again (the cutoff) lies before the window, and when a window that holds a compaction has too few rows (the rows are in what the compaction folded away, which only the whole read puts back). A window that holds a background task's notification without the tool call that launched it is not used while a larger one is cheap (the core would name the task by guess): the next size is read, up to 16 MB, and then the smallest window that had enough rows is taken.
- Item ids of text and reasoning are numbered by their own message (`<message id>:t0`), not by how many the read has seen, so a row id (the `before` of a page) names the same row in a window of any size and in a whole read (`withOwnTextIds`).
- Codex reads pages of turns newest first and stops once enough are in hand. A chat with more than one segment (it switched harness) and ACP chats are read whole.
- A chat with a saved note that has no turn id is read whole, since such a note goes by its index among all the turns (`notesNeedWholeHistory`).
- Known difference from a whole read: the cards of a phone come from the last 3 turns, so a question the agent asked in a message long ago and never answered is not offered there (answering one still reads the whole history). In real transcripts the end read equalled the whole read's turns in 72 of 77 windows; the rest differed in how a background task's notification was worded (its kind, status or title), where the task began before the window.
