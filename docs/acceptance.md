# Acceptance checklist

The acceptance list of the multi-harness design (`design-v2.json` `acceptance`, A1 to A27) written as a checklist someone can walk. Each row is one check and is either:

- **auto**: a named e2e spec or unit test. Run a unit test with `node --test <file>`; the e2e specs run in the release suites.
- **manual**: steps to follow and what you should see. These need a real CLI, a real Mac permission, a second machine or a human eye, so no fake can stand in for them.

A item with both kinds has one row for each kind (A3.1, A3.2, ...). How the tests run: `TESTING.md`. Which journey steps the e2e specs walk and which they skip: `JOURNEY-COVERAGE.md`. Manual rows that need credentials or a signed build are also in `human-needed.md`.

Reference format in the tables: a path in backticks, then optionally `›` and a fragment of the test title in quotes.

Manual rows are walked on a build from the release ring being cleared, on a Mac with a throwaway profile (`MOPILOT_USER_DATA=$(mktemp -d)`), never against your real `~/.codex` or `~/.claude`.
