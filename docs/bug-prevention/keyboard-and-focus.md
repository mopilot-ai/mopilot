# Keyboard and focus

One of the [bug classes](README.md#bug-classes). A pull request adds its note about this class as a file of its own in
`notes/keyboard-and-focus/` (one note per file), not below; the bullets below are the earlier notes.

Popovers that drift from their anchor, keyboard handling scoped to the wrong menu, controls that only respond
to the mouse, focus that escapes a dialog, Enter during IME composition (#290, #452, #481, #482, #483).

## Notes

- An unavailable group must not disable an action that recovers it: explicitly enable descendants such as sign-in when their group carries aria-disabled. After changing accessible roles or separate hit targets, update E2E locators to select the enabled control by role and name rather than covered text or forced clicks. Sweep checked menu options separately from action rows, including options whose accessible names include descriptions. Assert enabled behavior with `toBeEnabled()`; enabled controls can omit `aria-disabled` rather than spelling `false`.
- Composite button names: give a clickable row, file header or tab its own primary accessible name, so nested archive/new/close controls cannot become part of the parent action's name. Keep child action labels and keyboard behavior independent.
- Accessible-name changes: sweep role/name test selectors along with renderer assertions. Query the exact primary action name within its owning control; an exact label can still match both the main row and a Recents action. Standalone New chat journeys share the primary-row locator and verify it against the real sidebar alongside those siblings. Visible shortcut hints are metadata and may be excluded by an explicit accessible label.
- Use `isEnter` from `src/lib/focus.ts` for Enter; give clickable non-buttons a key handler and a role
  (`useKeyWithClickEvents`). Escape needs the same care: an input method's Escape cancels its candidate, so a
  window-level Escape that closes a dialog or stops a turn must check `imeComposing` first (the bug report and
  peer-message dialogs closed and lost the typed text). `tests/imeKeys.test.ts` fails on any Enter or Escape
  comparison without a guard unless its file is listed there with why.
- Prefer a real `<button>`, or an `<a href>` for something that opens (`WebLink` for a web page); an in-app action
  inside a sentence is a `<button className="text-link">`. A row that holds buttons of its own stays a `div` with
  a role, `tabIndex={0}` and `onActivate` from `src/lib/focus.ts`, which runs on Enter or Space pressed on the row
  itself and leaves keys on its buttons to them; a wrapper that only keeps its buttons' clicks off the row is
  `role="presentation"`. Nothing interactive goes inside a `<button>`: a row whose text holds links (a step
  naming a file) lays its toggle button over the row instead (`.step-row-hit`).
- Menus and listboxes follow one WAI-ARIA pattern (`src/components/ui/MenuList.tsx`): focus stays on one owner and
  the active row is named with `aria-activedescendant`. A menu's list (`MenuList`, used by `Menu` and `SubMenu`)
  takes focus when it opens and gives it back when it closes; a list filtered by a search field (`useListbox`)
  leaves focus in the field (role combobox). Rows are `MenuRow` buttons with the role the list requires, never
  focused themselves, so a row's own click handler is all it needs. Arrows move, Home/End jump, Enter (not an
  input method's, `listKey`) or Space picks, ArrowRight opens a submenu and ArrowLeft goes back, Escape closes.
- A safety check that judges clicks must also judge the keys that click: Enter on a focused button or link, and Space on a focused button, press it (`siteRisk.cjs` `pressesKeys`). Raw CDP key events go through one reader (`iabBackend/policy.cjs` `keyPressed`): a `char` event with `\r` is a keypress Enter that submits a form or presses a button (`\n` is a typed new line), and Space presses on `keyDown` with or without text. Sweep every executor (`browser_*`, `browser_script`, the Codex plugin's CDP, Your Chrome) and frames in other origins. A Tab before such a key leaves its target unread, so it asks (#1384, CM-J23, CM-J24).
- An input's Escape that cancels its edit (a rename, a search, a typed address) cancels only that: the app's own Escape (`src/session/appShortcuts.ts`) closes the side pane unless the key was handled, so a pane tab's or a chat's rename cancelled by Escape also hid the pane. Cancel with `cancelOnEscape` from `src/lib/focus.ts`, or call `preventDefault()`/`stopPropagation()` with the cancel; `lint/rules/escape-leak.grit` warns on an `<input>`/`<textarea>` whose `onKeyDown` names Escape without either. A handler that already handles other keys passes the rule, so check its Escape branch by hand (the browser address bar's did). React does not dispatch `onBlur` when Escape unmounts a focused field, so blur-to-commit fields need no cancelled flag.
- A driver that types or clicks through the OS (the benchmark VM's `bench/drivers/gui.mjs`) acts on whatever app is in front, a person's sign-in included (#1561). Keys, keystrokes and clicks go through `toFront`: it checks that the app the driver last activated (`activate`, `focusProcess`) is the frontmost process in the same System Events call that sends the key (`bench/lib/frontGuard.mjs`), and otherwise throws `NotFrontmost` and sends nothing. Callers treat a refusal as a message not sent, never as a turn to retry blindly. Test a guarded AppleScript against a real System Events once: `error (name of p)` passes a reference, not the name.
- A text field switched off while its own work runs loses the keyboard: Chromium moves the focus of an input or textarea that turns `disabled`, or an editor that turns `contentEditable=false`, to `<body>`, and nothing gives it back. The composer did it on every send, so Esc never stopped a running turn and the next message could not be typed (#1658). Make the field read-only with `busyField(busy)` from `src/lib/focus.ts`, or block edits as `ComposerInput` does; `lint/rules/focus-drop.grit` warns on an expression-valued `disabled` on a text field or `contentEditable`. A button that a click focuses and that is then replaced (Send becoming Stop) drops it too: hand the keyboard back to the field. happy-dom keeps the focus in all these cases, so a test of a key after async work installs `focusFixup()` and presses the key with `pressKey` (`tests/support/focus-fixup.ts`), which sends it to whatever has the focus rather than to the element; a benchmark sends keys the same way (bench/README.md, Fairness rules).
- A program edit of the text the user is typing in (a picked @ file, a / command, a skill) places the caret in the same step: insert through the editor's `replaceRange`, or `setCaretAfter(text, position)` so the render that draws the text places it. A caret set on the next frame lets keys typed before it land inside the inserted text (#1719; `[deferred-caret]` in `lint/rules/deferred-caret.grit`). Composer tests of such an edit focus the editor (an unfocused one is redrawn with the caret at the end) and hold frames until after the next key (the DOM shim's frame is a timer that `act()` runs first), as `tests/composerMentionCaret.test.ts` does; `tests/support/composer-setup.ts` installs a browser-like `insertHTML`.
- Numbered navigation and its hold-to-reveal hints share the displayed target collector (`sidebarShortcutTargets`), including pinned duplicates, nested sessions, collapsed groups and manual order. Exercise reveal, actual dispatch, modifier release, lost focus, rebinding and a changed list together; a shortcut-catalog test alone cannot establish that a number opens the row displaying it.
- Hold-to-reveal shortcut hints need a mocked-clock assertion before the hold threshold, at it, and after cancellation: quick modifier taps and ordinary shortcuts must stay quiet in both renderer and native browser input. Repeats and list mutations preserve one hold deadline; release, composition, focus loss, blocking overlays, input-source replacement and disposal retire it, including a callback already queued before cleanup. Keep command dispatch immediate while delaying only the hint metadata.
