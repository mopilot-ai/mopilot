# Wrong scope

One of the [bug classes](README.md#bug-classes). A pull request adds its note about this class as a file of its own in
`notes/wrong-scope/` (one note per file), not below; the bullets below are the earlier notes.

State, a cache or a result is keyed by less than its real identity, or the code reads the global or active
value instead of the chat's own: the active account instead of the chat's account (#152, #167, #263), a window
event every composer handles (#290), a cache keyed without the theme or language (#451, #459), a commit draft
not keyed by repository (#506).

## Search for and ask

- Search for: `.active` and `getState().` reads inside functions that receive a chat id; `CustomEvent`
  dispatches without an owner; `Map`/`Record` caches and what their key includes; a new-chat default
  (`prefs.claudeSelection`, `prefs.model`, `prefs.effort`) read as the fallback for a chat's own setting on each turn,
  where another chat's pick moves it.
- Ask: *is this the chat's own account, folder and harness, and does the cache key include everything the
  value depends on?*

## Notes

- Folder-backed task identity belongs to the directory read, never an `id` field inside its file. All save/delete/migration consumers must use that owner so stale metadata cannot target a sibling or parent folder. Native task-directory IDs use `isTaskFolderId` at import and mutation boundaries; Desktop-only deletion must never delete a MoPilot-owned folder.
- Chat-file ownership: match each record's ID to its canonical filename before publishing it or applying a newer-schema write lock, for both v2 records and legacy segment files. Skip misplaced IDs and diagnose unencodable IDs, preserving the files; neither can replace or freeze a sibling chat. Migration failure counts exclude foreign records, and rollback deletes only records owned by this schema; foreign, newer and unreadable files remain available for recovery.
- Project lookup preserves identifier provenance: a Codex thread projectId uses the native namespace, while Claude/ACP fields and remembered chatProject associations use local ids. Try all primary-namespace matches before legacy fallbacks; list order cannot decide which project owns a chat.
- ACP native session ids are scoped to the agent process instance. Route callbacks through that namespace, release terminals by their owning chat instance, and let late startup cleanup remove only its own binding.
- Notes written into a Codex thread's history (turn/start `additionalContext`) outlive MoPilot: the ChatGPT/Codex app reads the same thread file. A note that names MoPilot's own tools or settings (the `sage_<nonce>` server's `browser_*`, "not available in MoPilot") must say first that it applies only while that server is in the tool list and what to use otherwise (`scopeNote` in codexConfig.cjs), or the model looks for tools that are gone and reports the browser unavailable. Add a new key only after checking its text this way; `tests/persistedContextNotes.test.ts` lists the reviewed keys.
- Browser site grants: query and edit the table belonging to the browser being exercised. Your Chrome and the in-app browser keep separate grants; a journey that changes browsers must grant the new route explicitly and verify the other route's permission is unchanged.
- A canonical chat filename and id do not establish schema ownership. Require a positive safe-integer schema declaration before migration, rollback or live writes; preserve present unreadable/non-record files instead of treating them as absent, and retain read-only handling for valid future versions. Reuse the same version guard in the migration and live store. Protect the canonical filename owner when a body claims another id, and reject filename aliases before using them to lock a sibling.
- A normalized project snapshot is not write admission: preserve unreadable roots and unsupported schema declarations, including fields an older build cannot interpret. Gate every mutation and background import through one guard, persist the local project before creating an optional native copy, and show a rejected removal without dropping its row. Link late native results only against the admitted local id; persist exact deleted-folder tombstones in a versioned schema so imports before or after a native reply cannot resurrect it across restarts. Explicit re-addition clears the folder tombstone; verify the final id still exists.

- Versioned browser JSON is writable only by a supported declared format (or its explicit versionless legacy format). Preserve malformed roots and reject unknown declarations before mutating bookmarks, import ledgers, recovery ownership or session cookies. Admit the entire import before category writes; an explicit bookmark clear may recover unreadable data after its backup is kept, but cannot take ownership of a future format.

- PR prevention metadata belongs to one visible Markdown section. Parse Markdown structure before extracting fields so fenced examples, HTML comments, and fields after another heading cannot establish a bug class or absence of recurrence; ambiguous or missing evidence stays unknown.
- A setting shown once per harness is stored once per harness. "When a limit is reached" read one global pref and each harness's own auto-switch, so changing Codex moved Claude Code's row, and a fresh install showed a choice the offer never acted on. One helper (`limitChoice` in `shared/switch.mjs`) decides both what the row shows and what the offer does.
- A process's limits and authentication errors belong to what it was billed on. A Claude Code process on an API key, MoPilot credits or a cloud account says nothing about the subscription login in use: its `message` events carry `login: false`, and `LoginMarks` and the renderer ignore them for the login's marks, usage and sign-in state. Scope by the process's own billing at start (`s.billing`), never the mode read when its message arrives.
- An account that stands in for another stays in its billing lane: one provider (compared by provider id, never by profile object) and one billing type. When the active account goes (sign-out, removal, the CLI signing out) the fallback is a subscription only (`fallbackFor` in electron/identity/accounts/providers.cjs), else nothing; a chat's signed-out login is stood in for only by a usable login of its lane while auto-switch is on (`claudeLoginFor` in electron/identity/contract/switch.cjs). Pay-per-use is never taken up on its own, and a chat's saved account (`meta.account`) is Claude's, never read for a Codex chat.
- A test loader compiles only its own tree. A coverage run that mixes desktop and web tests imports both `tests/support/register.ts` (rolldown) and `web/tests/setup.ts` (esbuild), and the web loader, registered last, compiled every `.tsx` in the process, desktop ones included. The same desktop function then had two maps with different ranges across a shard's files, and the merged report counted the esbuild copy as a function no test called. `web/tests/setup.ts` now leaves files outside `web/` to the next loader, and `tests/testLoaders.test.ts` runs both loaders together and checks which compiler each tree got.
- A harness's install is named by the binary chats run, not by its kind (#1402). The page header read main's update check per kind with `installSource(via)`, while the Version row used `sourceOfBin` with the binary, the installs found and the path the user set. With a custom location the header said "Native installer" for a binary no longer in use, and never "Custom location". Both now call `sourceOfBin` from the same `HarnessBinary` (each harness part's `useBinary`). The header shows nothing while main's check is of another binary and asks main once for a fresh one, after any check under way. `tests/support/install-source-cases.ts` runs both surfaces over one matrix.
- A guard that measures a whole process acts only on the share its targets caused: the browser memory guard read main's RSS and stopped every browser page when it grew 512 MB in 10 s, so main's own periodic work killed idle pages. Main now reports its own JS memory to the guard's worker, which subtracts it and, past the limit, waits for a newer report (none within a second means a flood starved main) before stopping pages (`electron/capabilities/browser/memoryGuard.cjs`).
- What an agent hears with its next result is the chat's, not the turn's. The browser host cleared every pending change line at a turn's end, so a download that finished after the agent's last call was never reported (#1523). A line saying how a download ended (`isDownloadOutcome`, electron/capabilities/browser/agentDownloads.cjs) is kept for the chat's next result; the rest of an ended turn's changes are dropped.
- A shared pane tab does not make its visibility a window preference. Navigation tests must cover a new chat, a previously closed chat, an active unowned Changes tab, summary visibility and a removed active tab, then return to each owner. Snapshot the actual selected Changes scope; a default for future panes cannot stand in for this chat's current target. Code selection and open comment editors also retire on chat, workspace, file or content changes, even when the text is identical.
- A run's Chrome folder is the run's, not the machine's (#1535). `MOPILOT_CHROME_RELAY_USER_DATA_DIR` pointed the relay at a scratch profile, but the sign-in hand-off (`open -na "Google Chrome" --profile-directory=…`) and `shell.openExternal` still opened the default folder, which in the benchmark VM is the user's real, synced profile. Every page main opens in Chrome or the default browser now goes through `capabilities/browser/userChrome.cjs` (`openInChrome`, `userShell`), which keeps a pinned run on its folder and refuses a bench run without one; CM-E22 fails when a module takes Electron's shell unwrapped or starts Chrome with a profile anywhere else.
- A login's plan usage belongs to the server account it measured, not to the login's id (#1582). The CLI's own login (`default`) can be signed in again as another account, and the renderer kept the old account's figures under `default` (persisted across restarts) while main already named the new account. Main's usage answer now names the account (`account`), a reading of another account replaces rather than merges, and every surface reads a login's figures through `loginUsage`/`usageOfLogin` (`plugin/login-usage` flags a raw `claudeUsage[id]` read). Per-login work is also not gated on the state of the login in use: usage refresh returned early unless the active login was `ready`, so a sign-in on another login was not read until detection ended.
- When several providers serve one surface, test each selected route with the other provider absent or disabled, through the real availability producer and loaded-session consumer. A prospective backend, a listening backend, and current permission to use it are separate facts; preserve load identity without retaining revoked authority or silently substituting another provider.
- A product's bug-report form owns its recipient independently of the chat's harness. Review the destinations of each report action and test the outgoing calls on every harness; a harness's native response-rating capability does not authorize adding its vendor to the product's report form. Removing a report preview also removes its automatic read, while an explicit save-to-file action may still build the report locally.
- What a Changes surface counts is the disk's state in the chat's folder, not the card's or the harness's (#1939). The summary card counted an edit still awaiting approval (an `inProgress` file change), kept a turn whose edits the Edited card had undone (its Undo state lived in the card's own React state), and counted Claude's plan file in app data. Every Changes surface now counts a turn through `changedFiles` (src/lib/turnDiff.ts): applied edits only, inside the chat's folder, and none once `TurnState.undone` is set by Undo; `tests/changedFilesReaders.test.ts` keeps raw `turnDiffFiles` reads to the Edited card, which needs an undone turn's files to Redo them.
- Showing one item is not opening its whole container. Opening a chat from Recents set its project's `expandedProjects` flag, so the project listed every chat until Show less (#280's reveal); the user saw all 19 of a project's chats. Each sidebar list now folds through `chatWindow` (src/components/sidebar/chatWindow.ts), which stretches only as far as the open chat. Ask: *does this reveal write state wider than the one item it means to show?*
- A chat not on screen never changes what the window's side pane shows. An agent tab of a background chat set the window's `diffPanel.open`, a rule left from `<webview>` tabs that attach only in an open pane; with main-owned views the page existed anyway, and the empty pane opened Changes in the chat the user was reading. A page's popup and a Duplicate finished after the user moved on did the same. Agent tabs, popups and copies now open the pane only when the view shows them (`inView`), and `tests/paneOpenInvariants.test.ts` lists every write that opens the pane with why it may. Ask: *when a mode or flag changes its default, which code was written for the old mode's needs?*
- A request to hide one indicator does not remove adjacent status behavior. #2129 hid the sidebar's PR status together with the worktree icon, and its tests asserted both absences. Ask: *which neighboring outcomes must this removal retain?* Test the requested absence alongside the retained behavior through the production container: `tests/sidebarPullRequestUI.test.ts` renders real chat rows, PR badges and hover cards across harnesses, including draft, ready, conflicting and merged PRs, multiple-PR counts and preview actions, while asserting no worktree icon.
- A chat-owned source action or Markdown follow-up routes by that chat's id through `giveBackToComposer`, including when another pane has focus or no composer is mounted. A global Markdown preview without a chat owner may retain the focused-composer shortcut. Test a usable complete edit and preserved input, not just the event or a placeholder prefix; cover the empty entry, cancel/Escape and several additions in a row. A chat-owned permission guide likewise outlives turn-owned activity: release, Stop, helper exit and older read/wait/native-claim cleanup must not clear it. `ComputerPermissions` preserves the current guide while still notifying main about released control; native retries request a complete positive Accessibility and Screen Recording status before clearing the refusal/lifecycle they started under. Local/fallback/cleanup success is not permission evidence and must not initiate that check. Automatic checks share latest-request ownership with Try again and use a non-launching read, including when the helper exits mid-read. Unknown, partial or wrongly typed status retains the guide. Test the full handler through failure, cleanup and late success, including disable/reenable, rather than testing error and cleanup separately or stopping at an inner read helper; stopping or retiring the caller during an awaited attendance lookup must prevent a new native prompt even though an already-running prompt remains shared.
- A check relative to "the previous commit" must ask which commits a merge commit has. The pre-commit file-size check compared the staged merge of main with `HEAD` alone, so a file main had grown past 500 lines blocked the merge commit of a branch that never touched it, while CI (`--base=<main>`) passed the same tree. `scripts/file-size.mjs` now takes every `MERGE_HEAD` parent's size (#2268), renames and allowances (#2270) into the ceiling, as the lint ratchet already scoped a merge to what differs from `MERGE_HEAD`. Ask: *during a merge, does this staged check compare against every parent?*
- A turn's provenance is decided when it starts, but its input keeps arriving (#2249). `activeTurn.human` stayed true after a peer message was steered into the user's turn or a queued message was sent into it with Send now, and a goal round sent to Claude Code or ACP was marked human. So `start_session`, hand-offs and offers acted on words no human wrote. Every gate on the user's word now reads `isUserTurn` (electron/session/userTurn.cjs), which `ChatController.dispatch` clears with `withInput` as other input enters the turn. `tests/userTurnAuthority.test.ts` (an invariant) keeps every `not_user_turn` gate on it. Attendance (`human`/`userEngaged`) is a separate question. Ask: *can anything join this turn after it started, and does the gate still hold for what joined?*
- A prop that says where a view sits is not what the chat is. MoMo's chat passed ThreadView's `inPane` to keep the window's keys to itself, and `inPane` also meant "a side chat": its empty chat said "Side chats are temporary…", its ACP questions were read-only, and its composer showed the coding side's mode, access and model pickers and the + menu's projects, goal and plan (#2279). Chrome that belongs to the coding side now asks what the chat is (`useMomoChat`, src/components/momo/useMomoChat.ts), not where it is drawn. Ask of a flag reused by a new surface: *which of its readers meant something else by it?*
- A rule is only as wide as the calls routed through it (#2283). MoMo's sentinel had a taint/egress rule and a trust gate that audited each action, but only the sources hub called them: the browser and computer-use tools that `toolIsolation.cjs` lets MoMo's chats use ran straight from the registry, so after a file read `browser_navigate` sent the value out in a URL with no ask and no audit entry. Every call of a chat kept apart now runs through the registry's chat gate (`Registry.setChatGate`, `electron/momo/toolTrust.cjs`), which classifies each allowed tool by exact name, and `tests/momoToolScope.test.ts` fails when a tool MoMo may use has no trust class. Ask: *for a check that guards what a caller may do, does every entry point that scope allows pass through it, and does a test start from that entry point rather than the check?*
- When a window-wide surface becomes tab-scoped (#2325), move its drafts and explicit empty choices with its identity, not only its visible chat. An absent binding may inherit an owner; an explicit New chat must not. Check a real panel after reload, and cover tab replacement, unreadable storage and a restore that settles after a new user choice.

- A per-tab panel has one storage writer in the worker: binding choices, unsent composer text, selection text, close and replacement share its queue. A tab replacement updates the live document URL as well as its in-memory id, migrates all three keys and retries failed migration before accepting newer writes. Reads that restore an inherited owner never turn it into a saved explicit choice.
- A lock, slot or build cache that several processes must agree on is scoped to what they share, never to a folder each one owns (#2374). `ensureSageMcp` serialized `swift build` with a lock under `os.tmpdir()`; #2340 then gave every test process its own `TMPDIR`, so each took its own lock and `sageMcp`, `toolChannels` and `admission` built `native/sage-mcp` at once ("unable to attach DB: accessing build database" in the `unit-tests` macOS shard). The lock is now `buildLockPath()` (`native/sage-mcp/.build.lock`, beside the `.build` database it protects), and `tests/crossProcessLockInvariant.test.ts` refuses a lock, slot or cache path under `os.tmpdir()` in `scripts/`, `bench/` and `tests/support/`, apart from the listed machine-wide slot dir. Search for: `os.tmpdir()`, `TMPDIR` and `os.homedir()` in a path named lock, cache, slot or pid; ask: *which processes must agree on this path, and does every one of them see the same folder?*
- Does a per-turn change list read the folder's contents, or what the turn wrote? A checkout, pull or reset during the turn changes the working tree without the turn writing a file, so a snapshot diff shows files nobody edited (#2482, a card of 1608 files after a branch switch); take HEAD and its reflog with each snapshot, and test with a real repository.
- An owner keyed by *more* than its real identity retires work for changes that don't concern it. A dictation capture fingerprinted the chat, every account's status, the login epoch, the model, the harness and the dictation settings, so a background token refresh or a model pick in another window ended a recording with "This voice input belongs to an earlier chat or account" (speech PR1). A dictation now belongs to its window and draft only (`createSpeech.current`, electron/platform/speech.cjs) and its engine and account are resolved when it is transcribed; only work bound to the chat and account (an audio message, a native conversation) keeps the full check (`unchanged`). Ask of every fingerprint used as an owner: *which of these fields, if it changed, would make the result wrong, and which would only make it fail?*
