# Cross-harness gaps

One of the [bug classes](README.md#bug-classes). A pull request adds its note about this class as a file of its own in
`notes/cross-harness-gaps/` (one note per file), not below; the bullets below are the earlier notes.

A feature works for one harness, only while a window is open, or not at all because the new code is never
called: harness-name checks in shared code (#18, #128, #394), logic that lives in a renderer component and stops
without a window (#253, #254), a setting or keybinding some path ignores (#27, #35, #41).

## Search for and ask

- Ask: *does this work for Codex, Claude Code and ACP, with no window open, and what calls it in production?*
- For shared naming defaults, test an upgraded profile carrying the old harness-branded default through both main's background reads and window reads; testing only a fresh profile misses persisted defaults.
- Ask: *for each native event this reads, how does each other family report the same thing, live and read back, including one that only says it in text?*
- Ask: *does a new reader of main's state or a chat's history read the shape its real producer writes on each harness, and do its tests get their records from that producer (drive `ChatController`'s event handlers, as `tests/chromePanelApprovalRecords.test.ts` does) rather than from another layer's copy of them?* Search for a method or kind name the reader keys on and check which module writes it.
- Ask: *does the copy of a shared feature name the chat's own harness, or none, on every harness?* Search for `HARNESS_LABEL[newChatHarness(`, `?? HARNESS_LABEL.`, and a harness name in a shared component's strings.

## Notes

- Unit tests must mock Electron before importing modules that transitively require it, even when testing pure exports. In Node, the real Electron package may download its executable on import; concurrent test workers can race in that installer.
- Follow AGENTS.md "Multi-harness feature development": shared behavior in main-process services, harness
  differences in adapters and capabilities.
- Make sure every new export, parameter and setting has a production caller.
- Lint: `plugin/harness-gate` in shared code; `tests/boundary.test.ts` in components.
- In the renderer, read a trait from `src/harness/family.ts` (`HARNESS_TRAITS`, `chatFamily`, `composerFamily`) or
  pick the family's entry from a `Record<HarnessFamily, …>` of implementations, so a new family is a type error
  until every behavior has an answer (an entry of `null` is an explicit "not on this harness", which the caller
  must tell the user). A harness kind's spelling is read only by `shared/harnessKind.mjs` (`parseKind`), the one
  module `plugin/harness-gate` exempts.
- In main, shared session code (`electron/session`, `electron/app`, `electron/app/ipc`) routes by the chat's current
  segment: the controller's `adapterOf(chatId)`, a trait from `electron/harness/family.cjs` (`traitsOf(kind)`: steers,
  native goal, holds the goal, ...), or a per-family table read with `byFamily(table, kind)`
  (`electron/session/contract/route.cjs`, which throws for a kind this build doesn't know). The capability differences live in
  one declarative table, `FAMILY_CAPS` in `electron/session/caps.cjs`; a basic harness's `null` entry in a table such
  as the switch's `IN_PLACE` is refused with a message, never routed to Codex.
- Text a session is told about its tools comes from the rule that decided it, for that session: a hidden tool is
  refused with `hiddenRefusalText` (`electron/capabilities/contract/toolRefusal.cjs`, re-exported by `visibility.cjs`), never one fixed sentence that names
  surfaces the harness may not serve (`plugin/hidden-refusal`). A remote switch flipped live must leave at most
  one controller per surface on every channel (`CM-X01` checks it at startup and switched live). Tool results
  are text the session is told too: Claude's servers pass every result through `rewriteResult`
  (`electron/capabilities/contract/hostServers.cjs`), so a refusal names the tools as that server presents them
  (CM-D05, CM-D06).
- An action offered to the user (a button, a ways-forward choice) must complete for every controller of its surface: Your Chrome, Claude in Chrome, the Codex Browser plugin, MoPilot's extension and relay. Decide what it does from one shared rule (the sign-in hand-off reads `shared/chromeHandoff.mjs` in main and the pane), and when no controller can finish it, show why and the way that works instead of a button whose only result is an error (CM-B21 to CM-B26).
- A control a harness family renders for itself must still offer every choice the shared feature has: the basic-harness picker in a chat listed only the harness's own options, so a chat on OpenCode or another ACP harness could not move to another harness. Moving a chat between harnesses that can't hand over in place starts a new chat with a handoff record (`newChatWithSummary` in the renderer, `SwitchRunner.summaryNote` in main, which reads a basic chat's transcript); test the picker in a chat on every family.
- A chat's harness is a family of three (`chatFamily`, `composerFamily`, `currentFamily`, `nativeFamily`), never a
  first-tier id with a basic harness folded into Codex: that fold showed Codex's account, model and limits in a basic
  chat's Status, sent its /logout to the Codex account row and read Codex's caps, plugins and usage limits for it. Code
  that needs Codex's or Claude's account, selection or caps narrows with `firstTierOf` or `composerFirstTier` (null on a
  basic harness) and says what a basic chat does instead; a capability read for a new chat passes `newChatKind`.
  `plugin/family-collapse` flags reads that fold it (`chatHarness`, `composerHarness`, `currentHarness`, an unguarded
  `ownerOf(id) === 'codex'`, `kind === 'claude' ? 'claude' : 'codex'`).
- An account policy ("Stop": auto-switch off) holds on every automatic path, not only the one that reads it first. Claude's policy returns `none` from one place; Codex's pool had four entry points (relay routing, token refresh, a limited turn, a usage reading) and two of them moved the app anyway. `tests/accountsStopPolicy.test.ts` lists every method that changes the active account and runs each automatic one with "Stop"; a new writer fails it until it is reviewed.
- A recovery offered when a harness fails (a usage limit's "Continue on …") needs a way forward for every family, picked from a `Record<HarnessFamily, …>` (`LIMIT_WAY_FORWARD` in `src/store/chats.ts`). A harness that reports the failure only in words is classified by one shared reader (`isLimitError` in `shared/acpStop.mjs`), on every path its failure arrives by (a turn that ends, a session that won't open).
- A recovery offered for one family's failure is offered for every family that can fail the same way: a failed turn's Sign in / Re-check is a `Record<HarnessFamily, …>` (`authRecovery`, src/session/chatActions.ts), and a basic harness reads its sign-in words from the same helper main uses (shared/acpAuth.mjs). A route that sends one family's work to another (a temporary chat picked on a basic harness) checks that the other can run, at the shortcut and again at send (`temporaryChatBlocked`).
- A policy the user set in one harness's settings and that the design applies everywhere (Codex Browser Use blocks, #1319 G13) is read by one shared helper that is never told the chat: OriginGrants' `external` hook takes only the URL, so it can't be gated on the chat's harness or thread again. A policy only a running harness reports is kept from its last report (on disk, its relevant fields only), so a session on another harness, or a restart, still has it (CM-P29, CM-P30). A renderer reader of tool items recognizes every harness's naming of MoPilot's tools, Claude Code's short names on `mopilot_browser` and `mopilot_computer` included (`ownBrowserTool`, `ownDesktopTool` in `src/lib/agentNarration.ts`): the ways-forward strip missed every browser refusal in Claude Code chats until the G13 dev-app check (CM-P31).
- A tool that names a tab reaches every browser host a chat's controller can be on, or says which one it can't. `browser_save_screenshot` resolved only the in-app browser's tabs, so a native Codex thread whose Browser plugin drives MoPilot's Chrome backend had no file of a Chrome page to give `setFiles` (#1539). A tab id the pane doesn't have now goes to the chat's Chrome group (`chromeScreenshots.cjs`), and a tab on a vendor's controller is refused with what to do instead. When a tool takes a tab id, sweep every host (pane, Chrome relay, the plugin's backends) and the vendor routes.
- A shared item (a context compaction, a status note) has to be produced by every family, including one whose protocol has no event for it and reports it only as text. #1502 fixed how a Codex compaction turn reads, but Claude Code's summary read back stayed a user message (#1501) and opencode's summary, which ACP streams as an agent message, stayed a reply (#1575). A family's compaction goes through `shared/compaction.mjs` (`compactionItem`, and `isCompactionSummary` for a summary that only arrives as text); CM-K40 runs every family's live and read-back path. When a feature reads one family's native event, ask how each other family reports the same thing, and which of them only says it in words.
- A step only the user may take in a browser (a bot check or CAPTCHA, a password) that the models are told about only in a tool description holds for the models that happen to read it that way: Claude Code handed the edge suite's "I'm not a robot" page over and a Codex model ticked it (#1615). Enforce it where every route's action passes (`hostTools.cjs` actionGate, the iab backend's gateWrite, Your Chrome's `chromeActionCheck`, the older `sage_browser_*` `onPage`), with one shared test and refusal (`browser/botCheck.cjs`) and the hand-off named per route, re-check after any card the user answers, and add the rule to the shared surface note so every harness hears it the same way. Ask: *is a rule that says "the user must do this" enforced on every route, or only described?*
- A decision that moves a capability's default route for every harness (MoPilot's own Chrome channel, #1483 / #1319 G28) moves every surface that sets up or offers a route with it: notes, Settings status rows and their actions, onboarding and hand-offs. #1631: the Claude in Chrome note and the status rows still offered Your Chrome, whose switch hides the `chrome_*` tools, so one click left Claude, and Codex after a switch, with no Chrome. Such surfaces read the served route from one shared answer (`servedChrome`, the status's `chromeTools`), and every switch to a route that replaces another is listed in `tests/controlMatrixChromeRoute.test.ts` with its reason.
- A view of what a harness produced takes its scope from what that harness covered, not from another family's default: Claude Code's own `/code-review` reads the branch's diff, so walking its findings in Uncommitted showed none, and a scope that held them at review time can lose them once the fixes are committed. Ask: *for every family and for the state after the user's next commit, does the scope this view opens hold what it shows?* (ReviewCard `walkScope`, `widenFindingsWalk`).
- A tool session's segment id and the owner checks that compare it took the id's form separately: Claude Code's session named the bare session id, the checks compared 'claude:<id>', and their tests fed the checks the prefixed form, so update_task_list, wrap_up and every linked-session, peer, scheduled-task, plugin-skill and PR-monitor tool refused Claude Code chats with no_owner. One helper (electron/platform/segmentOwner.cjs) now makes and checks the key, `plugin/segment-owner` flags hand-made checks, and change-contract I5 asks for the producer's real output in the checker's test.
- Shared copy named one harness where any could be the subject: the Code Review page interpolated the default harness's label ("Review with Claude Code", #1645), the transcript and `harnessLabelOf` fell back to "Codex", a Fast hint fell back to "Use your Claude subscription", an approval card fell back to "Codex is requesting…", the app's Help menu linked only Codex's docs, and plugin IPC refused "a plugin Claude Code or Codex installed" on any harness (#1864). `plugin/harness-fallback` flags the default harness's label and a one-harness fallback; `tests/harnessNamedCopy.test.ts` lists every shared file (components, harness services, store, lib, and main's app, IPC, sessions, capabilities, plugins and platform) whose strings name a harness, with why the harness is the subject there, so a new one is reviewed. Name the chat's own harness (`chatHarnessLabel`, `useSourceLabel`, `harnessLabelOf`) or none; per-harness lists (the Help menus' `shared/harnessDocs.mjs`) name every first-tier harness.
- A tool family exposed to every harness must also reach the renderer's shared classifier (#1639). `chrome_*` and Claude's short `mopilot_chrome` names normalize together in `agentNarration.callName`, before a short `browser_batch` can be mistaken for the in-app browser. `controlMatrixChromeNarration.test.ts` enumerates the production `CHROME_TOOL_NAMES` through each naming wrapper and checks narration, source and handoff retirement; example-only vendor tests did not catch the missing own-Chrome family. A new channel's tool-shaped names do not make its result format, handoff signals or permission targets those of another channel.
- A shared feature handed to one adapter as a constructor option reaches only that family. #316 counted a script's edits in a turn's changes by giving the Codex adapter Git snapshots (`CodexAdapter({ turnChanges })`), and Claude Code and ACP turns kept listing only their edit tools' files, so "Current turn" and "Branch changes" disagreed. Main now builds one TurnChanges, which the Codex adapter and `electron/session/turnSnapshots.cjs` share (the controller begins it for a Claude Code or ACP prompt and ends it in `onFinished`), and `tests/controlMatrixTurnChanges.test.ts` starts a turn of every family in `MAIN_TRAITS` on it. Ask: *is an option one adapter takes a feature every family needs, and does one owner serve them all?*
- A conversational question can arrive as a native tool request or as an async message. Route both through the same choice component and answered summary; otherwise option selection, custom text, keyboard ownership and the post-submit view drift even when delivery succeeds. Review the empty/default state, selection, submission, failure/retry and reloaded answer on both paths; keep protocol-specific serialization and typed ACP forms at their adapters.
- A lookup that reads only what this process heard from a harness has nothing for a chat untouched since MoPilot restarted. `CodexAdapter.cwdOf` knew a thread's folder only from `thread/started` or a resume in the current run, so a Codex chat that had not run a turn since the restart had no folder for the PR monitor, peers, scheduled tasks, dev previews or the missing-folder guard, while Claude Code and ACP fell back to their transcripts. Each family's folder reader now falls back to what its harness saved without loading the session (`CodexAdapter.folderOf` asks for metadata-only `thread/read`, which takes no writer lock), and `tests/support/electron-wiring/peer-services.ts` checks that main wires every family through that reader. Ask: *after a restart, before the chat runs a turn, does this read still answer on every harness?*
- A window that opens or reloads while main runs a Claude Code turn rebuilt the chat from its transcript, where a 30-second timestamp guess meant for other apps' sessions closed the last turn: the turn read "Worked for 1s" with no Stop while an approval card still waited, and a queued message never sent (#1838). Main's `SessionState.turn` owns whether the chat's turn runs; both ways a Claude chat opens (its latest page and a switched chat's segments) ask it through `mainRunsTurn`, keep that turn open (`reopenedTurn`), under the live id main's translator gave it. Codex and ACP read turn status from their own servers and were not affected. Ask of a window's first read: *does it take a running state from the process that owns it?*
- #1872: one rule said why a basic harness couldn't be the default (signed out, not installed, turned off) but only "can't run right now" for Codex and Claude Code, so a first run with Codex signed out opened on a red "Codex can't run right now". When a reason table covers one tier, check every tier feeds it, and test the note per harness and state.
- A chat that switched harness is several native sessions; an action that takes "the chat's session" takes only the last one. Fork forked the current segment alone, so the fork lost every turn from before the switch and took its title from that segment (#1941). `forkSwitchedChat` (src/session/harness/forkSwitched.ts) forks each segment's session once and gives the new chat the same segments over the copies; the user approved this meaning (the whole conversation, continuing on the current harness). Ask of a chat action: *what does it do to a chat whose segments span harnesses?*
- Stop meant three things: Claude Code's interrupt killed the running command, while Codex's `turn/interrupt` ended the turn and left its unified-exec command running as a background terminal, listed as "1 running task" and a Background terminals card while the turn still waited on it (#1940). `interruptTurn` in electron/harness/codexConnection.cjs now ends the stopped turn's own running commands on every Codex stop path (the one `request()` choke point, checked by `tests/codexStopChokePoint.test.ts`), their rows read "Interrupted" as on Claude Code and ACP, and a command becomes a background task only once its turn ends. Ask of a stop or cancel: *what does each harness's native call leave running, and does the user see the same outcome?*
- An agent tool that offered a harness let the agent move work there on its own: a Claude Code coordinator started a linked session on Codex that the user never asked for (#2084), and `create_scheduled_task` took any harness, model and effort the same way. Claude Desktop's start_session has no harness at all, takes a model only "same family or cheaper than yours; anything higher is ignored", and runs elsewhere "only when the user names the place". A harness an agent passes now stands only when it is the chat's own or the user's words this turn pick it as where the work runs ("use Codex", "in a Claude Code session"; a mere mention such as "the Codex adapter" is not a pick), and a model or effort only when it is the chat's Claude family or cheaper, a cheap effort, or named by the user (`electron/session/userWords.cjs`, recorded on the controller's dispatch hook for every harness); anything else is set aside and the result says so. `tests/agentChoiceOwner.test.ts` fails any tool schema with such a choice that doesn't go through `userChoice`. Ask: *who makes this choice, the user or the agent?*
- A card the renderer can draw is reached only if the thread routes its item to the drawing component. Session cards (`TaskProposalCard`) were dispatched in `BlockItem` but `isBlockItem` never admitted them, so `buildBlocks` folded every `start_session` call into a step group ("Called sage_… start_session") on every harness; the only test rendered `BlockItem` directly. Routing and drawing now read one answer (`toolCard` in `items/stepModel.ts`), and a card's test renders the whole thread view (`tests/threadSessionCalls.test.ts`), not the component alone.
- Chrome's side panel keyed its cards on the window's translated approval methods (`claude/toolApproval`) while main hands it the requests as stored (`claude/permission`), so every Claude Code approval read "Answer in MoPilot" and its answer would have sent the CLI an empty tool input (#2114); its tests fed it the window's shape. It also replaced the streamed reply on every read, which held only on Codex, whose thread read has the reply being written; Claude Code's transcript has none until the turn ends, so the reply vanished while it ran (#2116). Both now read a shared contract: `shared/approvalRequest.mjs` builds the window's and the panel's cards from main's record, and the panel keeps streamed text until a read's rows hold it (`electron/chrome-extension/src/panelPreview.mjs`).
- MoMo's chats (#2139) were kept apart on Claude Code and Codex by each harness's own switches, but on ACP only by refusing the client's `fs/*` and `terminal/*` requests: opencode runs its shell, read, search and web tools inside its own process, so they ran in MoMo's chat, read files MoMo's Files source had Blocked, and its ~/.config/opencode/AGENTS.md loaded (#2278). The isolation assumed every ACP agent does its work through the client. Now an ACP chat kept apart runs on a process of its own that its harness's `isolation` quirk confines (opencode: every tool but MoPilot's denied and hidden, its own config folder with only the user's providers and models carried over, project and Claude Code instructions off, the session pinned to MoMo's agent, and no start while ~/.opencode holds settings of its own), told it has no files or terminal, with every native permission request refused without a card; a harness without that quirk is refused as MoMo's brain by the menus, MoMo's service and the ACP host. Each MoMo chat holds its confined process alone: opencode registers MCP servers per folder, so every session in a folder could call every other's `sage_` server and act as that chat (#2302). `tests/momoHarnessConfinement.test.ts` makes every family and every ACP quirks file say which, and checks that no two MoMo chats share an ACP process. Ask of a boundary on what a chat may do: *where does each harness run the thing being limited, and is it refused there?*
- A tool's name reaches the window in each harness's own form: Codex names the server beside the tool, Claude Code writes `mcp__<server>__<tool>`, and opencode joins them with `_` (`sage_3f880302123f_momo_memory_search`). Only the first two were read, so on opencode every MoPilot tool step said "Called sage_<nonce>_<tool>", the browser and desktop tools lost their narration, and MoMo's memory searches went to usage data with their query (#2280). `nameOf` (src/lib/scheduledTaskCall.ts) and `controlTool` read the joined form, every own tool reads as a line from one table (src/lib/ownToolLines.ts), and `tests/ownToolLines.test.ts` (an invariant) registers every MoPilot tool module and fails a tool with no line. Ask of a new tool, or of a reader of tool names: *what does each harness call it, and what does its step say?*
- Sharing the question card was not enough: Claude Code's AskUserQuestion and Codex's `request_user_input` waited in the composer's place, while a Codex async question (an `agentMessage` with `questions`) was drawn in the turn where it was asked, so the work that followed pushed it up out of view before it was answered. A waiting question has one place on every path: `dockedAsyncQuestions` (src/lib/asyncQuestions.ts) docks the latest turn's unanswered questions in the composer's place (`DockedQuestions`), as approvals are, and the transcript draws them only once answered or written past. When a feature has several delivery paths, compare where each one waits, not only which component draws it.
- A confinement applied to a chat's own session left the helper runs written beside it open: a MoMo chat's harness-switch handoff note was written by a Claude Code run that still read CLAUDE.md (#2364), its Codex fork ran with memory on because no chat named the fork thread, and a title ran on a hidden session that read the folder's instructions. Every model run started for a chat (a note, a title) takes the chat's rule from the chat id; `tests/momoHelperConfinement.test.ts` lists each place that starts one.
