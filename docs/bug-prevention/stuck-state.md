# Stuck state

One of the [bug classes](README.md#bug-classes). A pull request adds its note about this class as a file of its own in
`notes/stuck-state/` (one note per file), not below; the bullets below are the earlier notes.

A state is set by one event and cleared only by another that may never come: a missed `mouseleave`, a turn
that never ends, a `requestAnimationFrame` that never runs, a request that never answers (#277, #289, #325,
#335, #340, #353; unbounded waits #176, #208).

## Search for and ask

- Ask: *what clears this if the clearing event never arrives?*

## Notes

- A blocked or failed peer delivery belongs to its durable journal, not the ordinary input retry queue. Check early kill-switch refusals as well as native dispatch failures, and preserve unrelated user input while leaving peer resume explicit.
- Harness teardown: approvals can outlive the root turn (background agents), so an idle phase alone does not prove there is no pending work. Parent-turn completion retains identified sub-agent requests and their approval notification until the request resolves or is cancelled; interruption and owning-process exit still clear them. Track native-source ownership privately: old-source exits remove only their cards and settle only their tasks; stale messages and controls cannot finish or mutate a replacement turn, including a same-family session switch. Retract notifications only after the last card goes, while retaining queued input; keep truly idle chats unchanged.
- Give every "pending", "loading", "open" or "busy" state an exit on failure, timeout, blur, chat switch and
  unmount. Give every wait on another process a timeout.
- A long transfer is bounded by a stall timeout (no bytes for a while), never a fixed total: the macOS updater's 20-minute limit on Squirrel's download failed a 145 MB update arriving at 60 KB/s that was still moving, and Squirrel reported no progress to tell slow from stuck. Download it yourself to see progress, resume with Range after a stall, and keep a fixed limit only for local steps (electron/updates/download.cjs).
- A "not installed" status is a snapshot of something outside the app: give it a way back without a restart (Re-check on the row, and a re-read when the window regains focus or a view that offers it opens), and never hide Re-check because the last look found nothing (basic harnesses installed while MoPilot ran stayed "Not installed").
- A "lapsed" or "limited" mark on an account needs the exit that matches its cause: a Claude Code login marked signed out by an authentication error stayed out after the user signed it in again, so a later limit on another login stopped with "limit reached". `LoginMarks` (electron/identity/contract/loginMarks.cjs) owns those marks: an answer from the login (a rate-limit event), a verified Re-check and a status that reads signed in again each clear the lapse. Codex's `refresh()` clears its `expired` status the same way.
- A cached sign-in state of a harness that signs in on its own (a basic ACP harness) is a snapshot too: a chat's failure that asks for a sign-in marks it signed out (`Admission.signedOut`), a signed-out one is checked again on window focus with a back-off and before unattended work, and one only a prompt can see (the probe only opens a session) is cleared by a prompt that goes through or Re-check, never by a probe that cannot tell (electron/harness/admission.cjs).
- Open the trusted window before awaiting slow startup services, but delay full renderer imports until main's IPC, flags and harness setup are ready. One process-owned readiness result must settle on success, failure, timeout or termination; late setup completions must not start later services after that startup is retired.
- A state whose only setter is one DOM event is stuck the same way a state with no clearing event is: the selection
  toolbar read `window.getSelection()` once per `selectionchange`, in a `requestAnimationFrame`, so a read that
  landed while the transcript was still settling left the bar hidden for a selection the reader still had, and
  nothing read again until they scrolled, resized the window or selected something else. It also never read on
  mount, so a remount with text already selected showed no bar at all. Ask of derived DOM state: *what reads this
  again when the thing it was read from moves?* State read out of a container's layout is watched with
  `watchTranscript` (#1245).
- A latest-wins guard that drops a result because its owner changed must make sure the new owner gets its own run. The renderer's startup Claude detection read the default login, the account list then named another login in use, and the dropped result left that login on "Checking…" forever: every write of the account list goes through the one writer (`setAccounts`), which detects again when the login in use changes (`tests/claudeStartupDetect.test.ts`).
- A no-progress check that counts events misses a loop that keeps sending them. #1543's no-response state reset on every item, so an opencode turn that compacted after every step (36 times) never showed it (#1575). `compactionLoop` in `src/lib/turnStall.ts` reads the turn's items for compactions with no work between them and shows the same banner with Stop / Retry; a turn that ended in one keeps a note. When a turn can repeat one step forever, ask what shows that it is getting further, not only that something arrived.
- A window's first read that main refuses, then nothing reads again until the next change. Main answers the linked sessions, peer messages and PR monitor only for a window that sent `session:ready`, which boot sends after several awaits while React has already rendered; the refused first read was swallowed or shown as an error, and a window opened after the work finished (every window closed, a restart) never got a change to repair it (found by `tests/e2e/cuj-orchestrator-chat.spec.ts`). Such reads wait for `windowReady()` (`src/lib/windowReady.ts`). Ask of a read made on mount: *does main answer it before the window is ready, and what reads again if it fails?*
- A CI pending status needs an owning run, a bounded execution deadline and recovery for cancellation or a missing report. Test every automatic entrypoint with a silent/replaced owner, a failure before any child status and a newer main: terminal checkpoints must neither fill status history nor resume forever ahead of newer work. Paired suite inputs and execution deadlines are enforced by `tests/mainValidationWorkflow.test.ts`.
- A scroll input does not guarantee a scroll event: a downward wheel or key at the bottom, a horizontal wheel, zoom, a tap and nested scrolling can leave the transcript unmoved. Keep follow intent separate from bottom distance (`ScrollFollowing`), test nonmoving input through the real decision helper, and observe viewport as well as content size. A jump with no distance cannot wait for `scrollend`; queued resize and initial-position frames must yield to navigation, history and actual upward input, including gentle movement inside the bottom tolerance.
- A tool call never waits on the user's click. `browser_request_signin` held its call open until the pane's button, and Claude Code moves a blocking MCP call to the background when the user writes: "Done" then answered a call nobody waited on and the turn never ended (#1834). A hand-off returns at once and ends the agent's turn; the user's reply, or a button that sends a message through the chat's current adapter, starts the next one (electron/capabilities/browser/userTurn.cjs). Only approval cards wait inside a call, and the card sweep at turn end and Stop release them. Ask of a new wait in a tool: *what if the harness moves this call to the background?*
- An approval card asked inside a tool call takes the call's abort signal. The registry stops waiting for an aborted call (a per-call cancel, Stop), but `ApprovalBroker.ask` took no signal: the card stayed up until the turn-end sweep, and a late click still applied, so a site card stored a chat or always grant for a call nobody waited on (#1865). `ask(chatId, kind, params, { signal })` withdraws the card from every window when the signal aborts and puts none up for a call already aborted; the site checks read `ctx.signal`, and a card several calls share (`SharedCard`, electron/capabilities/sharedCard.cjs) goes only when the last of them aborts, storing neither a grant nor a refusal. The native Codex in-app browser backend, which is not under the registry, gives its requests a signal its Stop aborts. `plugin/unsignalled-wait` flags a `broker.ask` with no options and a `grants.require`/`grants.act` given a context with no signal; a card that is not a tool call's (a page the user drives, a paused chat's deferred card) has its own exit and stays in the baseline. Ask of a card in a tool: *what takes it down if the call is aborted and the turn goes on?*
- A card that goes away unanswered is not the user's no. A Codex chat's site card for a chat not open in the window was still up when the turn ended; the turn-end sweep resolved it null, and `OriginGrants.require` stored every non-allow answer as a refusal, so the site was denied for the rest of the chat and the next turn's call failed at once with `site_permission_denied` (retryable=false) without asking. Only an explicit Deny is remembered now; an unanswered card throws `unanswered` and records nothing, so the next call asks again (`tests/siteCardUnanswered.test.ts`). Ask of every stored answer: *which value means "nobody answered", and does it store anything?*
- An error shown in place of something is cleared by whatever makes it untrue, and a Retry next to it can fix its cause. A Codex chat opened while Codex's app-server was down showed "Codex isn't connected" with Retry; Retry only read the chat again, which failed at once while Codex stayed down, and Codex coming back reloaded the chat without taking the error away, so the chat kept saying it after the user restarted Codex and signed in again. A chat read's failure goes through `readFailed` and its success spreads `readSucceeded` (src/store/chatReads.ts, `plugin/read-error`), and the chat's Retry restarts a harness that is down before it reads (`BEFORE_REREAD` in src/store/threads.ts). Ask of every error with Retry: *what clears it when its cause goes away, and can Retry reach the cause?*
- A "ready" state is a snapshot of an external feed too: the app updater stopped checking once an update was downloaded, so a release that published several versions in a row installed each one after another (restart into the first, then find the next). A check keeps running while ready (`Updater.refresh`, electron/updates/updater.cjs) and replaces the waiting update only with a strictly newer one, without flashing a busy state, so a stale CDN copy cannot ping-pong it; ask of every busy-state early return in a poller: *which of these states is really final?*

- A parent turn ending does not end its background work. For progress markers derived from that turn, test completion with linked sessions and background tasks still running, tasks waiting for approval, and their eventual settlement. Use the shared task classification and verify actual animation movement in the app, as well as rendered active/still states.
- A wait on an OS prompt needs a word, a way out and an end. Dictate on this Mac's engine handed the first clip to the helper, whose recognition asks macOS for Speech Recognition and waits for the answer: the button spun on "Transcribing…" for minutes with no word, no cancel and only the helper's own timeout as an end (#2286). The window now asks first and says so (`speechGate`/`askSpeech`, src/lib/localSpeech.ts: "Allow Speech Recognition to dictate"), a second press gives the clip up, a refusal ends on one line, and the prompt and every engine's transcription have a timeout; main's local path ends a clip at once while the prompt is up (Chrome's side panel). Ask of every await on something outside the app: *what does the user see while it waits, how do they stop it, and what ends it if it never answers?*
- A reset that deletes a store's files under a service that keeps running leaves that service holding what is gone. Reset MoMo deleted the audit log's folder while the log still took it as made, so every source read failed until a restart (#2307); the sources hub kept its cached state, and the chats store stopped at the first chat its harness no longer had, so every retry failed the same way (#2291). Each store's reset goes through the store's own erase or reset (`AuditLog.erase`, `SourcesHub.reset`, `resetMomoChats`), which forgets what it cached and lets the next write start again, and `tests/momoResetRecovery.test.ts` writes to every registered store after a Reset. Ask of every reset or delete-all: *does the next write in this same process work, and can one item that fails stop the rest?*
- A record's own "running" is not the chat's. A Claude chat showed two running lines with two clocks (#2332): a turn read back from a transcript tail written seconds before stayed `inProgress` once this window started the next turn, and every `TurnView` drew its live line from its own `turn.status`. A chat runs one turn: only the turn `liveTurnId` picks draws live (src/lib/liveTurn.ts), every turn start settles the others (`settleOtherTurns`, src/store/pendingTurns.ts), and a chat opened right after its own turn ended reads that tail closed (src/session/harness/claude/history.ts). Ask of every live element drawn per record: *what if two records say they run, and which one owns the one-per-chat line?*
- A failure that keeps the user's input must not keep the shared resource too. A failed dictation clip kept the app-wide microphone capture until Retry or Discard, so every other composer got "Voice input is already active in another composer" (speech PR1). The clip now stays in the composer and the capture is released at once; Retry takes a new capture. Ask of every retained failure: *what does it still hold that someone else needs?*
