# Stale async results

One of the [bug classes](README.md#bug-classes). A pull request adds its note about this class as a file of its own in
`notes/stale-async-results/` (one note per file), not below; the bullets below are the earlier notes.

An `await`, `.then` or callback applies its result after the context it was started for has changed: the user
switched chat, turn, draft or repository, a newer request superseded it, the component unmounted, or the
process or terminal was replaced. This is the largest class (about 50 fixes, e.g. #283, #324, #474, #478, #500,
#507, #510, #535, #543, #544).

## Search for and ask

- Search for: `await` followed by `setState`/`set(`/`toast`/store writes in the same function; `.then(set`;
  `on('exit'` and `on('close'` handlers; `getState().route` or `.active` read after an `await`.
- Ask: *after each `await`, what proves the chat, draft, turn or repository is still the one this started for? What does an event
  that arrives during the `await` resolve to?*

## Notes

- Browser import failures recheck job ownership too: a rejected key, cookie, password, bookmark or history read after cancellation, expiry or replacement reports cancellation and cannot continue another read or publish the retired job. Keep replacement jobs and key cleanup intact.
- Goal restart acknowledgments belong to the restart that requested them: old clear replies, round feedback and turn results must not erase its fresh limit while it awaits Goal set. Retire ownership on acknowledgment, command/goal replacement, failure, missing-acknowledgment completion or crash; retain retired ownership for already-sent acknowledgments so Pause/Clear cannot be undone by a late Goal set. Queued commands carry their owner token and are admitted before switching, steering or dispatching to any harness; discarded internal commands cannot requeue or block later human input. Ordinary human clear replies still apply.
- Snapshot recovery: coalescing a patch-gap refresh must retain the newest required revision. A gap received while a snapshot is in flight may require a follow-up; the earlier snapshot cannot count as recovery unless the current copy has reached that revision. Follow up only for a newer gap observed during a request, so a stale or missing answer alone cannot spin retries. Capability single-flight keys include session revision and change generation, and answers publish only while both are current. Cached capability answers carry the same revision/generation; readers offer them only while those stamps match, so a failed refresh cannot keep old capabilities marked loaded.
- Optimistic session writes: a rejected reply does not confirm whether main applied the write. Recover from main's snapshot taken after the reply, including on failure (an earlier in-flight read cannot settle it), and retain newer pushed revisions; if the recovery read also fails, a subsequent refresh or patch gap must remain able to retry.
- External-writer reconciliation: only the latest check for the selected native source of a followed chat may publish or schedule its silence timer. Old-source reads/unwatch events cannot affect its replacement. Initial watch callbacks run only after successful registration and while that watcher is still live; retired watcher callbacks cannot start new reads or timers. Unfollowing invalidates pending reads, and a writer that goes silent during a read stays idle. Native ownership must be rechecked after reading turns, so MoPilot taking over cannot be reported as activity in another app.
- Delayed goal work: capture the goal snapshot, native session key and last started turn before scheduling completion or login continuation. Recheck that context after each transcript read and flush wait, and before queued continuation or the next pause/clear plan step. A clear writes its final state only while the captured goal remains current; commands a plan itself starts do not invalidate its remaining steps. Keep only the latest action of each kind, so an old result cannot stop a replacement goal, revive a cleared one or cross a session switch. Renderer goal loads likewise match the captured goal and selected native/harness, and publish only the latest read for that chat.
- Agent transcript loads: live steps and drops retire both success and failure from stored reads. Keep each read's identity through cleanup so an old completion cannot clear its replacement. Return stored metadata with the items and commit both under the same guard; adapters must not publish late model names separately.
- Quick Chat requests: after awaiting the main window's renderer readiness, recheck that the sending window still owns Quick Chat and that a chat-specific request still owns its target. A replaced or closed floating window must not send, navigate, or hide its replacement. Use one sender predicate in navigation and send IPC.
- Task polling: native source identity owns in-flight terminal/agent reads, cached task rows, stop indicators and stop/output actions. A switch can keep the chat id, task id and harness family: let the new source poll immediately, reset its baseline, and prevent old replies or cleanup from publishing into it. Subscribe polling effects to segment changes even when their wanted state stays true. Historical and nested agents keep their spawning segment owner; continue polling historical Codex/ACP agent work even while Claude owns the current turn. Main-backed jobs can intentionally outlive their segment: retain their native owner through snapshots and UI projections, and route stop/output actions by that owner rather than the replacement chat harness.
- Live output polling: both successful replies and failures belong to the exact live task watch, not just its native task id. A retired request cannot publish output or disable polling for later tasks. Disabling a process-wide polling capability retires all its watches, including in-flight sibling requests.
- Tool-session owners: a harness switch starts the native session (a Codex thread) before it records the chat's
  new segment, so a chat looked up when the session opens is still the native id. A tool session stores a
  resolver (`chatId: () => chatOf(id)`) that each call evaluates; `plugin/captured-owner` flags a looked-up chat
  passed to `open`, `assign` or `rotate` (docs/control-plane/design.md, ControlContext).
- Native session identity: a native session started for an existing chat (a harness switch) is claimed for the
  chat (`ChatController.claim`) before it can send anything, not when the segment is committed after the start's
  `await`; a Codex start claims in the answer's hook (`request(..., { onAnswer })`), which runs before the next
  message is handled. Drop the claim when the start or the switch fails. Events that name a native session
  carry the chat main resolved, so the renderer does not look it up in segments it has not received yet.
- In-flight tool actions: a computer-use or browser-use handler keeps running after Stop, Esc or its turn's end
  (the Registry answers the harness at once). Every side effect it has after an `await` must still be allowed:
  the call runs inside a guard of its abort signal and its chat's control epoch (`electron/capabilities/contract/actionGuard.cjs`);
  the helper client and Your Chrome refuse a stopped call's requests, and a lock is taken only after `checkAct()`
  (CM-R13 checks every lock taker). Requests that give the Mac back (`GIVES_BACK`) run anyway. Let go of a lock
  only after the epoch moved, and give back what a request did once its turn already let go (hidden apps).
- Positional ids: an accessibility element id is a child-index path ("0.3.1"), so after the UI changes the same
  id names another control. A request that names an element sends what the snapshot showed of it
  (`expectElement` from `identityOf` in `electron/capabilities/contract/desktopPolicy.cjs`) and the helper refuses a
  mismatch (`element_changed`); a refusal is never turned into a click at the old center, and a batch reads an
  element again after a step that may have changed the UI (CM-D01 to CM-D04).
- Capture the identity you started for (chat id, turn id, draft id, request generation, process object) and
  compare it before every write after an `await`: `const gen = ++this.gen; await x; if (gen !== this.gen)
  return;`, or `if (this.proc !== proc) return` in process handlers.
- For unattended schedules, recheck current run authorization after discovery and between awaited launches; advance the cutoff through time spent disabled.
- Feature-flag caches retain their channel/version scope in memory as well as on disk. Refresh replies match
  that scope and the newest request generation after each await; stop/replacement invalidates pending work.
  Effective channel changes refresh and publish shared flags even when discovery fails or no window is open.
- Update checks and install approvals retain the channel, generation and artifact they started for. Native
  updater events have no request id: serialize checks until their terminal event, retain ownership after a
  visible timeout, and preserve staged-artifact information across channel changes. Idle scheduling must not
  replace an in-flight install promise; old idle probes cannot clear a replacement timer or restart its artifact.
- In React effects, cancel in the cleanup and list every dependency (`useExhaustiveDependencies`). When an effect's
  trigger is not what it reads (a chat switch resets the scroll, a turn's end refreshes git) or it is a run-once
  setup, name the triggers with `useEffectOn` from `src/lib/effects.ts`: each run starts with the latest props and
  state, but the listeners, timers and promise callbacks it creates keep that run's values, and the linter cannot check
  the trigger list, so prefer a plain `useEffect` whenever its dependencies are what it reads. A window listener that
  must answer with what is on screen now uses `useWindowListener`; other effect code reads later values through
  `useEffectEvent` and still rechecks the context after each `await`. State that belongs to one chat or folder is reset
  while rendering when that changes (`if (shownFor !== chatId) { setShownFor(chatId); setList([]); }`), so no frame
  shows, or acts on, the last one's. An effect that creates something native (a pty, a browser view or its listeners)
  runs once per that thing's identity (`useEffectOn([tab.id], ...)`): props its callers rebuild every render (a tab
  object, a command array, an inline handler) are not a reason to tear it down, and its listeners call handlers
  through `useEffectEvent`; settings it should follow later (theme, font size) get effects of their own.
- A `useMemo` over store slices hands those slices to the function it memoizes
  (`chatAccount(h, chatId, { claudeChats, claudeAccounts, accounts, segments })`) instead of letting it read
  `getState()`: anything it reads there that is not a dependency (a chat's segments, through `nativeOf`) stays at
  its old value until an unrelated slice changes.

- Browser import completion owns global progress and the durable last-import summary by its latest admitted job ID, not by whether the current job is non-null. Cancellation may let a replacement finish before an old reader settles; keep the latest owner after completion, gate both success and failure publication, and still return the retired job's cancelled result to its caller.
- Private Unix endpoints are published only after bind and final socket permissions succeed. Use the shared `PrivateSocketListener` to capture the directory/server, reject cancelled startup, retire failed attempts and drain late bind errors. Close clears advertised paths immediately; old callbacks cannot chmod or publish a replacement. Reopening tool transport restores session-revocation observation exactly once.
- Retriable browser listener startup owns both its server and its promise. Stop rejects a pending listen; callbacks and failure cleanup from that attempt cannot publish or clear a replacement. Close a bound listener if post-listen setup (including pairing persistence) fails, release temporary listeners, and recheck connection generation before opening a page after startup. Keep the captured resource through cleanup, including cleanup failures. A server-lifetime error observer still handles queued bind errors after cancellation removes the attempt listeners.

- A Codex sidecar login owns startup, browser opening, account reads and installation until commit, cancel, removal, timeout or dispose. Reserve ownership before the first RPC, capture early completion, claim completion once and recheck after every awaited boundary; retire only that attempt and clean only its staging home. Queued removal immediately cancels target re-verification and refuses new target attempts. Account removal coalesces by id and serializes across ids, removes from the latest collection, and reapplies a surviving account selected during cleanup. Add/re-verify/key writers skip retiring identities; a stable MoPilot record waits for its removal before being saved again.
- A MoPilot sign-in owns its listener and exchange until it settles: cancelled, timed-out and replaced callbacks cannot save credentials, open a page or finish a newer attempt. Account API retries, status bodies, consent acknowledgments, capability caches and refresh coalescing retain the credential identity they started for. Clear account-derived state on replacement/revocation, and let an old refresh retire only its own coalescing slot. Notify gateway consumers when the key changes even if the signed-in boolean stays true.
- A completed wait must release every subscription it raced, including the event that did not fire. Update retry delays remove their abort listener when the timer wins; write-backpressure waits share one cleanup path for drain and close, preventing a large or repeatedly resumed download from accumulating obsolete listeners. Test listener counts during repeated successful waits as well as cancellation and I/O failure.
- Model relay startup retains a captured listener attempt through bind and URL publication. Coalesce pending and ready starts, reject stopped attempts immediately, clear every advertised endpoint on stop, and track accepted connections so upgraded sockets cannot survive shutdown. A shared `listenLoopback` helper handles bind cancellation and queued errors for both browser channels and the model relay; old callbacks and cleanup never publish or retire a replacement listener. Couple pending upstream WebSocket handshakes to downstream end/close before sending the request, then remove those temporary listeners when the upstream closes; a backend that never answers must not survive client disconnect or relay shutdown.
- Acquiring a local update feed is not a completed native hand-off: if `setFeedURL` rejects it, close that feed before allowing a retry. Use one captured-feed cleanup helper for failed setup, obsolete startup, terminal native events and disposal; retire its published reference before closing, and record close failures without masking the check error or interrupting timer cleanup.

- A live thumbnail belongs to its chat, turn and capture slot. Coalesce slow polling and permission reads until they settle, then recheck ownership after every helper await. Forget, feature shutdown and helper exit retire pending captures and permission caches; queued probes cannot relaunch a retired helper. Reset both images and action targets when a card changes chat or turn.

- Recording history reads own one expanded-panel generation, for both successful snapshots and errors. Closing, unmounting or successful deletion retires pending reads. Capture the generation before deletion too: its delayed reply must not erase a newer reopened history that can include recordings saved after the delete executed.

- Scheduled-task lists, app availability and run ledgers use the shared latest-loader owner for both results and errors, including malformed-entry callbacks during parsing. A new request retires earlier publications; component cleanup also refuses queued requests. Key a task-detail view by task identity so another task never inherits its ledger while its own read is pending. A persistent shared list owns its reads independently of a particular navigation mount.
- Claude sign-in polling owns one attempt and its exact account record through both candidate and default-account status reads. Retain that attempt until validation commits, recheck after every await, and retire its timer on removal as well as cancellation/replacement. Share per-account status-read ownership between polling and refresh, and retire an older refresh before it starts more reads. A superseded poll retries within its existing deadline; retired attempts cannot update the default-account cache, publish success or rearm polling.

- Permission cards own both the chat ID and the missing permission. Remount local state when either changes, and retire the effect owner before unsubscribing. Recheck that owner after Request, recheck and status awaits, including errors/finally, so old actions cannot probe a retired chat, show old errors or clear a replacement action's busy state; queued notifications start no helper reads after disposal.
- A reading that names no account belongs to the login that produced it, not to the one active now. Codex app-server usage readings are charged to the login the app-server holds (`heldLogin`, none while a switch is applying), a limited turn to the login it started on, and a reached limit is confirmed with that login's own usage read before moving away.

- Retiring a read must not strand the state it was the only loader of. A Codex chat's first read retired by this app taking the chat (a fork's thread/started, a resume) still fills an unloaded chat that has shown nothing, as this app's own history without external-writer claims; only a newer read, a source switch or shown turns stop it. For every retirement path, ask what loads the state afterwards.

- A reading that can come from someone else's cache is dated by when its data was measured, not when it arrived. Claude Code's `/usage` answers from its own cache when the usage endpoint refuses, so that answer carries the CLI's fetch time and cannot replace newer live limits from a chat; merge readings by measurement time.

- A limit read earlier lifts at its reset, not when a new reading arrives: Claude Code's cached `/usage` answer can outlive the window it describes. Derive the reset time from what the source printed, check limits only with `windowLimited`/`resetAhead` (src/harness/usageWindows.ts) and show a window past its reset as started over (`usedNow`). Lint: `plugin/limit-expiry`.
- #1225: A split that moves what has already rendered remounts it, so a boundary learned later than the block it cuts must be left where it is. #1226 made `useStreamedSegments` (src/components/markdown/Markdown.tsx) parse the tail before each render, which covers the blocks of one delta arriving together; but a block whose first line could still continue a list or indented code above it (`closedBlocks`'s MAY_CONTINUE) only closes a render after it first appeared, and cutting there then moved a paragraph that was on screen into a run of its own, replaying its entrance animation and dropping any state inside it. Runs are now cut only in the text a render adds (`state.shown`), so a run may hold two blocks rather than move one. Ask of any boundary, key or grouping worked out from accumulated text: has what it would move already been shown?
- A Stop is counted, not remembered as a flag a later write can clear: `ChatController.claudeDeliver` and `acpSend` reset `interrupted` when they send, so a Stop pressed while a start or steer was still awaiting (live-control steps, a CLI or agent starting, a handoff, a delivery check, a Codex resume) was forgotten and the prompt went out. A send now attaches `stopGuard` (a check on the chat's Stop count) to its item when it begins, adapters carry it with `carryInputGuard` (including copies made for a handoff or a goal command), and every transport checks it right before the prompt goes. Ask of any flag a send path resets: can the event it records arrive between the moment the operation began and the reset?

- Native acquisition owns the effect before its acknowledgement arrives: retire pending debugger attachments on close, disconnect, tab release and obsolete turns, then serialize their eventual cleanup before a successor attaches. Cleanup failures retain the old native effect for retry, while a rejected duplicate attach owns no new effect; terminal absence is already released. The main-process producer also waits for its deferred release before starting another attach and rechecks the exact attempt after every wait. A command timeout after dispatch is uncertain native ownership, not proof that acquisition failed; retire it through the same release barrier, while known attach rejections preserve earlier effects. Startup restoration uses the same queue and every connection path waits for restored ownership. Command replies carry their original authenticated connection independently of the effect owner, because a replacement connection can reuse request IDs. Test delayed effects and acknowledgements, a queued successor, failed cleanup followed by a new turn, a command timeout followed by late native success, and real request-ID reuse across reconnect.
- When a request carries a snapshot or context note, does its post-await acknowledgment identify the exact sent generation? Retire acknowledgment receipts on reload, compaction, shutdown and async readiness changes, including when the old note has not yet been acknowledged. Test readiness settling before the old response as well as after it.
- Terminal connection cleanup retires pending readiness, pairing, HTTP upgrade and cryptographic work before clearing timers or closing sockets. Exercise completion after teardown and retry callbacks already queued before reset; neither may reopen transport, install a keepalive or clear a replacement timer. Fixture teardown uses the connection owner's disposal, with explicit transport-only retirement when simulating abrupt worker death.
- A leak this class leaves after teardown (a late callback starting a referenced timer) stalls the whole unit run with every test green (#1759). `tests/support/exit-watchdog.ts` fails a test file still alive 15 s after its last test, naming what is open; a new trip points at the file whose teardown skipped its owner's disposal.
- #1866: An id a card captured when it rendered is a claim, not proof. `codex:respond` forwarded any answer whose id was not a live approval, and Codex numbers its requests from 0 again after an app-server restart, so a stale card could answer the new server's request with the same id; the renderer also sent a Claude or ACP answer to Codex once its card had left `pending`. Main now takes an answer only for a card it still holds for that harness (`takeApproval` in electron/session/controllerEvents.cjs; Claude Code, ACP and MoPilot's own broker already refused a gone id) and says retired out loud (false); the renderer routes by the card's own source, sends nothing for a card that is gone, and reads false as "Already answered" (`answerTaken`, src/store/answerRetired.ts) instead of counting it as delivered. Ask of any action that takes a captured id: who checks it is still live, in the current process generation, and does the caller hear the refusal?
- #1866: A Stop, Retry, Take over, Hand back, Resume or task Stop button is bound to the turn, tab, task or app it showed, not to whatever runs at the click: a stall banner's Stop stopped the next turn a queued message had started. Pass the id the button showed (`interrupt(chatId, turnId)`, which main checks against the turn it runs on every harness: Codex names the turn on `turn/interrupt`, Claude Code and ACP through `ChatController.turnIs`), and read the answer with `liveAction`/`liveClick` (src/store/liveAction.ts), which shows the shared "Already ended" line for false or 'retired'. Lint: `plugin/detached-action`.
- #1988: A toast's action, a message's Fork, an offer card and a "Save password?" bar acted on what they captured when they showed. "Continue on X" set a pending switch with the model the toast saw, after the chat had switched; the paid-access offer moved chats the user had since pinned elsewhere; an expired account's "Sign in again" added a new account once the old one was removed; "Fork chat from here" forked the whole chat when its turn was gone; "Do it here" sent its message before main refused the expired offer; and Save stored a newer sign-in the bar never showed. Read the state again at the click (`takeWayForward`, `moveStillPinned`, `signInAgain`, `forkPointHere`), let main take the claim before the step that can't be undone (`task(id, 'here')` before the message, `reopen` when the chat refused it), and name what was shown (the login offer's `offerId`). The lines are shared in src/store/liveAction.ts. Lint: `plugin/stale-toast-action`.
- A window that has not read a value yet must not send "none" for it (#2304). After a reload, `syncOwn` pushed `{ model: null }` for every Claude chat whose settings were still unread or whose model list hadn't arrived. Main took that null as the chat's pick, so the next turn ran on the default model, and a live CLI got `setModel(undefined)`, which wrote a hidden `/model default` into the transcript. A MoMo chat also lost the model its brain set through the same map. The window now sends only what it knows (`src/harness/claude/own.ts`), main's `setOwn` keeps a field the push leaves out, and a MoMo chat's model lives in its file (`meta.momoModel`), which main runs above any window push (`tests/momoClaudeModel.test.ts`). Ask: *is "unknown" distinguishable from "none" in this push, and who owns the value when both a window and main write it?*
- #2847: A render read the chat's session twice, from two copies. Since session patches are held for the next frame (`flushSessionPatches`, src/store/session/useSession.ts), `sessionOf` returns the held copy while `useSession`/`useSessionField` return the committed one, and an app-store selector that called `composerFirstTier` (which reads `sessionOf`) is not re-run when the session commits. The composer took its basic harness from the committed pending switch and its first-tier one from the held "switch done", got neither, and `permissionMenu(null)` crashed the chat mid-switch. Components read the session through a session hook and pass it in (`useComposerFamily`, `useComposerFirstTier`). Ask of any value a render combines from two stores: do both parts come from the same snapshot, and does a change to either re-render it? Lint: `plugin/held-session-selector`. Holding the patches also reordered them against the harness events main sent after them: the CLI's own end of a crashed turn landed before the crash patch, so `onCrashed` found no turn running and added the banner a refused send gets, beside the turn's own error. Each harness's event entry (Claude's `flushHeld`, ACP's and Codex's `onEvent`/`onCodexItem`) commits the held patches before any event but a streamed delta. Ask of any queue that holds one kind of message: what other channel did the sender order it against?
