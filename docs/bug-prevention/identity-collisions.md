# Identity collisions

One of the [bug classes](README.md#bug-classes). A pull request adds its note about this class as a file of its own in
`notes/identity-collisions/` (one note per file), not below; the bullets below are the earlier notes.

Two things get the same id: `Date.now()` ids made in the same millisecond, React keys from array indexes or
non-unique names, pane tabs opened in quick succession (#290, #447, #450, #456, #498).

## Notes

- Project disk readers keep one nonempty local id per entry, alongside unique folder paths; reject a duplicate id before reserving its path. Validate imported native ids with the same reader, so malformed entries cannot absorb a healthy project or make one id-based action change two folders.
- Use `crypto.randomUUID()` or a counter; key React lists by a stable unique id.
- A list whose items have no id is keyed by `withKeys` (`src/lib/listKeys.ts`): the item's content and how many
  equal items came before it, so a row keeps its key when rows before it come or go (long values go through
  `fingerprint`). A list edited in place, an input per row, is keyed by `useRowIds`, so removing a row removes
  its input instead of showing the next row's text in it.
- Lint: `plugin/time-id`, `noArrayIndexKey`.

- Encode opaque multi-part identities with the shared `identityKey` tuple helper; include the account, browser or operation namespace that owns them. Retain original owner fields for exact cleanup and callbacks instead of splitting encoded keys or deleting by string prefixes; represent wildcard scope separately from literal native IDs.

- Decimal filenames are integer sequences, not floating-point numbers. Allocate recording successors with BigInt and use the shared filename-sequence comparator for recording listing/retention and Chrome LevelDB discovery; retain string IDs at the IPC boundary and numeric capture timestamps only as display metadata. Test existing IDs beyond the safe-number range, reverse directory enumeration, same-tick saves and backward clocks so neither allocation nor pruning overwrites a clip and discovery selects the newest sequence.

- A login's identity read from a file other clients also write is a claim, not a fact. Claude Desktop writes its own account into `~/.claude.json` while the keychain login MoPilot runs is another account. Trust such an identity only at the moment MoPilot saw that login sign in as it (electron/harness/claude/loginIdentity.cjs), otherwise show it as unconfirmed with a way to confirm, and never let it refuse or merge another login by email.

- A login's identity comes from the server's answer for the token that login runs on, not from a file that other clients also write. The Claude Code CLI's own login is read in MoPilot's folder (`CLAUDE_SECURESTORAGE_CONFIG_DIR` names its credential store), with its profile marked stale so the CLI refetches it, and its usage is read the same way, so the reading and the account it names come from one token (electron/harness/claude/loginIdentity.cjs). After a failed read, keep the last answer and mark it unverified. Never refuse or merge another login by an email the server did not confirm. `tests/claudeLoginNames.test.ts` keeps every read of a config's `oauthAccount` behind that module.

- A login is a credential store, an account is what the server bills. Two logins can become one server account after they were added, when one is signed in again outside MoPilot (the Claude or Codex CLI's own login). Every account list folds signed-in logins by verified server identity at read time, not only when a login is added (electron/identity/contract/sameAccount.cjs: Claude's accountUuid, the CLI login only by the server's answer; Codex's workspace and member from the token), and the switch and pool policy count the folded logins as one quota. Keep reading the folded login, so a later re-sign lists it again. `tests/sameAccountGuard.test.ts` keeps any source from matching two logins by their emails.
- A name a login's own folder holds stops being its identity once the sign-in that wrote it is over. An added Claude Code login's folder named one account while its credential store held another's token (#1582), and the CLI never corrects the name: a token refresh merges the new profile's plan fields, keeps `accountUuid` and `emailAddress`, and marks `profileFetchedAt` fresh, so the CLI's own daily profile check never runs again (CLI 2.1.302). Every login, added ones included, is the server's answer read in a MoPilot-owned folder with its email cleared first (a refresh leaves it empty, so it is never taken for an answer), the answer is kept on the login's record until it is signed in again or out, and a login whose answer is another account than the one it was added as says so on its row. `tests/claudeLoginNames.test.ts` lists the only functions that may read a config's name.
- A saved list position is an identity only for the list it came from. A question card's answers were kept as a chat note anchored to their turn's id and, as a fallback, its index; after `/compact` the transcript read starts at the compaction, the turn's id is not among the turns shown, and the index (clamped to the last turn) put the old answers into whichever turn was newest, moving again on every reload (#1949). `withChatNotes` (src/lib/chatMeta.ts) now places a note whose turn is not shown after the latest shown turn that began before it was written, or nowhere when none did; the saved index is kept only for turns with no times and for notes with no turn id (the chat's latest turn by design).
- One account, two avatars. The account list decides avatars with `accountAvatars` (initials told apart across the list, "?" for an unverified login), but the model pill built its own from a bare email: an unverified Max login read "API" and four Codex accounts starting "du" all read "DU" (#1930). Its test stubbed `AccountAvatar`, so it never saw the initials. `AccountAvatar` now takes the account, not an email, and reads it through `accountAvatars` (the list's label when given), so no surface can derive initials from a bare email; the pill's test renders the real avatar (change contract I4).
- Every stylesheet in src/ is global, so a class name is an identity shared by the whole app. The composer's PR sheet named its rows `.pr-row` and `.pr-row-title` while the Review page's PR list already used them in page-sidebars.css; the later rule made the sheet's rows centered columns, and the sheet's rules centered the Review list. The Schedule dialog's fields and the Scheduled list's rows shared `.sched-row` the same way, held apart only by a more specific override. Prefix a new component's classes with its name, and never answer a shared name with a specificity patch: rename one. `tests/cssClassOwners.test.ts` fails when a class has base rules in two stylesheets unless it is listed as one component styled in layers, with why; it reads only bare `.name` rules, so a name shared through compound selectors alone still needs the grep (`rg -n 'className=.*\bname\b' src`).
- A component's own classes are local to it, so no other file can share them. A component that owns its styles keeps them in a CSS Module (`<name>.module.css`, docs/code-quality.md#component-stylesheets-css-modules), whose classes Vite hashes per file, as the PR sheet's `prMonitor.module.css` does; only `src/styles` holds global stylesheets, and `tests/cssClassOwners.test.ts` refuses a plain `.css` file anywhere else and a module class no component reads (or one it reads that the module lacks).
- One ownership, two keepers. The Chrome extension kept a chat's tab on a `target_closed` debugger detach (Chrome replaced the page, as a prerender's activation does) while main's `ChromeLink` revoked it on every detach, so the next step was refused as "taken back by the user" (#2325). When two processes each keep an owner of the same id, list every invalidating event and test it against both keepers (`tests/chromeDetachOwnership.test.ts` runs the real extension `Sessions` against the real link). Ask: *does each side retire this owner on exactly the same events?*
