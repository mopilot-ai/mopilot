# MoMo core: notes, approval gate, learning

Pure TypeScript in `shared/momoCore/`: no I/O, no Electron, no Host. The clock, ids, hash, stores and audit sink are injected. Everything stays behind the existing MoMo flags and invite gate. Design: "Function 2 of 5 Knows your work" (notes), "Function 5 of 5 Asks first, and learns", sections 3.4 and 3.5 (#5474). Third-party origins and licences: `shared/momoCore/NOTICE` (also shipped in the notices file).

| File | Owns |
| --- | --- |
| `text.ts` | Quote folding, same-line test, secret-looking text, text that reads as an order, untrusted-data wrapper |
| `notes.ts` | Note, line, source, archive shapes; `statusOf` (Mentioned once, Learned, Confirmed, Let go: computed, never stored); `bringBack`, `editByOwner` |
| `noteOps.ts` | `applyOps` (model proposes add, update, retire; code checks the quote, secrets, planted orders, Confirmed lines), `undoEntry`, journal entry |
| `noteTidy.ts` | `tidy` (nightly: expired, duplicate, stale; at most a fifth of the lines; never a Confirmed line; one snapshot, one journal entry), `restoreSnapshot` |
| `gateRules.ts`, `turnTaint.ts`, `approvalGate.ts` | The gate: unprompted may only read, then deny, allow, ask; taint; cards bound to the exact action, single use, 30 minute expiry for background cards, one answer on any device, audit line first |
| `learning.ts` | Reactions per pattern, a rule after two that agree, opposite starts over, silence never counts, quiet rules on at once with Undo, others wait for a tap |

## Rules in code (and the test that holds each)

- A line is added or updated only if its quote (at least 8 characters after folding) is in the cited source itself, and its text says what the quote says. Only an owner's own message is owner evidence; a mail can never vouch for itself. Text or quote that reads as an order, or looks secret, is rejected, even when the owner wrote it. Rejected ops are listed with a reason; the others apply (`tests/momoCoreNoteOps.test.ts`, `tests/momoCoreReview.test.ts`).
- Outside lines are origin `mail`, Mentioned once until a second source agrees; they never authorize anything. A mail may only update or retire lines from its own message or thread, and an update takes the new origin, never an older stronger one.
- An owner's order ("always send invoices to X") is not a note: from an owner message it comes back in `suggestions` and becomes a `suggested` rule that waits for a tap and is plain text, never a gate rule by itself; from mail or the web it is rejected. A mail may only update or retire lines whose origin is `mail` and that came from its own message or thread; agreeing with an owner-derived line adds a source but grants no right to rewrite it.
- Confirmed lines change only when the owner says so in a clean chat (`tainted: false`). A tainted chat never creates Confirmed lines and never touches one; every automatic pass leaves them alone.
- Every applied op returns an undo entry. Undo restores a line only if it still looks as that op left it, and puts it back in place.
- Gate order: unprompted work that is not a read or a write to MoMo's own notes is denied before any rule; then deny rules; reads and own-notes writes pass; spend and settings always ask; a chat that holds outside content asks and no allow rule changes that; then ask rules, allow rules; otherwise ask. The Auto checker level is not built (decided: not in v1).
- Taint is sticky: from the first outside (or unclassified) tool result it stays for the chat, through later owner messages, until the Host calls `reset()` because a compaction or new session provably dropped the content.
- A card is bound to a keyed digest of tool, effect, scope, arguments, chat, origin and taint. The first answer wins on any device. The `approval.decided` line is written while the card is `deciding`, before it can be used; use is claimed (`using`), its line written, then `used`. An allowed card unused for 5 minutes is void; a background task's card ends as a deny after 30 minutes; a chat card never expires. At use the rules are read again, so a deny added since refuses. If the chat became tainted after the owner answered, `authorize` returns `reissue` with a fresh card (`replaces` names the old one) and the old approval is void; the UI shows it as the same card needing a new tap. An approval given while tainted still works after a reset. An unattended repeat of a denied action, or of one that timed out unanswered, is refused for 24 hours unless a newer card was allowed or is still waiting (an approval that simply went unused is not a refusal); the owner asking again in chat always gets a fresh card. Arguments that are not plain data fail closed, and the gate refuses to start without a keyed hash.
- If an audit line cannot be written the check denies, an answer or use is rolled back, and nothing runs. The core never verifies `by`: the Host must set it from the authenticated session of the device that answered.
- Learning: a quieter or ask-more rule turns on at once with Undo; a rule that does more, skips a question or rewrites drafts waits for a tap. A reaction the other way retires the opposed rule at once, on its own pattern and on any pattern that names the same action. Skip-a-question rules become allow rules and ask-again rules become ask rules in the gate (`toGateRules`, values escaped, so a scope holding `*` is literal); an ask rule beats an allow rule, and taint, unprompted and mandatory limits still come first. Labels are sanitized when recorded and rule sentences are made from data when shown.

## On a Host (phase 2)

**Status: in the path of MoMo's own tools once #4843 lands.** With the tool runner of #4843 (`host/src/momoTools.mjs`) merged into this branch, every call of MoMo's four tools passes `home.gate.run`, and the runner refuses the call when `home.gate` is absent (tested in `tests/hostMomoToolsGate.test.ts` against the real registry). It also refuses writes in a chat the gate (or its own record) marks as holding outside content, before my gate is asked. Two taint records exist today, the runner's (`taint.json`, written by `momoChats`) and the gate's (`gate-taint.json`, never evicting a chat); each reads and writes only its own file, and either one saying tainted refuses. They are to become one (one file, one shape, one API) with the scheduler lane; until then they are two. Every store of this layer is sealed with the home's data key (`home.data.safeStorage`) under `home.storage.dir`, so it moves with the home: cards (`cards.json`), the gate's key (`gate-key.json`), taint (`gate-taint.json`), notes (`notes.json`), rules and reactions (`learning.json`); the audit log is MoMo's own (`home.stores().audit`). `electron/momo/toolTrust.cjs` is the desktop app's own path and is not on the Host. Not yet: tools beyond MoMo's four (a mail send, a browser) have no runner on the Host, so nothing sends yet; `notes.ops` is called by the `momo_notes` tool (below); `learning.suggest` by `notes.ops` for an owner's order.

New files only, found by folder (`host/src/momoServices/README.md`): `momoServices/gate.mjs` (id `gate`), `notes.mjs` (`notes`), `learning.mjs` (`learning`), shared helpers in `host/src/momoCoreHost.mjs` (sealed card store with compare-and-set transitions, the audit sink over MoMo's hash-chained log, the HMAC key, the taint store) and `host/src/momoToolEffects.mjs` (what each tool does), and the wire methods `host.momoCards`, `host.momoCardAnswer`, `host.momoNotes`, `host.momoNoteAct`, `host.momoRules`, `host.momoRuleAct`, `host.momoReact` (`host/src/methods/momoNotes.mjs`, `shared/host/methods/momoNotes.mjs`). State lives under `home.storage.dir`, so a move carries it and Reset deletes it.

- **Who may act as the owner.** Answering a card, changing a note or a rule and recording a reaction need a paired `desktop` or `phone`; the local command line (any process on this machine) may only read. `by` is `kind:` plus a short digest of the connection's key, never a request field; the card keeps the device's name for "answered on Dana's iPhone".
- **The call.** `home.gate.run({chatId, tool, args, origin}, exec)` classifies the tool (`momoToolEffects.mjs`: an unlisted tool is a settings change that always asks and taints the chat; in a chat holding outside content, saving or forgetting what MoMo remembers and open loops need a card, so what is kept was approved), decides it, and runs `exec` only if allowed, on a Host that still holds the stamp. A call without an `origin` is unprompted; a call without a chat is never clean. Refusals and cards reach the model as a `ToolError` (`approval_pending`, `denied`, `unprompted`, `unavailable`, `invalid`, or the tool's own failure, cut and cleaned). The model's retry after Allow spends the card once. Every change of a card calls `home.push.cardChanged({cardId, status, chatId})`.
- **Taint** is kept on disk (`taint.json`, so a restart and a move keep it), is marked by every tool that ran whether or not it answered, and is cleared only by `reset()`. `notes.ops` reads it from the Host's record, never from its caller.
- **A move** voids every card made for an earlier lease: it cannot be answered or used, and the call asks afresh.
- **Changes of what the gate may allow** (owner rules, learned rules, confirms, undos) and every change of the notes or a reaction write their audit line first; with no audit log nothing is changed. A reaction is derived from a card the same device answered, once.
- **Notes**: the nightly tidy runs at most once a day however often it is asked for; a restore keeps the notes it replaces as a snapshot, so it can be restored in turn.
- **Cards** show the call's own arguments (up to six plain fields, cleaned and cut), never the arguments object.
- The nightly tidy runs from 03:00 home time (a 15 minute tick); "Restore last night" is `host.momoNoteAct {op:'restore'}`.
- The Host bundle strips the core's types at build time and ships it as JavaScript (#5496), so the core must stay erasable TypeScript: no enums, namespaces or parameter properties.

Open, not done here: the runner wiring above; the audit sink writes an intent and its outcome back to back for an approved action, instead of the outcome after the action ran; a note's source label carries no message title.

## What the home lane implements

1. `CardStore` (`approvalGate.ts`): `get`, `put`, `list`, `byFingerprint`, and an atomic `transition(id, expected, patch)` (compare-and-set). One store on the Host, so an answer on any device resolves everywhere. Broadcast `gate.subscribe` changes to every connected client.
2. `AuditSink.append(event)`: write one metadata-only line to the existing hash-chained audit log (`electron/momo/audit.cjs` and the Host's `host/src/audit.mjs`) and resolve only after it is on disk; reject if it cannot. Event names follow rakazo: `action.allowed`, `action.refused`, `approval.requested`, `approval.decided`, `approval.expired`, `approval.consumed`, `approval.policy.changed`.
3. Set `origin` on each run: `chat` (owner in the conversation), `task` (owner started it, runs in the background), `unprompted` (triage, brief, tidy, routine). Set `tainted` from `createTurnTaint()`: call `toolResult('outside' | 'owner_state' | 'unknown')` for each tool result and `ownerMessage()` for each owner message.
4. Run `gate.sweep()` on a timer (for example each minute) and tell each waiting run nobody answered in time. Call `createTurnTaint().reset()` only when a compaction or new session provably dropped the outside content.
5. Notes: persist `NotesTree`, `UndoEntry`, `JournalEntry` and `Snapshot`; build `SourceText[]` for each op batch (owner chat messages have `owner: true`; mail and events never do); run `tidy` once a night and keep the returned snapshot.
6. Learning: persist `LearnState`; call `record` on each tap (never on silence); pass `toGateRules(state)` with the owner's own rules to `check`; show each rule `record` returns in `retired` (a reaction the other way retired it) so the owner can see why it stopped; hand `OpsResult.suggestions` to `suggestRule`.
7. Hash: pass a keyed digest (HMAC) marked `keyed: true` as `hash`, so cards and audit lines never carry arguments.
8. `CardStore` also needs `byFingerprint` and `list(statuses)`; `authorize` takes the current rules (deny, ask, allow).

## Host responsibilities that keep the core honest

- Derive the learning `pattern` deterministically from the action (for example tool, effect and scope), never from model text, so the same action always lands on the same pattern.
- Treat a compaction summary as still tainted unless the outside content is provably gone; call `reset()` only then.
- Authenticate `by`, and set each run's `origin` and `tainted` itself; the core trusts both.

## Not built here

UI, Host wiring, Google OAuth, the Auto checker, model calls. The model proposals (`Op`) come from the home lane's background model; this code only checks them.

## The action's own audit lines

Besides the gate's decision lines, a call the gate lets run that is not a plain read has its own intent line (`run <tool>`, the keyed digest of its arguments, and the card id when a card was spent) on the disk before it runs, and an outcome line when it ends: `done`, `not sent` or `uncertain`. A plain read has no such pair, so a loop of reads cannot rotate the evidence of a send out of the log. With no audit log, or one that cannot be written, the action does not run (`audit_unavailable`), and an answered card is not spent: the intent is written before the card is, and a card that cannot then be spent ends the intent as `not sent`.

A failure of a call that may have left this Host (a send, a spend, a delete, or a read that sends model-chosen text out) is `uncertain` unless the error positively says `notSent`; the model is told it may already have happened and the card is never retried. An outcome that cannot be written leaves the intent open. When the gate is built (the first use of a process), `settleUnfinished()` of the audit log records every intent an earlier run of the Host left open as `uncertain` and the Host reports how many; nothing is retried.

## Notes from the owner's words (`momo_notes`)

The chat's own model proposes one add, update or retire per call through `momo_notes` (`host/src/momoNotesTool.mjs`); nothing is read from a background model. The source of a note is never an argument:
- **The words.** The Host records the message a paired owner device (desktop or phone, `isOwner`; not a home client or another Host) sends to the main chat when `momoChats.guard` accepts it (`host/src/momoServices/ownerWords.mjs`). Only the message of the turn that is running is kept: one per chat, at most 4 chats (the least recently heard goes, never the chat being written), 4000 characters cut on whole characters, sealed under `home.storage.dir`, and dropped when the turn settles (`home.turnEnded`). With none (a background run, a told result, an ended turn, a client that is not an owner device) the call is refused as `read_only` and nothing is written.
- **The checks.** The note core checks the quote is in those words and that the line says what the quote says. For an update or retire the quote must also be about the line it changes (`notes.binds`: at least half of the stems each way, against the line's text); any other words of the owner's make a card, also in a clean chat, which shows the line as it is now, the new text and the words it was checked against. A chat that holds outside content always gets a card.
- **The card carries its op.** When the call becomes a card, the exact op and the owner's words it was checked against are kept with the card (`bound-notes.json`, at most 50, dropped when the card is denied, expires or is void). The owner's Allow, in any later turn, runs that op once through the gate's resume path, with no retry by the model and no re-check against a later message; Deny and expiry write nothing.
- **Orders.** An order found in the owner's words is kept out of the notes and becomes a suggested rule (`learning.suggest`): the same order folded (case, spacing, accents) is one suggestion, at most 20 wait for a tap, each is audited before it is kept, and it can never be an allow rule.
- **Design limit.** Text the owner pastes into their own message counts as the owner's words: a page or a mail they paste is as trusted as what they type. The checks bind a note to the words and to the line, not to who first wrote the words.

## Questions (`momo_ask`, `question.answer`)

MoMo's main chat can ask the owner one question with 2 to 6 short answers to tap (`momo_ask`, `host/src/momoAskTool.mjs`); a question never asks to act, that is an approval card. The question is kept by `host/src/momoServices/questions.mjs` (sealed under `home.storage.dir`, at most 10 waiting), shown as a `question` row of MoMo's chat, and answered by the owner's `question.answer` intent from any paired device: the first answer wins, the audit line is written before it is kept, and a question of a lease this home no longer holds is void. The answer reaches the turn the way an approval does: the model asks the same question again and is given the answer once; after that the same words are a new question. A background run never asks (the runner refuses it as `read_only`).

## What the owner does with their own hands (`note.write`, `note.forget`, `rule.add`, `rule.turnOn`)

These come from the owner's paired device through the owner veil, so they are owner-origin writes: no card and no model quote, audited first, lease-checked, with a History entry and an Undo (`shared/momoCore/noteOwner.ts`). A line the owner writes is Confirmed at once (not a secret, not an order: orders go to Rules); forgetting a line or a whole note lets the lines go, so History can bring them back and Undo restores them in order. A rule written in words (`rule.add`) is the owner's, on at once, kept as their words with the effect they chose (tell now, stay quiet, ask first). It names no action, so it can never become a gate rule and cannot remove a card; "don't ask" is refused from words because a rule that stops MoMo asking must name the action, and that is what Always allow on a card does. **How it applies, with no parser:** the owner's rules in words (and the orders they accepted) are given as standing instructions: `home.service('learning').ownerRules()` returns `[{ id, text, kind }]` (kind `tell_now`, `stay_quiet`, `ask_first`, or `instruction` for an accepted order; at most 100 rules, each at most 300 characters) for the notice judge's prompt (tell now / stay quiet decide whether a notice is told now) and for MoMo's brain's turn context (ask first can only add asking). They are the owner's own text from a paired device, so trusted as instructions, but they never remove a card and never become a gate rule. Until both lanes call `learning.appliedBy('notice')` and `learning.appliedBy('brain')`, the Rules page shows such a rule as `saved`, not `on`. `rule.turnOn` brings an undone or turned-down rule back.

## Ask again and edit a card (`approval.askAgain`, `approval.edit`)

The gate keeps the request each card was raised for (`host/src/momoGateBound.mjs`, `bound-notes.json`: at most 50, sealed, moved and deleted with the home; for a note also the owner's words it was checked against). The entry is forgotten when its card is void, completed or gone, so a card that was turned down, ended unattended or ended uncertain can be asked again.
- **Ask again** raises a fresh card for the same request, as the owner's own request (so the unattended repeat refusal and short expiry do not apply); asking twice gives the card that already waits. A note's line is shown as it is now. When the gate would now let the request through, the owner is told to ask in the chat.
- **Edit** (a waiting card with a `body` or `text`): a NEW card for the edited text, with new arguments and a new binding, and the old card void ("superseded"): a bound card is never changed in place. The edited text is the owner's own, so on Allow a note is written as the owner's line (Confirmed). A card with no text (a retire, a delete) has nothing to edit.
- **Keeping the words:** the owner's words of a turn live as long as the card can still be asked about (up to 50 cards), not only while the turn runs; a card that is denied keeps them for Ask again.

**Restore (`note.restore`).** "Restore" on a note brings back the lines the nightly tidy let go in that note, where they were, using the tidy's own undo entry for that note's changes only: a line the owner changed since is left alone, the other notes are not touched, and what came back is not brought back twice. The restore is a History entry of the note.

## Tools of other lanes behind the gate (`home.gate.tools.register`)

MoMo's own tools (memory, loops, notes, ask) have their effects fixed in `host/src/momoToolEffects.mjs`. Another lane that adds a tool (a mail send, a calendar change, a browser action) puts it behind the gate with `home.gate.tools.register({ tool, effect, egress?, scope?, summary? })`: it says what the tool does (`read`, `write`, `send`, `delete`, `spend` or `settings`), and, for the card, what it touches (`scope(args)`) and one line (`summary(args)`). Until a tool is registered the runner refuses it ("isn't available to MoMo yet"), and an unknown tool is `settings`, which always asks. A lane cannot claim the free class of MoMo's notes, cannot take the name of one of MoMo's own tools, and cannot say its results are trusted: what comes back from another lane's tool is outside content, so the chat that called it is tainted and its next change asks. A `send`, `delete`, `spend` or `settings` tool is a card the owner taps; a background run may only read. The tool's own runner (registering it in the Host's registry, `authorizesItself`) stays with the lane that owns it.

## Limits and retention of what the gate keeps (review of #5556)

- **At most 50 cards wait for the owner in all, and 10 from one chat.** More is refused to the model in words; a waiting card is never pushed out by newer ones, so injected text cannot hide the owner's genuine cards or fill their phone.
- **Edit is offered only on a card the Host itself runs** (a note: `editable` on the card), because for any other card the chat runs the call and would never see the new text. The old card is claimed (void, "superseded") before the new one is made, so the old text cannot be allowed beside it.
- **After an Allow, if the chat read outside content,** the gate voids the card and asks again; the fresh card keeps the op and says "Asked again: this chat read outside content after you allowed it".
- **A card's request is kept** only while it waits, or for an hour after it was turned down, ended unattended or ended uncertain (so the owner can Ask again); a void or completed card keeps nothing.
- **Ask again** when an Always allow rule lets the request through does it (and says so), but only on the line the owner was first shown.
- **Questions:** a chat that read outside content is not asked questions through a card (MoMo says in the chat what it needs); the row names no device (who answered is in the audit line); a question that waits is never trimmed; stale ones are voided on start and every minute.
- **The owner's rules in words:** 100 rules on or waiting at most (turned-down and undone ones do not count and are forgotten after 30 days), 300 characters each, 6000 characters in all given to the judge and the brain, as the owner's standing preferences below the gate; a rule that skips a question and was undone comes back only through Accept; an order the owner turned down is not suggested again.

## What the owner does with notices becomes learning

`learning.consumeNotices()` is the one place the notice lane's reactions are counted. It reads `notice.reactions()` (recorded by the notice lane from its own decision log, never a client's description) when the home starts, every minute, and when called. Every reaction carries the notice store's id and a number that only grows in it; what was looked at last is remembered as that pair (the **cursor**, kept with the learning state, so it travels with the home). Only what comes after it in the same store is looked at, so nothing is counted twice or skipped however many reactions the lane has trimmed. A store with another id (Reset, Start fresh) or numbers that went back is read from its beginning, and a tap older than the owner's last Undo or turning down of its rule never counts. The cursor and the matter marker move only after the audit line is written: a tap whose line could not be written is looked at again next pass (a pass stops there, so order is kept). At most 50 per pass, and the home's own look repeats passes until nothing is left; the matters already counted are remembered (500) so a second tap on one matter counts once.
- **"The same kind of notice"** is the sender: its **domain**, except for a **public mail service** (`shared/momoCore/senders.ts` `isPublicMail`: the mailbox providers, their country variants like outlook.fr or yahoo.co.jp, and shared-hosting names like github.io or blogspot.com; the file says how to add one; a domain under a shared-hosting suffix is one owner's), where a domain is thousands of unrelated people, so the key is the **full address** (the reaction's `fromAddress`; with none there is no key and the tap is set aside). Domains and addresses are written in one plain form (lower case, no trailing dot, punycode) and a key is built only from characters that cannot add a separator, so a crafted address cannot change the pattern or the label on the Rules page; only a pattern this module made is read back.
- **2 taps on different matters** (`REACTIONS_NEEDED`) make **one** rule in the suggested state ("Don't tell me right away about mail from acme.com", with the line "All mail from acme.com is held for the brief."): it waits for the owner's Accept (audited; never on by itself). A second tap on the same matter, no usable sender or matter, an unknown kind, one already looked at, and a sender whose suggestion the owner turned down (until it is forgotten after 30 days) do not count.
- **Signals:** "Make it a rule" makes the rule at once (the owner pressed it), and it is on the Rules page as on, with Undo; "Ignore" drops the signal and the next tap starts the count again.
- **Applying it:** `learning.quietSenders()` returns `[{ domain, address, ruleId }]` for accepted quiet rules (`address` only for a public mail service; at most 200). The notice lane keeps those senders' notices out of "tell now" in code, still never over the phishing check, quiet hours or the daily cap. An owner's rule of "tell me" (`tell_now`) whose words name the sender **wins**; the words are read as whole words by `namesSender` in `shared/momoCore/senders.ts` (the same function the notice lane calls): an address names only that address (and also a domain-wide sender at its domain: the more specific wish wins), a domain names that domain, so `notacme.com` or `bana@gmail.com` lifts nothing and one gmail address never lifts another: that sender is left out of `quietSenders()`; and a learned "keep" reaction for the same sender undoes the quiet rule itself. The Rules page line says where the mail is held: "for the brief", or "in Watching (your brief is off)" when the owner's brief is off (`inBrief` is then false); the learning service reads that from the Host's prefs on every `view()`.
