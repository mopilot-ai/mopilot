# mopilot-host

The MoPilot Host runs chats for the harnesses on a machine you choose, without Electron. It is a Node program that reuses the app's session and harness code (`electron/harness`, `electron/platform`), with the app's Electron-only parts replaced by ports the Host installs (`host/src/electronPorts.mjs`). It listens on a unix socket in its data dir (no TCP); the Mac reaches it through an SSH tunnel to that socket, or through the relay (below).

Design and plan: umbrella #2709, this package #2711, decoupling #2720. How to use a Host from the app (adding a machine, chats, the remote browser, continue on another host, troubleshooting): [docs/host.md](../docs/host.md).

## Needs

- Node 22 or later, and `tar` (used to unpack updates).
- The harnesses you want: the `claude` and `codex` CLIs and any ACP agent, installed and findable on the PATH of the process that starts the Host (`install` writes the installing shell's PATH into the unit).
- For a chat's browser: a Chrome or Chromium (`MOPILOT_HOST_CHROME` names one), else the Host downloads a pinned `chrome-headless-shell` into `<data dir>/browser-bin` on first use (`MOPILOT_HOST_BROWSER_DOWNLOAD=0` turns that off).
- One native module, carried with the Host: the Rust core (`mopilot_core.node`), built per platform (`darwin-arm64`, `darwin-x64`, `linux-{x64,arm64}-{gnu,musl}`; `shared/host/coreBuild.mjs`). It uses Node-API, so one file loads under any Node 22+ and nothing is compiled on the machine. Linux addons need glibc 2.17 or newer, or musl. A Host whose core is missing or does not load won't serve, and `status` says why (`core.problem`). The Host does not use `node-pty` or `sodium-native` (an agent's `terminal/create` is refused for now).

## Commands

    mopilot-host serve   [--data-dir <dir>]        run in the foreground
    mopilot-host status  [--data-dir <dir>]        JSON: version, harnesses {id, detected, signedIn}, capabilities, core {loaded, build, routes}, isolation
    mopilot-host login <harness> [--method <id>]   run the harness's own sign-in on this Host; prints the link and code (`claude` runs `claude auth login`, `codex` runs `codex login --device-auth`; at a terminal a line you type is passed to the sign-in, for the code Claude Code asks to be pasted)
    mopilot-host pair                              print a one-time pairing code for a client
    mopilot-host update --manifest <https url|file>  stage a signed version; the Host restarts into it once idle
    mopilot-host trust-update-key                  keep the public key (PEM) on standard input as the key updates are signed by
    mopilot-host install | uninstall               write or remove the systemd user unit / launchd plist

Installing an agent: a paired app asks `host.install { harness }` (feature `install`) for a harness `status` lists as missing and `installable`. The Host runs only the vendor's npm package from the app's install table (`shared/harnessInstall.mjs`; Claude Code, Codex and the ACP agents with an npm line) as `npm install --global --prefix <data dir>/tools`, with the npm beside the Node it runs on, as the Host's user (no root), one install at a time; a second request for the same agent joins it. npm checks each package against the registry's integrity hash, and the new CLI must answer `--version` before the install counts. `host.installStatus` reports it as one line (`queued`, `running`, then `done` with the version, or `failed` with npm's reason, secrets cut out); `host.installCancel` stops it. `<data dir>/tools/bin` is on the Host's PATH (after the PATH it was installed with), so the agent is found at the next status without a restart; removing that folder removes what the Host installed.

`status` asks the running Host, or reads the machine when none runs. `serve` prints a pairing code on start while no client is paired. `pair` prints a new one; a code pairs one client once, is good for 24 hours and is retired after five wrong tries. Nothing is fetched at start.

`install` writes the launchd agent `ai.mopilot.host` (its output goes to `<data dir>/host.log`) or the systemd user unit `mopilot-host.service`, set to restart the Host. `uninstall` stops the service and removes the unit; it keeps the data dir and the config dir (the chats, the Host's identity `host-id`, the pairings and the relay enrollments), says so, and a later `install` resumes with them. `uninstall --purge` also deletes the data dir, the config dir and the install tree it runs from (`~/.mopilot-host`; never a checkout), and leaves a data dir that is not plainly a Host's. The app's Remove on a machine that answers over ssh is the purge: the app forgets the machine and its pairing, so a Host that kept its side would only hold a stale pairing and relay enrollment (#4721); a machine that does not answer keeps its files, and the sheet says so. A systemd user service stops at logout unless lingering is on (`loginctl enable-linger <user>`); `install` does not set it, but the app's Add machine does (electron/host/install.cjs).

Environment: `MOPILOT_HOST_DATA` (data dir), `MOPILOT_HOST_ROOTS` (folders the picker may browse and clone into, `:`-separated; default the user's home), `MOPILOT_CLAUDE_BIN`, `MOPILOT_HOST_CHROME`, `MOPILOT_HOST_BROWSER_DOWNLOAD`.

## Claude Code

Claude Code chats (`claude:<id>`) run the app's own Claude adapter and harness on the Host (`host/src/claudeFamily.mjs`): the real Agent SDK in the Host process, driving the `claude` CLI found on the Host (`MOPILOT_CLAUDE_BIN` names one by hand), signed in with `mopilot-host login claude`. Nothing of the Mac's `~/.claude` is used. A message to a chat the Host has no session for starts a session in the folder it names, or resumes the one whose transcript is on disk (after a Host restart). The CLI is started through the Host's tracked spawn, in a process group of its own, so a Host killed hard leaves it for the next Host on the data dir to end (children.json), which also ends the chat's turn as cancelled (running.json). A running turn keeps the Host from being idle, so a staged update waits for it; stopping the Host interrupts the turn and asks each CLI to quit. A message's model and effort (`chat.send`) and a new chat's permission mode (`chat.start`) run its turn, `chat.permit` sets the mode for the chat's next turns and its live CLI (`default`, `auto-review`, `full-access`, `read-only`), and the `claude` entry of `host.status` lists the models the CLI offers (`models`: asked in the background and kept ten minutes, so absent until the first answer). The CLI is the one named by `MOPILOT_CLAUDE_BIN`, else the `claude` on the Host's PATH (the one `status` reports and `login claude` signs in). The stream carries the turn as ACP session updates (host/src/claudeAcp.mjs): `turnStart` with the person's message, message and thought chunks, tool calls and their results (command output, file edits, images), the todo list as a plan, a sub-agent's calls linked to their parent, `permission` cards, the context used, and `turnEnd` with how it ended (the CLI's own failure message, usage). A sub-agent's own text and thoughts, goal state and background tasks are not carried.

## Browser, tools and the app

The app is the executor of the tools a Host's agents call: it announces its tools after connecting (`host.toolsSync`), the Host relays each call of a harness to the app that owns the chat (`tool` event, answered by `host.toolResult`) and fails it with `app_offline` when no app is connected. ACP chats get the Host's sage-mcp shim (`bin/sage-mcp.mjs`, whose two streams the Host's Rust core frames) over the Host's tool socket, Claude Code gets in-process SDK MCP servers over the same registry, Codex gets the shim in each thread's config (`host/src/codexTools.mjs`). The browser tools drive a Chromium the Host starts when a chat first opens a tab (`host/src/browserService.mjs`) and stops 60 seconds after the last chat lets go.

## Through the relay

A paired app can also reach the Host from any network through MoPilot's relay (`relay/`, #2709), with no inbound port and no Remote Login. Over the paired connection the app sends `host.relayEnroll` (feature `relay`): a relay address, a relay id and secret the app issued for this Host, and its half of a fresh X25519 exchange. The Host keeps them in `<config dir>/relay.json` (0600), dials out to the relay with `Authorization: Bearer mh1.<id>.<secret>` (Node's own WebSocket), and pipes every stream the app opens into its own socket (`host/src/relayLink.mjs`), so a connection through the relay is served like one through an SSH tunnel. Everything on the relay is sealed end to end (`shared/host/relaySession.mjs`: the phone's root, chain and ratchet, a fresh exchange per session, XChaCha20-Poly1305 from `node:crypto`). When the app removes the machine the relay closes the Host's socket with 4403 and the Host deletes the enrollment; `host.relayForget` does the same when the app can still reach it, and `host.relayStatus` lists each enrollment's state (never its secret). A Host that has lost its enrollments (reset, reinstalled) has no phone to push to: it logs `push: no phone is linked to this Host…` for each waiting card it cannot push, and `host.status` reports `push: { phones, skipped, lastSkippedAt }` so the Mac's machine page says "No phone linked · push is off"; a phone whose own session to the Host does not open reads the machine as "Not reachable directly" and, while the Mac says the machine is up, enrols it again by itself (#4721). On macOS a Host started by launchd is kept off the local network until the machine allows it (System Settings › Privacy & Security › Local Network), so a relay on the same LAN (a self-hosted one at a private address) is not reached; MoPilot's relay is on the internet and is.

## Where things live

Data dir (`--data-dir`, `MOPILOT_HOST_DATA`, else `~/.local/share/mopilot-host`, or `~/Library/Application Support/mopilot-host` on macOS):
`host.sock` (moved to the system temp dir as `mopilot-host-<hash>.sock` when the path would not fit a unix socket), `host.lock`, `host.log` (the launchd unit's output), `threads/` (transcripts), `sessions/` (each chat's durable journal), `queues/` (messages held behind a running turn), `images/` (images a chat carries), `harnesses.json` (extra ACP harnesses `{ id: { label, bin, args?, env? } }`), `signed-in.json`, `updates/` (staged versions), `epochs.json`, `owners.json` and `continue/` (moving a chat to another host), `ledger/` (request keys), `tools/` (agents the Host installed: `tools/bin`, `tools/lib`), `children.json` and `running.json` (survivors and turns the next Host ends after a hard kill), `browser/`, `browser-bin/` and `downloads/` (the Host's browser).

Config dir (`$XDG_CONFIG_HOME/mopilot-host`, else `~/.config/mopilot-host`; `<data dir>/config` with a data dir other than the default one; the default folder spelled out, as the installed unit does, is still the default Host):
`secrets.json` and `safe-storage.key` (0600; there is no OS keychain on a headless machine), `update-key.pub`, `pairing.json`, `relay.json` (0600, the relay enrollments).

A Host and the app use different data dirs, and every path they key on (socket, lock, build lock) is derived from the dir, so they never share one.

## Updating

`mopilot-host update` takes a version only from a manifest `{ version, sha256, url, hostId, seq, notAfter, signature }` signed (Ed25519) by a key the Host trusts: its `<config dir>/update-key.pub` and every app paired with it (the install hands the Host the app's public key with `mopilot-host trust-update-key`, key on standard input). The signature covers all of it, so a manifest is refused when it is unsigned, signed by another key, made for another Host (`hostId` is the name in `host.challenge`), expired or valid for more than 30 days, or not newer than the newest build taken (`seq`, kept in `updates/floor.json`; the same number must be the same build). With no trusted key every update is refused. Nothing is downloaded before that is settled; a download follows redirects only to https on the manifest's own host (three at most) and is read as a stream: 64 KB for a manifest, 256 MB for an archive. The archive's SHA-256 is then checked against the manifest, and it is kept content-addressed under `updates/` and activated only when the Host is idle (no turn, no sign-in); under a supervisor the unit restarts it, otherwise it re-executes itself. A version that never serves after three starts is dropped. The app sends one itself: `machines.updateHost` (`host:update`) signs a manifest for the machine's Host with its own key, puts the archive and manifest on the machine over ssh and runs `update` there.

Each platform has its own archive, with its Rust core in `host-core/` (`mopilot_core.node`, and `build.json`, `{ build, sha256 }`). The app asks the Node the Host runs on which build it needs (`uname -m` cannot see a C library, or a 32-bit userland on a 64-bit kernel) and sends nothing to a machine it has no build for, whose Host keeps running. The core needs no signature of its own: the manifest's signature covers `sha256`, that archive's, so it covers the addon and its record. So the manifest format did not change, and a Host from before can update to this one. The Host then checks what arrived: `update` refuses a version whose record names another machine or whose addon does not match the record, keeping nothing and staying on the version it has (that command runs the code the Host was first installed with, so a Host installed before cores skips this check), and the loader (`electron/platform/core.cjs`) checks that hash before each load, on every Host. An addon that is missing or fails to load stops the Host from serving, with the reason in `status` (`core.problem`); an install that ends this way puts back the Host it replaced.

## What is not here yet

- Claude Code and Codex sign-in runs those CLIs as above and counts as done only when the CLI exits 0 and `claude auth status` / `codex login status` then says signed in; the exact prompts and output of the vendors' CLIs are not verified against real installs yet (real-machine acceptance).
- Codex turns run on the Host's own `codex app-server` and the Host's own Codex login (`mopilot-host login codex`); nothing of the Mac's `~/.codex` is copied, and relaying a Mac's Codex account to a Host is not part of v1 (docs/host-signin.md). A chat is refused with `harness_not_configured` and a one-line hint when `codex` is not on the Host's PATH or is signed out. Approvals for commands and file changes arrive as cards and are answered with `chat.answer`; approvals asked by a Codex sub-agent get no card, and other app-server requests (user input, elicitation, permission grants) are refused to the app-server. `chat.permit` sets the permission mode of later Codex turns; for the other families it stays unsupported. An app-server crash ends the running turn with an error; the next message resumes the thread. Command output is not streamed while the command runs.
- A turn running when the Host stops hard is ended as cancelled by the next Host; a graceful stop interrupts it.
- Images beyond JPEG, PNG, GIF, WebP and BMP: those pass through (a BMP is turned into a PNG in `host/src/imageDecoder.mjs`); HEIC, TIFF and the rest are converted by `sips` on a macOS Host and are otherwise left out of the message as "couldn't be attached".
- Remote Control and Claude in Chrome: a Host's Claude chats run without them, as do goal state, background tasks, the chat's automatic title and a sub-agent's own text. Each tool call is a card the app answers (`chat.answer`) unless the chat's permission mode allows it. MCP elicitation forms and sign-in links requested by a tool are declined.
- Computer use on the user's Mac and the user's Chrome are not remote; the Host reports `capabilities.cu` and `bu` as false and the app hides those tools for a Host's chats. A Host with a helper in a logged-in session may report `capabilities.desktop` for its own desktop (docs/host.md, "The Host's own desktop").
- Windows: the Host is for POSIX machines.
- A musl machine without systemd (Alpine, Void): the core has a build for it, but `install` writes a systemd unit, so the app's Add a machine stops at the service step there; run `mopilot-host serve` under the machine's own service manager.
- Key rotation for signed updates (a new app key is trusted once it is paired; an old one stays trusted until its pairing is removed by hand).
- A run on a Linux machine and on a real systemd unit: the install, pairing, a fake-agent chat, a hard kill, an update and uninstall ran on a macOS machine under launchd (`scripts/host-accept.mjs`); systemd is tested as text and by Linux CI only, and no real Claude Code or Codex login has been used.

`status` lists which isolation guarantees this machine gives and which are blocked, so what it prints is what to trust.

## Managed policy and audit record

- A root-owned `managed-policy.json` (`/etc/mopilot-host/` on Linux, `/Library/Application Support/MoPilot Host/` on macOS) constrains this Host: allowed harnesses, a permission ceiling, no phone clients, organization sign-in only, folder roots, spend and approval limits. A file the Host's user can write is ignored and reported.
- The audit record is one metadata-only, hash-chained line per decision in `<data dir>/audit/<day>.jsonl` (0600, 90 days by default, `audit.retentionDays` from the managed policy). With `audit.required` an action runs only after its line is written, otherwise it is refused with `audit_unavailable`.
- `mopilot-host audit export [--since <date>] [--verify]` prints the lines, or checks the chain. The app reads the record with `host.auditRead` (desktop and CLI clients only).
