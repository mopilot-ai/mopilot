MoPilot on the phone: a remote for everything the Mac runs

The agents, the browser, the computer and MoMo keep running on the user's Mac. The phone is a second client of main, like the Chrome side panel already is, reached through a relay that only ever sees ciphertext. One app, every harness, every account, MoMo included.

Decisions already taken confirmed by the product owner on 2026-10-26; the rest of this document builds on them

Zero-knowledge relay
Every message between the Mac and the phone is end-to-end encrypted. The relay stores and forwards opaque blobs, holds push tokens and presence, and can never read a chat, an approval or MoMo's memory. This is the privacy difference from Claude Remote Control and vicoa, whose servers keep the transcript.
A standalone app
A native iOS and Android app (not a PWA). Recommended stack: Expo / React Native, so the phone shares shared/ TypeScript with the desktop (approval normalization, notice titles, item shapes) instead of re-implementing them, as a Flutter app would have to.
Self-hostable relay
The relay is one container with no secrets of its own. MoPilot hosts relay.mopilot.ai; a team can run the same image behind their own domain, and the QR code names the relay, so the apps need no setting.
MoMo is in scope
The personal agent is the strongest reason to have a phone app at all. MoMo's chat, its "needs you" cards, its memory and its routines are first-class on the phone, under the same trust layer, which stays on the Mac. See MoMo on the phone.

Three things follow. Outbound only: nobody opens a port on the Mac. Approvals are the killer feature: every product pushes "needs you" and lets the phone answer. Breadth is open: each vendor remotes its own harness; a client that remotes Codex, Claude Code and ACP agents under one account, plus a browser, a computer and a personal agent, has no equivalent.

System architecture

What the Mac keeps

Code, credentials, harness homes, MoMo's memory and audit log, the keys. Execution never leaves. The phone is a window, as in every product surveyed, so the Mac must stay on until M6 gives main a life of its own.

What the relay keeps

Ciphertext in a short-lived mailbox per device pair, presence, push tokens, account id. No plaintext, no keys, no chat titles. It is replaceable: a self-hosted relay is the same image behind another domain.

What the phone keeps

Its device key and the pair key of each Mac in the Keychain; a cache of followed chats, encrypted at rest by the OS. It never holds a harness credential or an API key.

Principles what every milestone is checked against

  1. Main owns the truth; the phone is a client. No state lives only on the phone or the relay. The phone sends intents, never runs a turn, exactly like a window (docs/multi-harness/ARCHITECTURE.md §1).
  2. One behavior on every harness. The remote protocol speaks MoPilot chat ids and translated items. No harness name or id prefix reaches the phone as a feature gate; Codex, Claude Code and ACP chats look and act the same, including cards and Stop.
  3. Zero knowledge, measured. The relay's schema has no column that could hold plaintext. A test runs the relay against a captured session and asserts that nothing but ciphertext, sizes and timestamps is stored.
  4. Same authority as a window, never more. A remote answer passes the checks a window answer passes (ownership, current rev, offered choice). A remote device can't raise a chat's permission mode above what the Mac allows, and Bypass permissions can't be chosen from the phone.
  5. Degrade honestly. Mac asleep, relay down, phone offline: the UI says queued, offline or failed and never pretends. A message typed offline is queued on the phone and marked so; it goes when the pair reconnects, through the same ChatController queue as any follow-up.
  6. Minimal push. A notification carries a fixed title, a kind and an opaque chat reference, in line with shared/momoNotices.mjs. Chat titles in push are a per-user opt-in.
  7. MoMo's trust layer never moves. Sentinel, trust gate and audit log run on the Mac; the phone only answers the cards they raise and reads what memory IPC already exposes.
