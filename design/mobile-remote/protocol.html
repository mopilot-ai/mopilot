Pairing and keys public-key pairing over an untrusted relay; the account only helps the two devices find each other

Identities

  • Each Mac has an identity key pair (X25519 for agreement, Ed25519 for signing), made on first use and kept only in safeStorage, the way electron/momo/auditKey.cjs keeps the audit key. Each phone has the same pair in its Keychain or Keystore, hardware-backed where the OS offers it.
  • A pair is one phone and one Mac. Its root key comes from X25519 between the two identity keys, HKDF'd with both device ids. From the root key each direction derives its own sending key; message keys ratchet forward per message (a symmetric ratchet with a counter), so the relay replaying or reordering a blob is detected and a captured blob can't be decrypted with a later key.
  • Payloads are sealed with XChaCha20-Poly1305 (libsodium on both sides; sodium-native in main, react-native-libsodium on the phone). The envelope's header (pair id, direction, counter) is authenticated, never encrypted.

Pairing flow

  1. Settings › Devices › Pair a phone shows a QR code: { v:1, relay, macId, macPub, code, exp }. code is a 32-byte one-time secret; exp is two minutes away. The Mac registers the pending pairing with the relay, signed with its account JWT.
  2. The phone scans, derives the root key, and sends a sealed pair request through the relay: its id, its public keys, a device name, and HMAC(code, both public keys) as proof it saw the QR.
  3. The Mac verifies the proof, shows the phone's name and a six-digit safety number (a short hash of both public keys), and asks the user to confirm. The phone shows the same number. Confirming writes the device to the Mac's device list (safeStorage) and to devices on mopilot.ai with kind phone.
  4. From then on the pair key does the authenticating; the account JWT only lets each device open its relay socket and lets the relay route by account.

Revocation and rotation

  • The Mac's Devices list removes a phone immediately; the phone sees unpaired on its next frame. mopilot.ai's Trusted devices page revokes the token, which closes the relay socket.
  • Pair keys rotate when either side asks (a new X25519 exchange inside the sealed channel), and every 30 days by default. An identity key rotation is a re-pair.
  • Clearing MoPilot's data, or a new Mac restored from backup, is a re-pair: the identity key is in safeStorage and does not travel with user data on purpose.

Open question for review: v1 uses a symmetric ratchet, not a full Double Ratchet. Forward secrecy per message holds; post-compromise security needs the 30-day rotation. Happy's scheme was not publicly documented at survey time, so this is our own choice.

Transport outbound WebSocket from both devices to the relay; a mailbox when one side is away

  • Main opens one WSS to the relay per account, authenticated by the account JWT, and keeps it up with the reconnect and backoff rules of electron/relay.cjs's peers. It never listens on a port.
  • A frame is { pair, dir, ctr, nonce, box }; box is one sealed message. Frames ≤ 256 KB; attachments go as chunked messages with their own stream id, capped at the Chrome panel's attachment limits.
  • The relay keeps a per-pair mailbox: frames for an offline peer wait up to 7 days, then are dropped and the sender told. The phone drains its mailbox on launch and on each push.
  • Presence: each Mac publishes online / sleeping / gone through the relay; the phone shows a machine card with a dot, like Claude's device card. A Mac that misses three pings is gone.
  • Several Macs under one account each have their own pair with the phone. The phone's home screen lists machines, then chats; a chat id is scoped by machine.
// a sealed message, after decryption
{ id: 'm_01J…', t: 1761436800123,
  kind: 'request' | 'reply' | 'event' | 'ack',
  // request / reply
  method: 'chat.send', params: { chatId, text, attachments },
  inReplyTo: 'm_01J…', ok: true, result: {...}, error: { code, message },
  // event
  ev: 'session.patch', chatId, rev: 418, patch: [...] }

// the frame the relay sees
{ pair: 'p_9f…', dir: 'p2m', ctr: 1032, nonce: '…', box: '…' }

Requests carry an idempotency id; main remembers the last 1,000 per pair and replays the reply instead of acting twice, so a phone retrying after a dropped socket can't send a message twice. The ctr must increase strictly per direction; a repeat or a rewind closes the pair's session and asks the phone to resync.

Every method's params are validated in main by the same kind of input checks capabilities/browser/chromePanel.cjs runs for the panel today; the two clients share one schema module so the panel can't drift from the phone. A method the Mac doesn't allow this device answers error.code = 'forbidden', which the phone shows as a grey control, never as a silent no-op.

Events and translation main sends thread items, not raw harness events

  • session.patch: the SessionState patch stream as windows get it, with rev. A phone that misses a rev asks for a snapshot. This carries turn status, the queue, the cards up, the goal and the plan.
  • items.append / items.replace: thread items (user message, assistant text, tool call with status, card, notice, compaction mark). Today src/harness/claudeTranslate.ts and src/harness/acp.ts build these in the renderer from raw events; for remote clients main runs the translation, batched by core/crates/batcher, and sends the result.
  • Streaming text is sent as deltas coalesced to ~10 Hz, then a final item; the phone renders the same way the window does so a reply reads identically on both.
  • machine.presence, device.unpaired, mailbox.dropped: the few events about the connection itself.

Moving translation into main is the one refactor the phone forces on the desktop, and it also removes a long-standing split: windows and the Chrome panel will consume the same items. It lands first, behind the existing renderer path, in M1, with the shared/claudeTranslate/ modules as the base.

Harness specifics (Codex notifications, Claude SDK events, ACP session updates) stay in the adapters. The phone's item renderer has no harness branch, which is the multi-harness rule of AGENTS.md applied to a new surface.

Approvals, questions and plans from the phone the same authority as a window, checked the same way

  1. A card is raised in main and joins SessionState.approvals (harness permission, Sage card or momoAction). Main notifies: the OS banner through notify.cjs and, for each paired phone, a push of the same kind.
  2. The phone, following the chat, receives the card in session.patch: title, detail lines, choice keys, the card id and the rev it was raised at. Tool arguments go only when the card already shows them to a window.
  3. The user taps a choice. The phone sends card.answer { chatId, cardId, rev, key }.
  4. Main checks: the device follows the chat; the card is still up; rev is not older than the card's; key is one the card offered; the device is allowed the choice (a permission-raising choice like "always allow" is allowed only if the Mac's policy lets a window choose it too). The first valid answer from any surface wins; later ones get error.code = 'stale' and the phone shows who answered.
  5. The answer goes through the exact path a window's does (claude:permission, Codex server reply, acp/permission, ApprovalBroker), so the harness can't tell a phone answered.

Questions and forms

AskUserQuestion and ACP forms use shared/claudeAnswer.mjs and chromePanelForm.cjs today. The ownership check in session/questionIpc.cjs ("the answering window shows the chat") gets a sibling: "the answering device follows the chat". Both checks live in one helper so they can't diverge.

Plans

A plan waiting for approval is in SessionState.plan; the phone shows it read-only with Approve / Ask for changes, which map to the same controller actions as the window's buttons (controllerPlan.cjs).

What a phone can't do

  • Choose Bypass permissions, or raise a chat above the Mac's permission ceiling.
  • Answer a card for a chat it doesn't follow, or a card that asks for a desktop-only act of the user (a macOS privacy prompt, a sign-in in the in-app browser): those say "finish on your Mac".
  • Change Settings, pair or unpair other devices, or turn MoMo on or off.

Spike findings that change the design M0, #2615; read from design/mobile-remote/spike/README.md

  • The phone library has no X25519. react-native-libsodium 1.7.0 exports no crypto_scalarmult or crypto_kx_*. The phone does key agreement with @noble/curves (matches sodium-native, checked); it runs once per pairing or rotation, so pure JS is fine. The seal and open path still uses libsodium.
  • HKDF is not in the wrappers. The phone has only the unstable native HKDF; the Mac uses node:crypto. The app pins the library version and runs shared/remote/vectors.json as a self-test at launch, so an API change fails loudly.
  • Ratchet state must be durable on both sides. A reconnecting client keeps its chain key and last counter per pair (phone: Keychain). A fresh session cannot open queued frames. Counter rule: strictly increasing, at most 1000 skipped, and state moves only after the box authenticates.
  • "Needs you" is an alerting push, not a silent one. iOS suspends the app and its socket; a silent push is throttled (two or three per hour), dropped after a force-quit and not guaranteed. The mailbox is the source of truth; a silent push only shortens the delay.
  • The notification extension is a separate native target. It decrypts the opt-in chat title in its own process (tight memory), so it needs libsodium linked natively, the pair's material in a shared Keychain group and App Group, and a read-only peek or per-notification key so it never advances the app's ratchet. In Expo this is a config plugin or custom target (an EAS step), not JS. Android's FCM data message has no such constraint. This is new work in M2.

Push notifications APNs and FCM through the relay; the Mac decides when, the content is a fixed title

  • The phone registers its APNs or FCM token with the relay, bound to its device id. The relay never gives tokens to the Mac.
  • When notify.cjs would show a banner, main also sends the relay a push request in the clear: { pair, kind, ref }, where kind ∈ needsYou · done · momoNeedsYou · machineOffline and ref is an opaque chat handle the phone resolves locally. The notification's title is the kind's fixed text, the body is empty, as shared/momoNotices.mjs does for MoMo today.
  • The relay applies the notifier's merge rule (one per chat, "needs you" outranks "done", same kind within 60 s merges to "(n)"), so phone and Mac agree on what the user saw.
  • An opt-in setting adds the chat's title to the push. It is sent sealed inside a tiny notification extension payload that the phone decrypts on device (iOS Notification Service Extension, Android data message), so even then the relay stays blind.
  • Quiet hours and the "Notifications" preference on the Mac apply to push as they do to banners; a "needs you" that fell in quiet hours is pushed once when they end.

Self-hosted relays and push

APNs needs Apple's key for our app id, so a self-hosted relay can't push to the App Store build directly. Two supported shapes:

  • Push proxy (default): the self-hosted relay forwards { token, kind } to push.mopilot.ai, which only holds the Apple and Google keys and sees no account or chat.
  • No push: the self-hosted relay runs without it; the phone falls back to background fetch and shows the state when opened. The UI says so in Settings.

Teams that build the app themselves can set their own keys on their relay.

MoMo on the phone the personal agent is the phone's first job; its trust layer stays on the Mac

MoMo is a long-lived main chat in its own workspace (electron/momo/mainChat.cjs), with memory on the Mac (memory.cjs), routines the scheduler runs in isolated background chats (routines.cjs), local sources (Calendar, Reminders, Files) behind a hub that decides and audits every read, and a trust gate that raises a momoAction card before anything side-effecting. The Feed and Topics are being removed (#2609), so the phone's MoMo is Chat, Needs you, Memory, Routines.

Rules that carry over unchanged

  • Closed alpha: access.cjs gates MoMo on the account's features from /api/me. machine.hello tells the phone whether MoMo is allowed for this account; an uninvited account sees no MoMo tab, and every momo.* call is refused in main, as every IPC handler is today.
  • Nothing personal on the lock screen: MoMo's push is "MoMo needs you", title only, which is the existing rule of shared/momoNotices.mjs.
  • Memory is data: the phone's memory tab shows facts decrypted on the Mac and sent sealed; the relay stores none of it in the clear, and the phone caches it encrypted at rest. A fact edited on the phone is written by memory.cjs on the Mac, nowhere else.
  • Audit: a phone-answered card is audited like a window-answered one, with the answering device's id in the intent entry (a new field, so a review of the log can tell which device approved).
  • No harness name in copy: the MoMo tab names the brain the user picked, or none.

What the phone adds for MoMo

  • Ask MoMo from the phone's home screen and from a notification's reply field: the same single-target path as Quick Chat's Ask MoMo.
  • A routine's result read on the way to work; a proposed routine approved from the lock screen card.

Deliberately out of scope, for the owner to decide later: the phone as a MoMo source (location, photos, phone calendar). It would make MoMo far more useful and would also be the first time data originates off the Mac; it needs its own trust design (where the egress taint starts, what the audit log records). Not in M1–M6.
